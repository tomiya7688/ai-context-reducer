# 補助ツールのコメントを書く規則

**対象:** `tools/` 以下のPython・Goなどのソースと、そのテストです。これはObaPickを開発する人とAIが従う規則であり、一般の読者向けのツール利用説明ではありません。

コメントの形式は、[Json-like-comment-outsの日本語仕様](https://github.com/tomiya7688/Json-like-comment-outs/blob/main/docs/jp/SPECIFICATION.md)を正とします。本書ではObaPickのソースに適用する書き方だけを示します。別の形式を独自に作りません。

## 1. 関数・メソッド・型の宣言前

- **関数・メソッド**の宣言直前に、読み手が理解できる日本語で `責務`・`処理`・`引数`・`戻り値` を書いてください。
- **クラス・構造体・インターフェース**の宣言直前には `責務`・`フィールド`・`処理` を書いてください。状態を持たないものでは、その理由を説明し、形だけの情報を増やさないでください。
- 宣言名、引数名、戻り値の順序はソースに合わせます。引数がなければ `引数: []`、戻り値がなければ `戻り値: []` と書きます。
- `責務`には、どの入力から何を決め、何を返すかなど、その宣言**固有の仕事**を書きます。「処理を担当する」「内部で変換する」だけで済ませません。
- `処理`には、重要な段階を実際の順番で書きます。単にコードの一行ずつを日本語へ置き換えたり、機械的に項目を水増ししたりしません。
- 機能に関係する失敗条件や副作用が重要なら、`エラー`・`副作用`・`補足`を追加できます。
- 正式なソースへ空欄の説明を残さず、実装に合う内容を記載してください。処理・入出力が変わったらコメントも直します。
- 状態を持たない型なら `フィールド: []` とし、関数やメソッドに引数・戻り値がなければそれぞれ空の一覧とします。実在しない入出力を書かないでください。
- Pythonの装飾子や、宣言に付く属性指定がある場合は、その指定の前に構造化コメントを置き、どの宣言を説明しているか分かるようにします。
- 以前の一行コメントを残したまま別の説明を積み重ねず、実装を確認して具体的な構造化コメントへ置き換えます。関数内部の必要な日本語コメントは残してください。
- コメントには**固有名詞と、実際のプログラムの識別子・入出力項目名以外の英単語を書かない**でください。項目名は日本語を使います。例えば `file` とだけ書かず「対象ファイル」と書きます。プログラム上の `filePath` などの名前を示す必要がある場合は正確に記載できます。

Pythonでの例：

```python
# {
#   責務: [
#     normalize_path: 検索対象の場所を比較しやすい表記へそろえる
#   ],
#   処理: [
#     1: 区切り文字を統一する,
#     2: 先頭の相対位置表示を取り除く
#   ],
#   引数: [
#     path: 対象の場所
#   ],
#   戻り値: [
#     1: 表記をそろえた場所
#   ]
# }
def normalize_path(path: str) -> str:
    return path.replace("\\", "/").removeprefix("./")
```

Goでの例：

```go
// {
//   責務: [
//     readName: 入力された名前の前後の空白を取り除く
//   ],
//   処理: [
//     1: 前後の空白を除去する
//   ],
//   引数: [
//     name: 読み取った名前
//   ],
//   戻り値: [
//     1: 空白を取り除いた名前
//   ]
// }
func readName(name string) string {
    return strings.TrimSpace(name)
}
```

## 2. 関数内部には必要な通常コメントも書く

Json-like形式は**宣言全体の説明**です。内部の分岐、境界条件、失敗時の動作、理由、重要な変数など、コードだけでは分かりにくい箇所には、通常の日本語コメントを追加します。内部コメントまで波括弧で囲む必要はありません。

例えば、検索件数が上限に達してから一致を一件余分に検査する場合、次のように「なぜ余分に調べるのか」を説明できます。

```go
// 表示しなかった候補が実際に残っているか判定するため、一件余分に取得する。
wanted := maxResults + 1
```

**コメントを極端に減らさないこと。** 機能の境界、失敗時の保証、戻り値の意味、後続処理に必要な前提があるのに、宣言前の一行だけで済ませてはいけません。一方、読めば自明な代入や閉じ括弧に逐一コメントを書くことも不要です。

## 3. 確認すること

- 変更した関数・型に日本語の説明があり、宣言名・引数・戻り値と一致する。
- 関数内部で読み間違えやすい条件と重要な判断理由に、日本語コメントがある。
- 固有名詞・実際の識別子を除き、コメント本文に英語を混ぜていない。
- 宣言の形式は上記の[日本語仕様](https://github.com/tomiya7688/Json-like-comment-outs/blob/main/docs/jp/SPECIFICATION.md)に合う。
- テストにも「何を確かめているか」を具体的に記し、汎用的な定型文で済ませない。

この規則はコメントそのものの品質を確認するものです。構文・引数の機械検査と全ソースへの移行は、既存のIssue #70～#79に沿って順に実装します。**検査を実装する前から、全コードが自動検証済みだとは主張しません。**
