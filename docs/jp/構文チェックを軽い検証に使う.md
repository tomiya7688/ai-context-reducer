# 構文チェックを最初の確認に使う

構文チェックは、コードがその言語の書き方の決まりに従っているかを確かめる検査です。変更直後に実行すると、括弧や記号の抜けなど、すぐ直せる書き間違いを早く見つけられます。検査結果は問題のある箇所だけ確認すればよいため、正常なファイルの一覧や解析結果全体をAIに読ませずに済みます。

## 例：条件式を変更する

注文を割り引く条件を `price > limit` から `price >= limit` に変えるとします。構文チェックは、変更後の式の書き方が正しいかを確認できます。しかし、境界値でも割引するという要件に合っているか、他の処理に影響しないかまでは判断できません。

そのため、まず構文チェックで書き間違いを除き、その後、境界値を含むテストや要件に対応する確認を行います。構文チェックに通ったことだけを理由に、変更が正しいとは判断しません。

## 構文の確認と動作の確認

構文を調べる解析器は、ソースコードを言語の文法に沿って読み取り、書き方の誤りを見つけます。たとえば、閉じ括弧の抜けや、式の置き場所の誤りを検出できます。

一方、構文が正しくても、呼び出した関数が存在するか、型が合うか、計算結果が要件どおりか、実行時に期待した動きをするかは別の確認が必要です。コンパイラー、型検査、テスト、実行確認などから、変更の内容に合った方法へ進みます。

## 進め方

変更したコードを構文チェックにかけ、問題があれば報告されたファイルや行の周辺を直します。問題がなければ、それを確認結果として記録し、変更内容に必要なテストやコンパイルなどを行います。チェックが使えない、対象の言語や版に対応していない場合は、成功扱いにせず、その制約を明らかにして既存の検査方法を使います。検査器をこの確認のためだけに自動導入する必要はありません。

小さな修正で、通常のコンパイルやテストがすぐ実行できるなら、構文チェックだけの工程を増やさず、その方法で確認して構いません。構文チェックは早い手掛かりであり、完了の判定そのものではありません。
