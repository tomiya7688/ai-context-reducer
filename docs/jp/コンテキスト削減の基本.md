# コンテキスト削減の基本

ここでいう「コンテキスト」は、AIが依頼を処理するために受け取る指示、コード、資料、検索結果、検査結果です。コンテキストを減らすとは、必要な根拠を残したまま、今回使わない情報をAIに渡さないことです。

必要な情報まで外すと、AIは実装や確認を誤ることがあります。目的は無条件に短くすることではなく、「何を調べ、何を選び、何を原文で確かめるか」を決めることです。無関係なソースや全件ログを一緒に渡すほど、その分も入力に含まれ、必要な仕様やエラーに使えるコンテキストの余地が減ります。

## 例: 設定ファイルのエラー表示を直す

「設定を読み込めないときに、利用者へ理由を表示する」という変更を考えます。プロジェクト全体をAIに渡すと、画面、設定の読み込み、ログ出力、テストなど、多数のファイルから今回の変更先を探すことになります。

作業を頼む人がまずファイル名や関数名を検索し、設定を読み込む処理と関連テストの候補を取ります。候補一覧全体ではなく、その2か所と変更条件をAIに渡します。AIには元のソースとテストを確認させ、別の影響先が見つかった場合だけ対象を広げます。

```text
変更したい内容
  -> 関係しそうな処理とテストを探す
  -> 該当するソースコードを読む
  -> 必要な変更と確認を行う
```

この流れなら、プロジェクト全体を先に読み込まずに作業を始められます。案内や一覧は読む場所を見つけるためのものです。実装の判断や結果の確認には、元のソースコードやテストへ戻ります。

## AIにどう渡し、どう確認するか

プロジェクトで繰り返し使う決まりは、利用するAIツールが実際に読む指示ファイルや設定へ置きます。自動で読むかはツールによって違うため、設定を確認してください。一度だけ使う場合は、依頼文に手法の文書と対象箇所を直接指定します。

```text
設定のエラー表示を直してください。
まず設定読込処理と対応テストの候補を探し、候補の場所と理由を示してください。
選んだ元コードとテストを読んで変更し、関係するテストを実行してください。
追加の影響先が見つかったら対象を広げてください。
最後に、読んだファイル、実行した確認、結果、未確認の範囲を報告してください。
```

利用者は、報告されたファイルと確認結果を、表示される作業記録や差分と照らします。利用環境が読み込み記録を表示しない場合、自己申告だけで「実際に読んだ量が減った」とは証明できません。その場合は、候補から必要な原文へ進めたことと、必要なテストを省いていないことを確認します。トークン数を測る機能がある環境では、同じ種類の作業で前後の値を比較できます。

## 情報を選ぶ三つの方法

### 1. 機械的に調べられることは先に調べる

ファイル名、関数名、読み込んでいる別ファイル、構文の誤りなどは、プログラムで一定の方法により調べられます。AIに大量のソースコードを読ませて、こうした一覧を手作業で作らせる前に、機械で取り出して候補を絞ります。

たとえば、変更されたファイルと対応するテストを先に探せば、関係のないテストをすべて読む手間を減らせます。機械的な調査は候補を絞るために使い、変更の意味や設計上の判断は元の実装を読んで確かめます。

### 2. 繰り返す手順をまとめる

毎回同じ順に「変更箇所を探す、関連テストを探す、必要な確認を選ぶ」と進めるなら、その手順を短い案内やスクリプトにまとめられます。AIは確認の順番を何度も考え直さず、結果を見て必要な作業に移れます。

一度しか使わない手順や、まとめることで新たな設定・保守が増える仕組みまで自動化する必要はありません。繰り返しの負担が、仕組みを維持する負担より大きい場合にまとめます。

### 3. 関係する部分だけ読む

作業対象を特定したら、その実装、指示、資料、テストのうち、今回の判断に必要なものを読みます。短い一覧や要約を使うときは、どのファイルや記録を元にした情報か分かる形にします。

一覧や要約だけで変更を確定せず、必要な箇所は元の資料へ戻って確認します。関係する情報まで省くと、コンテキストは減っても判断の根拠を失います。

## 使うとよい場合 / 使わなくてよい場合

たとえば、変更するファイルと対応テストが依頼から分かる一度きりの修正なら、それらを直接読めば十分で、索引や専用の案内を作る必要はありません。同じ種類の依頼で毎回複数の機能から対象を探しているなら、最近の作業で探し直した場所を確認し、短い一覧や手順にまとめると次回以降の探索を減らせます。

判断の目安は、繰り返しの作業で減る検索・再読の手間が、一覧や手順を作成・更新する手間を上回るかです。導入後は、同じ種類の作業で関係する原典へ早く進めたか、必要なテストを省いていないかを確認します。方法ごとの具体例は[導入優先度](導入優先度.md)を参照してください。

## 正確さを保つ

読む量を減らすことより、必要な情報を正しく確認することを優先します。調査が途中で止まった場合や、読めなかったファイルがある場合は、その範囲を明らかにします。調べた範囲が狭いことを、プロジェクト全体を確認したかのように扱いません。

手法の一覧と使い分けは[手法一覧](手法一覧.md)にあります。個別の手法は、それぞれの文書で導入方法と向いている状況を説明しています。

## 補助ツールと呼び名

検索、索引、作業メモ、検証選択などの任意ツールは[手法と補助ツールの対応表](手法と補助ツールの対応表.md)から選べます。まずは既存の検索や短い指示で試し、繰り返しの手間が残る場合だけ導入します。この考え方は一般に「コンテキストエンジニアリング」や「コンテキストルーティング」と呼ばれることがありますが、このリポジトリでは実際に何を読む・渡すかを手順で説明します。
