# 場所ごとに作業ルールを分ける

大きなリポジトリでは、全体に共通するルールと、特定のアプリだけに必要な手順を別の場所に置きます。作業対象のファイルが決まったら、リポジトリ共通の案内と、そのファイルを含むフォルダーに適用される案内だけを確認します。

## 例：Desktopアプリの設定を直す

Desktopアプリの設定画面を変更するとします。プロジェクトにはDesktopとWebの両方があり、ビルド方法やテスト方法も異なります。

```text
repo/
  AI_CONTEXT.md                 # 全体で守るルール
  apps/
    desktop/
      AI_CONTEXT.local.md       # Desktopだけのビルド・テスト手順
      src/settings/              # 今回変更するファイル
    web/
      AI_CONTEXT.local.md       # Webだけのビルド・テスト手順
      src/
```

`apps/desktop/src/settings/`を変更するときは、全体に適用される`AI_CONTEXT.md`と、Desktop向けの`apps/desktop/AI_CONTEXT.local.md`を読みます。Webの手順は今回のファイルには適用されないため、読む必要がありません。

たとえば全体の案内には「保存形式との互換性を保つ」と書き、Desktopの案内には「Desktopの起動確認にはこのコマンドを使う」「設定画面のテストはこの場所にある」と書きます。Webだけで使うビルド手順を全体の案内から外すことで、Desktopの作業者は関係のない手順を読まずに済みます。

## ルールを置く場所

全体の案内には、どの部分を変更するときも守る条件と、各部分の案内の探し方を置きます。特定のアプリのビルド方法やローカル設計上の制約は、そのアプリのフォルダーに置きます。すべてのフォルダーに専用の案内を作る必要はありません。繰り返し必要な固有ルールがある場所だけに追加します。

上の例なら、Desktopの案内に全体ルールを丸ごとコピーせず、Desktopで追加して守る条件だけを書きます。親の案内が変わったとき、同じ文章を何か所も直す手間を減らせます。

## 対象ファイルに適用される案内を読む

作業では、対象ファイルまでのフォルダーをたどり、その途中にある案内を確認します。

```text
repo/AI_CONTEXT.md
  └─ apps/desktop/AI_CONTEXT.local.md
       └─ apps/desktop/src/settings/config.py
```

`apps/desktop/src/settings/config.py`なら、ルートと`apps/desktop/`の案内が対象です。隣の`apps/web/`にある案内は対象外です。さらに`apps/desktop/src/settings/`にも案内がある場合、そのフォルダー内だけに適用される追加条件として確認します。

エージェントがフォルダーごとの案内を自動で読み込む機能を持たない場合は、ルートの案内に「対象ファイルまでのフォルダーにある案内を確認する」と書き、担当者がたどります。ファイル名や自動読み込みの範囲は使うツールによって違うため、既定だと思い込まず、プロジェクトの設定を確認します。

## 内容が食い違ったとき

ルートの案内はリポジトリ全体の条件、下位フォルダーの案内はその場所に追加される条件を説明します。たとえば、ルートが「保存形式を変えない」と定めているなら、Desktop向けの案内だけでその条件を無断で取り消してはいけません。作業依頼は今回の目的や完了条件を示しますが、長く有効なルールを黙って無効にするものではありません。

ただし、指示の優先順位は利用するエージェントやリポジトリの規則によって異なります。矛盾を見つけたら独自の順序で片方を選ばず、該当する仕様や原典を確認します。それでも決められない場合は、実装前に矛盾点を明らかにします。

## 使うと効果がある場合

アプリごとにビルドやテストが異なる、同じルールを毎回読み直している、ルートの案内が長くなっている、といった場合に役立ちます。対象のフォルダーから必要な案内だけを追加で読めるため、無関係なアプリの手順を作業ごとに読み込まずに済みます。

小さなリポジトリで、短い全体案内からコードとテストへ迷わず進めるなら、場所ごとの案内は不要です。ルールがほとんどないフォルダーに空の案内を作ったり、同じルールを複製したりせず、繰り返し必要になる場所から始めます。

## 導入するときの確認

1. どのルールがリポジトリ全体で共通かを決め、ルートの案内へ置きます。
2. 特定のアプリだけに必要な手順や条件を、そのアプリのフォルダーへ置きます。
3. 対象ファイルから、どの案内が適用されるか分かるようにします。
4. 1つの作業例を使い、関係する案内だけで必要な条件と確認方法が分かるか確かめます。

機械的に適用範囲を調べる補助ツールはあります。導入やコマンドの説明は[scoped-guidesのREADME](../../tools/common/small/scoped-guides/README.md)を参照してください。この考え方自体は、ツールを使わず手で案内をたどっても実践できます。
