# 作業ごとにAIの役割とチャットを分ける

実装の相談を続けたチャットで、そのままコメント作成やレビューも頼むと、次の作業には不要な相談まで会話に残ります。まずは冒頭で、今回のAIの担当を短く伝えてください。

```text
あなたはコードレビュー担当です。
設定保存の修正を、仕様と変更差分に照らして確認してください。
ファイルは編集せず、不具合の候補を場所・発生条件・影響・根拠付きで報告してください。
確認していない範囲も示してください。
```

「あなたはレビュー担当です」だけでは、何を確認し、何を返すかまでは決まりません。役割に加えて、目的・対象・変更してよい範囲・確認観点・返す結果を指定します。これだけなら、いつものチャットで試せます。

別の作業の会話が長くなったときは、新しいチャットを開き、必要な情報だけ渡します。同じチャットで「ここからレビュー担当」と書くだけでは、以前の会話を入力から外せません。

## どこまで分けるか決める

| 今回の状態 | 試す進め方 | 判断の例 |
| --- | --- | --- |
| 一つの質問や短い修正で終わる | 同じチャットで目的と返答形式を伝える | 関数名を一つ直すためだけに三つのチャットを作らない |
| 目的は同じで、確認観点だけを変えたい | 同じチャットで役割と観点を指定する | 変更後の差分をコメント規則に照らして見直させる |
| 実装からレビューへ移り、過去の試行錯誤を渡す必要が薄い | 新しいチャットに仕様・差分・確認結果を渡す | 不採用案の長い相談を除き、保存形式を守ったか確認させる |
| 同じ役割を別の作業でも繰り返す | 短い役割の指示を保存して使い回す | レビューの観点を保存し、対象の版と差分は毎回入れ替える |

原因をまだ絞れておらず、直前の検査結果とのつながりが重要なら、急いで分けずに同じチャットで続けられます。別チャットにする場合も、失敗した条件や反例など、判断に必要な事実は引き継いでください。

チャットを分けても、共有された記憶、プロジェクト指示、添付資料などが自動で入る環境があります。新しいチャットに何が引き継がれるか設定を確認し、必要な指示や資料が実際に読めたか確かめます。

## 使うときの手順

### 1. 作業内容と共通の条件を一か所に置く

例えば、設定を保存して再起動すると値が消える不具合を直すなら、`docs/tasks/settings-save/task.md` に目的、守る仕様、完了条件と参照先を短く保存します。既にIssueにまとまっていれば、そのIssueを使えます。[作業メモのひな型](../../../templates/CONTEXT_PACK.md)も使えます。

```markdown
# 設定保存の修正
- 目的: 保存した値を再起動後も保つ
- 守る条件: 既存の設定ファイルの形式を変えない
- 対象候補: 設定の保存・起動時の読込処理と対応テスト
- 完了条件: 再現例と関連テストで保存・再読込を確認する
- 参照先: Issueの再現手順、設定形式の仕様、関係するコードとテスト
```

これは架空の例です。参照先は実際のパス・見出し・Issue番号へ置き換え、未確定の対象や条件は推測で埋めないでください。仕様の全文や長い履歴をメモへコピーせず、仕様書やコードなど、事実を確認できる場所へ案内します。

### 2. 各チャットで担当と作業範囲を伝える

次は同じ修正を、実装、コメント、レビューの順で進める例です。三つすべてに分ける必要はありません。コメントの変更が小さければ実装と一緒に頼めます。

**実装を頼むチャット**

```text
あなたは設定保存の実装担当です。
docs/tasks/settings-save/task.md を読み、対象の実装とテストを確認してください。
保存・読込処理と対応テストを変更できます。公開する保存形式は変えないでください。
関係する別の変更が必要なら、理由と対象を先に報告してください。
指定された完了条件を確認し、変更箇所・実行した確認と結果・未確認を返してください。
引継ぎを docs/tasks/settings-save/handoff.md へ残してください。
```

**実装が終わった後、コメントを頼むチャット**

```text
あなたはコードコメントの見直し担当です。
task.md と handoff.md を読み、記録された版の変更箇所を確認してください。
対象は今回変えた宣言のコメントです。読み手は、このコードを保守する開発者です。
プロジェクトのコメント規則を読み、実装と使う側を確認してから、
コードだけでは分からない理由・使う条件・制約を必要な箇所へ書いてください。
コメントだけを変更し、動作の修正が必要なら編集せず報告してください。
変更箇所と根拠、確認結果、未確認を handoff.md へ追記してください。
```

ここでの `task.md` と `handoff.md` は、どちらも `docs/tasks/settings-save/` 内です。コメントの具体的な確認観点は[読む人に役立つコメントの書き方](../手法/AIに読む人の役に立つコードコメントを書かせる.md)でも説明しています。

**その後、レビューを頼む新しいチャット**

```text
あなたはコードレビュー担当です。ファイルは編集しないでください。
docs/tasks/settings-save/task.md と handoff.md を読み、
対象の版と差分の比較元を確認してください。
仕様、変更差分、関係するコード・テストから、保存形式の互換性、
保存失敗時の状態、再起動後の読込、コメントと実装の一致を確認してください。
実装担当の「確認済み」という結論だけを根拠にせず、必要な元資料を読んでください。
指摘は重要度・場所・発生条件・影響・根拠・修正案で返してください。
読んだ範囲、実行した確認と結果、未確認を示してください。
指摘がない場合も、確認した範囲で見つからなかったと報告してください。
```

役割の指示は、ファイルの編集権限を制限する仕組みではありません。利用する環境に読取り専用の設定があれば、レビュー時に使えます。検査の実行でファイルが生成・変更される場合もあるため、実行する操作の範囲も決めます。

### 3. 次のチャットには、短い引継ぎと必要な元資料を渡す

`docs/tasks/settings-save/handoff.md` には、次の項目を残させます。次は空欄のひな型で、確認済みの結果ではありません。

```markdown
# 設定保存の引継ぎ
- 作業の目的と条件: task.md
- 対象の版: コミット番号、または未コミット差分を保存したファイル
- 差分の比較元: コミット番号など
- 今回使う決定と理由: 決定した内容と、その根拠の場所
- 変更箇所: パス・関数名・何を変えたか
- 確認結果: 対象の版・コマンドや操作・結果・ログの場所
- 未解決・未確認: 何が不明か、次に何を確かめるか
- 次に頼む作業と、変更してよい範囲:
```

コメントやコードが変わったら、対象の版も更新してください。前の版で通った検査を、最新の版で通ったことにしません。未コミット変更を含めるなら、その差分も次のチャットに渡します。

新しいチャットには、作業メモ、引継ぎ、対象の差分と、確認に必要な仕様やコードを渡します。ファイルを読めるAIには場所を指定し、読めないチャットには添付・貼り付けます。リンクを開けない場合も、必要な本文を渡してください。長い会話全文の代わりに短い入口を渡し、不足した事実だけ追加します。

繰り返す役割の指示は、例えば `docs/ai/roles.md` に保存できます。AIが読む入口の指示書から「レビューを依頼されたときだけ `docs/ai/roles.md` のレビュー節を読む」と参照させます。実際にその入口が読まれるか確認し、自動で読まれなければ依頼へパスか本文を添えます。対象の版や今回の作業内容まで、恒久的な役割設定へ継ぎ足さないでください。

### 4. あなたが結果と引継ぎを照合する

- 指定した変更範囲と実際の差分が合っているか見ます。
- レビューの指摘を、記載された版のコード、仕様、検査結果と照合します。
- 実行できなかった検査や、読めなかった資料を未確認として残します。
- 指摘を直した場合は、変更した版について必要な再確認を頼みます。

チャットを分けても、同じモデルが同じ誤りを繰り返したり、引継ぎの誤りを受け入れたりする場合があります。別チャットの同意だけを完成の証拠にせず、完了条件に対応する差分と確認結果で判断してください。

## 何が減り、何が増えるか

実装の試行錯誤を全部レビューへ渡さずに済めば、レビューと無関係な会話をその入力から外せます。短い引継ぎがあれば、次の担当に同じ条件を説明し直すやり取りも減らせます。役割名を付けるだけでは、入力は減りません。

一方、複数のチャットで同じ仕様を読むことや、引継ぎの作成・確認で使用量が増えることもあります。記憶の抜けやレビュー漏れがなくなる保証もありません。利用量を測れる場合は、[作業ごとの使用量の記録方法](作業ごとのコンテキスト使用量の目安を作る.md)に沿って、全チャットの入力・出力・やり直しを含む合計と、必要な確認が保たれたかを比べてください。

## 役割の効果を調べた研究

[Zhengほか（2024）](https://aclanthology.org/2024.findings-emnlp.888/)は、MMLUから選んだ2,410問の事実質問と162の人物像などを用いて評価し、役割を加えるだけでは、役割なしに比べ全体の正答性能が改善しなかったと報告しています。[1]

[Luz de Araujoほか（2025）](https://aclanthology.org/2025.emnlp-main.1364/)は、9モデル・27課題で専門家の役割などを評価し、専門家指定には改善または有意差なしが多い一方、無関係な人物設定にも性能が左右されたと報告しています。[2]

これらは本書のチャット分けや依頼文を検証した結果ではありません。役割の効果は課題やモデルで変わるため、「熟練者」と名乗らせるだけで品質が上がるとは考えず、対象・観点・根拠を具体化して結果を確認します。

## 補助ツール・機能

- **新しいチャットを作る機能:** 作業別に会話を始められます。あなたが必要な引継ぎを渡す方法から試せます。記憶や資料の引継ぎ範囲は設定を確認してください。
- **役割の指示を保存する機能:** 繰り返す担当と確認観点を再利用できます。今回の対象や版は依頼時に渡し、役割設定を長い作業履歴にしません。
- **別のAIエージェントへ依頼する機能:** 対応した環境では、調査やレビューを別の会話で実行し、結果を受け取れます。必要な資料が渡るか、編集権限、返答をまとめる担当を確認して使えます。単にチャットを手動で分ける場合とは、起動や受渡しの操作が違います。

## この手法について

役割を最初に伝えて、目的・対象・返す結果を指定する進め方は、**役割を指定した指示（role prompting）**と呼ばれます。人物像まで設定する方法は、参考論文では**persona prompting**として扱われています。

複数のAIに別々の担当を与え、結果を受け渡す構成は、**複数エージェントによる協調（multi-agent collaboration）**と呼ばれます。[ChatDevの論文](https://aclanthology.org/2024.acl-long.810/)では、設計・実装・テストなどの段階を役割のあるエージェントの対話でつなぐ構成を紹介しています。[3] このような仕組みの導入や同時実行は、手動でチャットを分けるための前提ではありません。
