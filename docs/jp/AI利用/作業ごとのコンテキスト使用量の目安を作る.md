# 作業ごとのコンテキスト使用量の目安を作る

短い質問、一つのファイルの修正、プロジェクト全体の調査では、AIに渡す資料ややり取りの回数が違います。「コード修正なら何トークン」と一つの値で見積もるより、読む範囲と作業の進め方が似た実績から目安を作る方が、自分の環境で判断しやすくなります。

ここでは、**一回に渡す入力**と**作業全体で繰り返し使う量**を分けます。公開された数値は測定条件付きの例として使い、短い質問や一ファイル修正の一般的な平均値として転用しません。

## 作業の種類ごとに、増える要因を見る

| 作業 | 最初に用意する情報 | 使用量が増える主な要因 | 作業を頼むときの工夫 |
| --- | --- | --- | --- |
| 短い質問 | 質問、前提、必要な短い例 | 長い会話履歴を引き継ぐ、全文の資料を付ける | 今回必要な前提だけ添える |
| 一ファイルの変更 | 対象の処理、仕様、使う側、関連テスト | 大きなファイルを全文読む、テスト失敗と修正を繰り返す | 関数などの範囲から始め、不足した依存先を追加する |
| 複数ファイルにまたがる変更 | 受け渡す形式、呼び出し元と先、影響するテスト | 同じ資料の再読、変更漏れ、長い差分 | 共有する仕様を一か所で示し、変更する単位を分ける |
| プロジェクト全体の調査 | 調査基準、対象一覧、確認済み範囲 | 多数のファイル、全件ログ、似た候補の比較 | フォルダーや機能ごとに結果と未確認を記録する |

ファイル数だけで使用量の順番は決まりません。一ファイルの難しい不具合で何度も検査する作業が、数ファイルの単純な修正より多く使う場合があります。検索プログラムが調べたファイル数と、AIへ本文を渡したファイル数も別です。

## 何の量を数えるか決める

トークンは、AIが文章やコードを処理するときの小さな単位です。区切り方はモデルによって違うため、文字数と同じではありません。

| 記録する量 | 意味 | 何の判断に使うか |
| --- | --- | --- |
| 各呼び出しの入力トークン | その回でAIへ渡された指示・履歴・コード・ツール結果などの量 | 一回の入力が大きくなっていないか |
| 各呼び出しの出力トークン | その回でAIが生成した量 | 長いコード案や報告がどれだけ増えたか |
| 作業全体の入力・出力の合計 | 各呼び出しの測定値を足した量。同じ履歴の再送も、その都度含む | 調査、実装、確認、やり直しを含む累積使用量 |
| 一回の入力の最大値 | 作業中に記録した入力の最も大きい値 | 一度に扱う入力の目安。出力用の余地や他の上限は別に確認する |

例えば次は**数え方を説明する仮の値で、実測結果ではありません**。

| 呼び出し | 入力 | 出力 |
| --- | ---: | ---: |
| 1回目 | 2,000 | 1,000 |
| 2回目 | 3,500 | 500 |
| 作業全体 | 5,500 | 1,500 |

作業全体の入力と出力を足すと7,000トークンですが、記録した一回の入力の最大は3,500です。累積7,000を「同時に7,000入っている」とは扱いません。2回目に前の入力・回答が含まれる場合、その履歴は累積入力で再び数えられます。

入力の再利用を記録するキャッシュの値が、入力合計の内訳なのか別枠なのかは、測定元の定義を確認してください。生成途中の推論に使われた値も、出力の内訳なら重ねて足しません。定義が分からない内訳は残し、合計を推測しないでください。使用量、料金、アプリの残り利用枠は同じ数値ではありません。

## 条件付きの数値例を読む

### 固定した小さなプロジェクトで、読む本文を測った例

このリポジトリの[実測ベンチマーク](../コンテキスト削減の実測ベンチマーク.md)は、五つの機能、実装・テスト・説明の計15ファイルから、三つの調査に必要な本文を選んでいます。実際のAIの応答は生成せず、選ばれたファイル本文の文字数を数えた結果です。

| 調査 | 検索後に読む本文の文字数 | ファイル数 |
| --- | ---: | ---: |
| 不正な設定ファイルのエラー表示の調査 | 1,328 | 3 |
| 表示名の空白除去の調査 | 1,032 | 3 |
| 通知失敗の再試行条件の調査 | 1,183 | 3 |

三件をまとめると、中央値1,183文字、平均1,181文字、最小1,032～最大1,328文字です。中央値は、値を小さい順に並べた中央の値です。これは**三つの小さな固定ケースの文字数**であり、一ファイル修正の平均トークン数や作業全体の量ではありません。依頼、履歴、出力、再試行も含みません。

数値は[固定版の基準結果](https://github.com/tomiya7688/ai-context-reducer/blob/4621d09c9d6a5b4131f6d6b9e46c29fc321730c2/benchmarks/context-reduction/reference-results.json)から集計しました。文字数はUTF-8で読んだ本文をPythonの `len()` で数えています。モデルやトークン分割器は使っておらず、実測トークン数の欄はありません。

### 自動で調査と修正を進めるAIの、公開研究の例

[Baiほかの論文 v3](https://arxiv.org/abs/2604.22750v3)の図1は、自動でコード修正を進める作業の入力・出力合計の平均を約417万トークンと報告しています。[1] 一回の入力の大きさではなく、履歴を再送する複数回の累積です。

条件はOpenHands、SWE-bench Verifiedの500課題、8モデル、課題ごと4実行で、履歴を次の回へそのまま引き継ぎます。モデルはClaude Sonnet 3.7 / 4 / 4.5、GPT-5 / 5.2、Qwen3-Coder-480B-A35B-Instruct、Kimi-K2、Gemini-3-Proです。測定は実行記録のusage情報に基づきます（第2節）。この平均に対応する中央値は掲載値から補いません。

これを「普段のコード修正には417万必要」とは使いません。対象課題、履歴の持ち越し方、モデル、実行のばらつきが違えば、自分の環境の目安も変わります。論文のモデル名は測定条件であり、利用するAIの推奨ではありません。

## 自分の環境で目安を作る手順

### 1. 作業の分類と、測定条件を保存する

例えば `docs/usage/measurement-method.md` に、次を短く保存してください。

```markdown
# 使用量の測定条件

- 作業の分類: 短い質問 / 一ファイル変更 / 複数ファイル変更 / 全体調査
- 開始と終了: 依頼から、必要な確認と完了報告まで
- AI・モデル・版・設定・測定日:
- 履歴の引継ぎ、要約、再読の扱い:
- 入力・出力を取得する画面やログ、その項目の定義:
- キャッシュや推論の値を合計へ含める方法:
- 別のAIや別チャットの確認を集計へ含める範囲:
- 実測 / 概算 / 文字数だけ、のどれか:
```

同じ作業名でも、エディターで見ている範囲だけを直すAIと、プロジェクトを検索して検査も実行するAIは分けて記録します。設定や測定方法が変わったら、前の結果と混ぜないでください。

### 2. 呼び出しごとの入力・出力と、作業結果を残す

取得できるログから、例えば `docs/usage/requests.csv` に記録します。次は列名だけのひな型です。

```csv
task_id,task_kind,request_id,input_tokens,output_tokens,measurement_kind,source_log
```

一行は一つの呼び出しです。数値が取れなければ空欄にして、0と扱いません。取得できる文字数だけなら別の列やファイルへ記録し、トークン数に見せかけません。

`docs/usage/task-results.md` に、作業ごとの入力合計、出力合計、呼び出し回数、一回の入力の最大、対象ファイル・検査・完了または未完了の結果を残します。途中でやめた作業、失敗後の再実行、別チャットでの確認も、それぞれの識別番号と集計範囲を示します。同じ呼び出しの記録が二つのログにある場合は一度だけ数えます。

一部の呼び出しを取得できなかった場合は「取得できた分の合計」と書き、作業全体の実測値として集計しません。画面に表示された残り枠の割合から、トークン数を逆算しないでください。

### 3. 同じ条件の作業をまとめ、中央値と幅を見る

まず普段の似た作業を数件記録します。件数、完了と未完了の件数、入力・出力の合計の定義を付けて、小さい順に並べた中央の値と最小・最大を示してください。件数が偶数なら、中央の二値の平均を中央値にします。

例えば、同じ条件の完了した五件が1,600、2,000、2,600、3,200、18,000トークンなら、中央値2,600、平均5,480、最小1,600～最大18,000です。**この数列は集計方法を説明する仮の例で、使用量の実測値ではありません。** 一件の大きな値で平均が変わることを示しています。

数件の最小・最大は将来の下限・上限ではありません。成功例だけを見て再試行や失敗分を隠さず、未完了は別の区分で示します。文字数だけの記録と実測トークン数、異なるモデルや進め方を一つの平均へ混ぜないでください。

### 4. 次の作業の進め方を決める

- 一回の入力が大きいなら、検索で関係する箇所を選ぶか、長い資料を意味のまとまりで分けます。判断に必要な仕様やテストは残してください。
- 一回の入力は小さくても累積が増えるなら、同じファイルの再読、長い検査ログ、修正のやり直しが続いていないか確認します。
- 複数の機能が独立して変更・確認できるなら、作業を分ける目安になります。共有する仕様と引継ぎも数えるため、分ければ必ず減るとはしません。
- 追加調査で判断に必要な事実が得られたなら、決めた完了条件へ進みます。不足した根拠があるなら、使用量だけを理由に必要な確認を止めません。

例えば設定読み込みと画面表示を別々に変更できる作業なら、仕様を共有しながら単位を分けられます。一つの不具合の原因を絞っている途中なら、別チャットへ移す前に確認済みの根拠と未解決点を残してください。

## AIへの依頼例

```text
今回の作業は、一ファイルの変更です。
docs/usage/measurement-method.md の条件で使用量を記録してください。
取得できる呼び出しごとの入力・出力を docs/usage/requests.csv へ残し、
完了時に docs/usage/task-results.md へ合計、回数、入力の最大、作業結果を追記してください。

測定値の出典を示し、取得できない値は未計測にしてください。
キャッシュや推論などの内訳を重ねて足さず、同じ呼び出しを重複集計しないでください。
再試行と別の確認に使った分も、集計した範囲を示してください。
同じ条件の過去の作業だけから、件数、中央値、最小・最大をまとめてください。
例の数値や文字数から、実測トークン数を作らないでください。
使用量を減らすために、必要な根拠や検査を省かないでください。
```

AIがログや使用量表示を読めない場合は、あなたが取得した値と項目の定義を渡します。記録ファイルを読めないチャットには本文を添付・貼り付けてください。AIに「何トークン使ったか」を想像で答えさせません。繰り返すなら、AIの入口の指示書へ「使用量を記録する作業では `docs/usage/measurement-method.md` を読む」と参照を置けます。

## ベンチマークとの使い分け

[実測ベンチマーク](../コンテキスト削減の実測ベンチマーク.md)は、同じ作業で情報を絞る前後を比べます。この文書の目安は、同じ環境の作業を種類別に記録して、次に読む量や作業の分け方を考えるためのものです。

目安から資料を絞ると、無関係な入力や繰り返す調査を減らせる場合があります。一方、記録や引継ぎも入力を増やします。必要な根拠と完了条件を保ったうえで、作業全体の量を比較してください。

## 補助ツール

- **利用しているサービスや実行環境の使用量表示・ログ:** 実測の入力・出力を取得できる場合があります。項目の定義と、どこまでの呼び出しが含まれるかを確認して使います。
- **モデルに対応したトークン分割器:** 渡すテキストが何トークンに分かれるかを数えます。渡す前の見積もりに使えますが、非表示の指示、履歴、出力まで含む実行量とは限りません。
- **表計算や短い集計スクリプト:** 記録した行を作業ごとにまとめ、合計・中央値・最小・最大を計算します。集計対象と欠測を確認して使います。

## この見方について

過去の測定から次の作業の量を考えることは、**実測に基づく見積もり**です。一度に処理できる情報の上限は**コンテキストウィンドウ**、文字列をモデルの単位へ分ける処理は**トークン化**と呼びます。作業全体の累積量と一度の上限を分けて扱ってください。

参考論文は特定のコード修正環境を分析した研究です。本書の記録方法や分類が一般的な平均値を保証するという意味ではありません。
