# コンテキスト削減の実測ベンチマーク

この文書は、「必要なファイルを先に絞ると、AIへ渡す情報量をどれくらい減らせるか」を再現可能な条件で測る方法を説明します。

ここで示す数値は、実際の大規模プロジェクト全般へそのまま当てはめる削減率ではありません。固定した合成リポジトリと三つの作業で、**広く読む方法**と**検索で候補を絞ってから読む方法**を同じ条件で比べた結果です。

## 何を比べるか

ベンチマークは `benchmarks/context-reduction/` にあります。固定fixtureには、設定、プロフィール、通知、レポート、キャッシュという五つの独立した機能を置いています。各機能には実装、テスト、説明文が一つずつあり、測定対象は合計15ファイルです。

三つの作業について、次の二つの方法を比べます。

### 広く読む方法

`baseline` は、作業場所をまだ絞れていない状態として、fixture内の `.py` と `.md` をすべてAIの入力候補にします。

この方法は「一般的な開発者は必ず全ファイルを読む」という主張ではありません。検索前に広い範囲をAIへ渡す場合と、検索で候補を絞る場合の差を測るための固定基準です。

### 検索してから読む方法

`context_reduced` は、同じ15ファイルを機械的な文字列検索で走査します。検索に一致したファイルだけをAIへ渡す対象にします。

検索プログラムが15ファイルを走査しても、その全文をAIのコンテキストへ入れたとは数えません。ベンチマークは、**機械が調べた量**と**AIへ渡した量**を分けて記録します。

## 同じ作業と必要な根拠を使う

三つの作業は `benchmarks/context-reduction/tasks.json` に固定しています。

| 作業 | 必要な根拠 |
| --- | --- |
| 壊れた `settings.json` のエラーへファイルパスを加えるための調査 | `src/settings.py`、`tests/test_settings.py`、`docs/settings.md` |
| `display_name` の空白除去を確認するための調査 | `src/profile.py`、`tests/test_profile.py`、`docs/profile.md` |
| 一時的な通知失敗だけを再試行する変更のための調査 | `src/notifier.py`、`tests/test_notifier.py`、`docs/notifier.md` |

両方の方法で、必要な根拠が全部含まれているかを同じ一覧で確認します。入力が減っても必要な根拠が欠けた場合は成功と扱いません。

このfixtureでは、三つの作業すべてで `baseline` と `context_reduced` の両方が必要な根拠をすべて含みます。

## 固定fixtureで得られた結果

現在の `reference-results.json` では、次の結果になります。

| 作業 | 広く読む | 検索後に読む | ファイル数削減 | 文字数削減 |
| --- | ---: | ---: | ---: | ---: |
| settings | 15ファイル / 4,826文字 | 3ファイル / 1,328文字 | 80.0% | 72.5% |
| profile | 15ファイル / 4,826文字 | 3ファイル / 1,032文字 | 80.0% | 78.6% |
| notification | 15ファイル / 4,826文字 | 3ファイル / 1,183文字 | 80.0% | 75.5% |
| 3作業合計 | 45ファイル / 14,478文字 | 9ファイル / 3,543文字 | 80.0% | 75.5% |

三つの作業では、検索後にAIへ渡すファイル数が45件から9件へ減り、AIへ渡す文字数は14,478文字から3,543文字へ減りました。必要な根拠は両方の方法で欠落していません。

この **75.5%** は、このfixtureと三つの作業だけの実測値です。「ai-context-reducerを使えば、どのプロジェクトでも75.5%減る」という意味ではありません。

## token数を実測値として載せない理由

コミット済みの基準結果では、token数を測っていません。

token分割はモデルやtokenizerによって違います。特定のtokenizerを実行していないのに、文字数を一定値で割った数字を「実測token数」として掲載すると、測定していない値を実測したように見せることになります。

`benchmark.py` には `--chars-per-token` を用意しています。これは利用者が明示した比率で概算値を出すための任意機能であり、出力でも `estimated_tokens` として実測token数から区別します。

実際のモデル入力token数を比較できる環境では、そのモデルと同じtokenizerまたは提供サービスのusage情報を使って別途測定してください。

## 再現する

リポジトリのルートで次を実行してください。

```bash
python3 benchmarks/context-reduction/benchmark.py
```

現在コミットされている基準結果とfixtureが一致することだけを確認する場合は、次を実行してください。

```bash
python3 benchmarks/context-reduction/benchmark.py --check-reference
```

成功すると、次の一行を表示して終了コード0で終わります。

```text
context-reduction benchmark reference matches
```

GitHub Actionsの `Context reduction benchmark` も同じ確認を行います。fixture、作業、検索条件、測定方法のどれかを変更して結果が変わった場合は、基準結果を意図せず古いまま残せません。

## 何を測っていて、何を測っていないか

このベンチマークが測るものは次です。

- AIへ渡す対象になったファイル数
- AIへ渡す対象になった文字数
- UTF-8でのbyte数
- 機械検索が走査したファイル数
- AIが読む対象になったファイル数
- 事前に定めた必要根拠が欠けていないか

このベンチマークだけでは、次のことは測れません。

- 特定のLLMが実際に消費したinput token数
- API料金
- 応答時間
- 生成したコードの品質
- 実プロジェクトでの平均的な削減率
- 人間が検索に使う時間

つまり、この結果は「検索してから必要ファイルだけを渡すと、固定fixtureでAI可視の入力がどれだけ減ったか」を測っています。LLMの回答品質そのものを比較した結果ではありません。

## baselineを不自然に悪くしないための注意

この基準では、`baseline` の定義を「fixture内の対象テキストをすべてAIへ渡す」と固定しています。比較のたびにbaselineだけへ不要なダミーファイルを足したり、`context_reduced` にだけ正解ファイル名を非公開情報として与えたりしません。

検索語、必要な根拠、fixtureの全ファイル、測定スクリプト、基準結果はすべてリポジトリへ公開しています。結果を読む人は、どの条件で数字が出たかを確認できます。

## 実プロジェクトで測る場合

実プロジェクトでは、同じ作業と同じ完了条件を使って比較してください。

1. baselineでAIへ渡したファイルや資料を記録します。
2. 検索や索引で候補を絞った場合に、AIへ渡したファイルや資料を記録します。
3. ファイル数、文字量、取得できる場合だけtoken数を比較します。
4. 両方で、必要な仕様、実装、テスト、エラーなどを確認できたかを残します。
5. 必要な検査結果が異なる場合は、入力が少ない方を成功例にしません。
6. 一件の測定結果を一般的な削減率として扱いません。

コンテキストを減らす目的は数字だけを小さくすることではありません。必要な根拠を保ったまま、今回使わない情報をAIへ渡さないことです。

## 作業ごとの使用量を見積もる

作業の種類ごとに目安を作る場合は、[作業ごとのコンテキスト使用量の目安を作る](作業ごとのコンテキスト使用量の目安を作る.md)で、入力・出力・累積量の区別と、測定条件をそろえて記録する手順を確認してください。
