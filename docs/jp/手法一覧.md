# 手法一覧

この一覧は、作業に必要な情報を探す時間と、AIに渡す文書やコードの量を減らす方法をまとめています。手法名から選ぶのではなく、作業中に起きている困りごとから該当する説明を開いてください。

## 例: 設定変更のたびにリポジトリを探し回る

設定ファイルの値を変えるだけなのに、毎回どの説明を読み、どのコードやテストを確認するか探すとします。

作業別の案内表に「設定変更なら、設定の説明、読み込み処理、設定テストを見る」と記録しておけば、次回はその3か所から調査を始められます。案内先で変更の影響が分かった後は、関係のない画面や機能のコードを読む必要がありません。手法が減らすのは、作業に関係のない場所を探して読む量です。案内表が古い場合や、変更の影響が案内の想定を超える場合は、調査範囲を広げてください。

## 手法

### 作業のたびに情報を探し直さない

| 手法 | すること | 読む量が減る理由 |
|---|---|---|
| [現状メモ](現在の状態を短くまとめる.md) | 現在できること、制約、未実装の機能を短く記録する | 現在の状態を知るために、README・Issue・変更履歴を毎回読み比べずに済む |
| [作業用メモ](作業用メモ.md) | 今回の目的、参照資料、変更対象、完了条件を一か所に記録する | 作業のたびに会話やリポジトリから依頼の条件を拾い集めずに済む |
| [参照先の目録](参照先の目録.md) | 原典となる説明・コード・テストの場所を一覧にする | ファイル名を手掛かりに、候補をリポジトリ全体から探し続けずに済む |
| [作業別の案内表](作業別の案内表.md) | 作業の種類ごとに、最初に見る説明・コード・テストを示す | 毎回同じ種類の作業で、確認場所を一から調べずに済む |
| [変更内容ごとの案内表](変更内容ごとの案内表.md) | 設定変更やAPI変更など、変更の種類と確認先を対応させる | 「何を変えたか」から影響しそうな場所をたどれる |
| [既存の設計境界で絞る](既存の設計境界で読む範囲を絞る.md) | 既に定義されている担当範囲や通信経路から調査を始める | 関係する機能の境界を、無関係なコードまで読んで探し直さずに済む |
| [ファイルとモジュールの役割表](ファイルとモジュールの役割表.md) | ファイルやモジュールが担当する内容を記録する | ファイル名だけでは分からない担当範囲を、ソースを開いて推測せずに済む |
| [場所ごとの指示](場所ごとの指示.md) | その場所だけに必要な作業ルールを、近くに置く | 作業場所に関係しない細かな指示まで毎回読む必要がなくなる |
| [リモートとの差分を先に確認する](リモートとの差分を先に確認する.md) | 前回確認した状態からリモートで変わった箇所を先に見る | 変化のないファイルを最初から読み直す作業を減らせる |

### 大きな資料から必要な部分だけ取り出す

| 手法 | すること | 読む量が減る理由 |
|---|---|---|
| [読む候補の優先度を付ける](読む候補の優先度を付ける.md) | 作業との関連性で候補を選び、大きなファイルは必要に応じて範囲を細かくする | 大きいという理由だけで無関係なファイルを読まず、関係するファイルも必要な箇所から確認できる |
| [通常は読まないものを決める](通常は読まないものを決める.md) | 生成物、ログ、外部ライブラリ、キャッシュなどを通常の調査対象から外す | 作業で使わない派生ファイルや外部コードが、最初の資料に混ざらない |
| [コード構造の索引](コード構造の索引.md) | 関数・型・読み込み先などを検索できる形で調べる | 大きなソースを先頭から読む代わりに、関係する定義や呼び出し元を確認できる |

### 調べ終える時点と確認範囲を決める

| 手法 | すること | 読む量が減る理由 |
|---|---|---|
| [探索を止める条件を決める](探索を止める条件を決める.md) | 判断に必要な情報が揃った状態を、作業前に決める | 必要な根拠を確認した後の「念のため」の検索や再読を止められる |
| [確認する根拠の量を決める](確認する根拠の量を決める.md) | 作業の判断に必要な資料や証拠を先に挙げる | 既に答えが出ている点について、別の資料を集め続けずに済む |
| [変更内容に応じて検証を選ぶ](変更内容に応じて検証を選ぶ.md) | 変更の種類に応じて、必要なテストや確認を選ぶ | 変更と関係のない検証手順やテストの説明を調べずに済む |
| [変更の影響範囲から検証対象を絞る](変更の影響範囲から検証対象を絞る.md) | 変更したファイルや依存関係から、関係するテスト候補を探す | テスト全体の一覧を読み、無関係なテストまで候補にする必要がなくなる |
| [構文チェックを軽い検証に使う](構文チェックを軽い検証に使う.md) | 使える構文解析器があれば、テスト前に構文上の誤りを確認する | 成功した大量の解析結果を読む代わりに、エラー箇所を確認できる。構文が正しいことだけでは動作確認にならない |

### 繰り返す説明や判定をまとめる

| 手法 | すること | 読む量が減る理由 |
|---|---|---|
| [規則の確認先を絞る](規則の確認先を絞る.md) | 機械で判定できる規則と、人が意味を判断する規則を分ける | 全規則の説明を読む代わりに、機械の判定結果と必要な規則だけ確認できる |
| [文書の重複を管理する](文書の重複を管理する.md) | 詳細を一つの原典に置き、他の文書からそこへ案内する | 同じ説明が複数箇所にある場合の読み比べや、食い違いの確認を減らせる |
| [定型文と定型ファイルを生成する](定型文と定型ファイルを生成する.md) | ライセンス表記などの定型内容を、決めた元データから生成する | 過去の例や書き方を読み直して、同じ形式の文章を作る作業を省ける |

## 困りごとから選ぶ

- 毎回どこを見ればよいか分からない: [作業別の案内表](作業別の案内表.md)、[変更内容ごとの案内表](変更内容ごとの案内表.md)
- 大きなソースのどこが関係するか分からない: [読む候補の優先度を付ける](読む候補の優先度を付ける.md)、[コード構造の索引](コード構造の索引.md)
- 十分な根拠があっても調査を続けてしまう: [探索を止める条件を決める](探索を止める条件を決める.md)、[確認する根拠の量を決める](確認する根拠の量を決める.md)
- 変更のたびにテストを一から探す: [変更内容に応じて検証を選ぶ](変更内容に応じて検証を選ぶ.md)、[変更の影響範囲から検証対象を絞る](変更の影響範囲から検証対象を絞る.md)
- 長い規則や同じ説明を毎回読む: [場所ごとの指示](場所ごとの指示.md)、[規則の確認先を絞る](規則の確認先を絞る.md)、[文書の重複を管理する](文書の重複を管理する.md)

どれから導入するかは[導入優先度](導入優先度.md)を参照してください。コマンドや設定例は各手法の説明に分けてあります。
