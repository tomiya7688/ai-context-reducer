# 手法一覧

この一覧は、プロジェクトで同じ調査を繰り返さないための方法を選ぶ入口です。利用者が困りごとに合う案内・一覧・検査を用意し、作業を頼むときにAIへその場所と使い方を伝えます。AIが自動で文書を読むとは限りません。継続して使う場合は、利用中のAIが読む指示ファイルや設定へ登録されているか確認します。

「複数ファイルの出力が後半だけ粗くなる」「どのモデルや編集方法を選べばよいか」など、具体的な質問から短い依頼例を探す場合は[AI利用でよくある質問](AI利用/よくある質問.md)を先に見てください。

## 困りごとから読むページを選ぶ

今の困りごとに近い行から、リンク先の説明を一つ読んでください。表の全項目を順に読む必要はありません。

- 毎回どこを見ればよいか分からない: [作業別の案内表](作業別の案内表.md)、[変更内容から確認先を選ぶ](変更内容から確認先を選ぶ.md)
- 何を変えるか、どこまでできれば完成かが曖昧: [設計と完了条件を先に決める](設計と完了条件を先に決める.md)
- 大きなソースのどこが関係するか分からない: [変更に必要なファイルから読む](変更に必要なファイルから読む.md)、[コード構造の索引](コード構造の索引.md)
- どの深さの解析や検査が必要か分からない: [言語に合った解析方法を選ぶ](言語に合った解析方法を選ぶ.md)
- 十分な根拠があっても調査を続けてしまう: [調査を止める条件を決める](調査を止める条件を決める.md)、[必要な確認を先に決める](必要な確認を先に決める.md)
- 変更のたびにテストを一から探す: [変更に合わせて確認方法を選ぶ](変更に合わせて確認方法を選ぶ.md)、[変更の影響から検証範囲を選ぶ](変更の影響から検証範囲を選ぶ.md)
- 長い規則や同じ説明を毎回読む: [場所ごとに作業ルールを分ける](場所ごとに作業ルールを分ける.md)、[今回の変更に関係する規則を確認する](今回の変更に関係する規則を確認する.md)、[文書の同じ説明を一か所にまとめる](文書の同じ説明を一か所にまとめる.md)
- AIの説明に「誰が何をするか」「どうすればよいか」を何度も聞き返している: [読者が理解できる説明に直す](手法/読者が理解できる説明に直す.md)。[修正例と聞き返しの比較手順](手法/読者が理解できる説明に直す.md#修正前後で聞き返しが減ったか確かめる)で、説明を長くしただけになっていないか確認できます。

- 仕様や実装を決めた理由をAIが調べ直している: [仕様や実装を決めた理由をAIに渡す](手法/仕様や実装を決めた理由をAIに渡す.md)

- いくつかの設計案から、今のプロジェクトに合うものを選びたい: [提示された設計案をプロジェクトの根拠で比較する](手法/提示された設計案をプロジェクトの根拠で比較する.md) — 候補を同じ基準で比べ、仕様・コード・設定・テストの根拠から推薦させます。

- 文章の見出しや順番が毎回変わる: [AIに文章の見出しと順番を渡して書かせる](手法/AIに文章の見出しと順番を渡して書かせる.md) — 短い構成を保存し、各項目に必要な内容と事実の資料をAIへ渡します。

- コードの命名や再利用の決まりを何度も指摘している: [AIにコードの決まりを読ませ、変更後に確かめさせる](手法/AIにコードの決まりを読ませ、変更後に確かめさせる.md) — 既存の規則と検査を使い、変更後の差分まで点検させます。

- コードのコメントを付けても使い方や理由が伝わらない: [AIに読む人の役に立つコードコメントを書かせる](手法/AIに読む人の役に立つコードコメントを書かせる.md) — 規則と読者を渡し、必要な説明を差分と根拠で点検させます。

- 同じ仕事をする関数・クラス・変数が増える: [AIに既存コードを調べさせ、似た役割の追加を防ぐ](手法/AIに既存コードを調べさせ、似た役割の追加を防ぐ.md) — 定義・使う側・テストから、再利用・拡張・新設を判断させます。

- 一か所で指摘した問題が他にも残っている: [一つの指摘から、同じ問題をAIに探させる](手法/一つの指摘から、同じ問題をAIに探させる.md) — 確認基準と範囲を決め、候補と根拠を点検してから修正させます。

- 作業ごとの使用量や分け方の目安が欲しい: [作業ごとのコンテキスト使用量の目安を作る](AI利用/作業ごとのコンテキスト使用量の目安を作る.md) — 一回の入力と累積量を分け、測定条件をそろえて中央値と幅を記録します。

- 使用量が増える原因を調べて改善したい: [AIの作業履歴から無駄な読み込みを見つけて改善する](手法/AIの作業履歴から無駄な読み込みを見つけて改善する.md) — 繰り返し渡した情報と再試行を記録から調べ、一変更ずつ品質・使用量・手戻りを比較します。

- 実装やレビューの会話が混ざり、同じ前提を伝え直している: [作業ごとにAIの役割とチャットを分ける](AI利用/作業ごとにAIの役割とチャットを分ける.md) — 担当と変更範囲を指定し、必要な資料・差分・確認結果を短く引き継ぎます。

- 同じ作業手順を毎回説明し直している: [課題一覧から一件ずつAIに進めさせる](手法/課題一覧から一件ずつAIに進めさせる.md) — 一覧・優先順・一回の範囲・停止条件を先に渡し、「次」で着手できる一件を頼みます。

- 複数のAIが同じファイルを変更し、結果をまとめにくい: [複数のAIに担当と編集範囲を分けて頼む](手法/複数のAIに担当と編集範囲を分けて頼む.md) — 独立した作業に担当と作業場所を割り当て、共有ファイルは一つの担当で編集し、まとめ役が統合後に確認します。

- 必要なファイルやログが、一度に読める量を超える: [長いファイルやログを区切ってAIに渡す](手法/長いファイルやログを区切ってAIに渡す.md) — 対象の版と確認範囲を記録し、区切りごとの結果を元の根拠で照合します。

- Webページの大量の文章や表から、今回の質問に必要なところだけ読みたい: [Webページから必要な情報だけをAIに渡す](手法/Webページから必要な情報だけをAIに渡す.md) — 目的に沿って要素を選び、URL・取得時点・未取得範囲を残して原典を確認します。

- READMEから使い始め方や、AIに渡す資料を選べない: [人とAIが必要な情報へ進めるREADMEを書く](手法/人とAIが必要な情報へ進めるREADMEを書く.md) — 目的別の入口、実在する参照先、AIへの読ませ方を短くまとめます。

### 初めてのコード変更なら

最初に[変更に必要なファイルから読む](変更に必要なファイルから読む.md)を読み、今回変える動作・仕様・テストの候補を確認します。変更の種類や影響範囲に迷ったときは、このページから必要な案内を追加で選んでください。

### 自分のプロジェクトに取り入れるなら

[導入優先度](導入優先度.md)を読み、繰り返し起きている問題に合う方法を選びます。

## 例: 設定変更のたびにリポジトリを探し回る

設定ファイルの値を変えるだけなのに、毎回どの説明を読み、どのコードやテストを確認するか探すとします。

作業別の案内表に「設定変更なら、設定の説明、読み込み処理、設定テストを見る」と記録します。次の依頼ではAIに表の場所を伝え、その3か所を候補にさせ、実際のコードとテストを確認させます。こうするとAIへリポジトリ全体を渡して入口を探させずに済みます。案内が古い場合や影響が想定を超えた場合は、利用者が範囲を広げます。

## 選んだ方法をAIに使わせ、効果を確かめる

単発の作業では、依頼文に「どの案内を使うか」「最初に何を返すか」「どこまで確認するか」を書きます。繰り返す作業では、その案内へのリンクと適用範囲を、AIが実際に読むプロジェクト指示へ置きます。フォルダーごとの自動読込はAIツールの設定次第です。

完了時には、参照したファイル、実行した確認と結果、未確認の範囲を報告させ、表示される作業履歴や差分と照らします。読み込み履歴が見えない環境では、報告だけで実際のコンテキスト量を証明できません。その場合は、案内が正しい原典へ導いたことと、必要なテストを省いていないことを確認します。ツールがトークン数を測れる場合だけ、同じ種類の作業で導入前後を比較します。

依頼には、選んだ案内のパス、今回の作業、AIに最初に返してほしい内容、必要な確認を含めます。たとえば設定変更なら、作業別の案内表のパスを渡し、「表から説明・読み込み処理・テストを候補として挙げ、元ファイルを確認して変更し、対応テストの結果を報告する」と伝えます。案内を添付するかパスを書くことで、AIがどの方法を使うか明確になります。

```text
今回の作業：[作業内容]
「[選んだ手法のページ]」を使ってください。最初に確認候補と選んだ理由を示し、候補の原典を確認して作業してください。
完了条件に必要な確認を実行し、参照先・結果・未確認範囲を報告してください。
```

## 手法

### 作業のたびに情報を探し直さない

| 手法 | すること | 読む量が減る理由 |
|---|---|---|
| [現状メモ](現在の状態を短くまとめる.md) | 現在できること、制約、未実装の機能を短く記録する | 現在の状態を知るために、README・Issue・変更履歴を毎回読み比べずに済む |
| [作業用メモ](作業用メモ（Context%20Pack）.md) | 今回の目的、参照資料、変更対象、完了条件を一か所に記録する | 作業のたびに会話やリポジトリから依頼の条件を拾い集めずに済む |
| [参照先の目録](参照先の目録（Context%20Manifest）.md) | 原典となる説明・コード・テストの場所を一覧にする | ファイル名を手掛かりに、候補をリポジトリ全体から探し続けずに済む |
| [作業別の案内表](作業別の案内表.md) | 作業の種類ごとに、最初に見る説明・コード・テストを示す | 毎回同じ種類の作業で、確認場所を一から調べずに済む |
| [変更内容ごとの案内表](変更内容から確認先を選ぶ.md) | 設定変更やAPI変更など、変更の種類と確認先を対応させる | 「何を変えたか」から影響しそうな場所をたどれる |
| [既存の設計境界で絞る](既存の担当分けから読む場所を決める.md) | 既に定義されている担当範囲や通信経路から調査を始める | 関係する機能の境界を、無関係なコードまで読んで探し直さずに済む |
| [ファイルとモジュールの役割表](ファイルとモジュールの役割表.md) | ファイルやモジュールが担当する内容を記録する | ファイル名だけでは分からない担当範囲を、ソースを開いて推測せずに済む |
| [場所ごとに作業ルールを分ける](場所ごとに作業ルールを分ける.md) | ルートのAGENTS.mdを短く保ち、場所ごとのルールや対応AIのSkillsへ手順を分ける | 共通ルールだけをいつも読み、場所や作業に固有の説明は必要なときに読める |
| [リモートとの差分を先に確認する](リモートとの差分を先に確認する.md) | 前回確認した状態からリモートで変わった箇所を先に見る | 変化のないファイルを最初から読み直す作業を減らせる |

### 大きな資料から必要な部分だけ取り出す

| 手法 | すること | 読む量が減る理由 |
|---|---|---|
| [読む候補の優先度を付ける](変更に必要なファイルから読む.md) | 変更する処理・仕様・テストから読み、外部形式を変えるときは利用側も確認する | 無関係な機能まで探さず、実装と確認に必要な資料から始められる |
| [通常は読まないものを決める](ふだん読まないファイルを決める.md) | 生成物やキャッシュを通常の候補から外す場所と、必要なときに読む例外を案内へ書く | 毎回の依頼で同じ除外先を伝えずに済み、作業に関係するコードやテストを探しやすくなる |
| [コード構造の索引](コード構造の索引.md) | 関数・型・読み込み先などを検索できる形で調べる | 大きなソースを先頭から読む代わりに、関係する定義や呼び出し元を確認できる |
| [言語に合った解析方法を選ぶ](言語に合った解析方法を選ぶ.md) | 場所探し、ファイル間の関係、ビルド・実行確認から必要な深さを選ぶ | 全ソースや全ログをAIに渡さず、候補や必要な診断から関係箇所だけ確認できる |

### 実装前に判断をまとめる

| 手法 | すること | 読む量が減る理由 |
|---|---|---|
| [設計と完了条件を先に決める](設計と完了条件を先に決める.md) | 目的、変更範囲、守る条件、完成の判定方法を実装前に記録する | 後から実装者が過去の会話や広い範囲の資料を読み、設計意図を推測せずに済む |
| [提示された設計案をプロジェクトの根拠で比較する](手法/提示された設計案をプロジェクトの根拠で比較する.md) | 少数の候補を同じ判断基準で、現在の仕様・コード・設定・テストに照らして比べる | 候補を無制限に増やしたり、一般論の長所短所を集めたりせず、判断に必要な原典へ調査を絞れる |

### 調べ終える時点と確認範囲を決める

| 手法 | すること | 読む量が減る理由 |
|---|---|---|
| [探索を止める条件を決める](調査を止める条件を決める.md) | 判断に必要な情報が揃った状態を、作業前に決める | 必要な根拠を確認した後の「念のため」の検索や再読を止められる |
| [確認する根拠の量を決める](必要な確認を先に決める.md) | 作業の判断に必要な資料や証拠を先に挙げる | 既に答えが出ている点について、別の資料を集め続けずに済む |
| [変更内容に応じて検証を選ぶ](変更に合わせて確認方法を選ぶ.md) | 変更の種類に応じて、必要なテストや確認を選ぶ | 変更と関係のない検証手順やテストの説明を調べずに済む |
| [変更の影響範囲から検証対象を絞る](変更の影響から検証範囲を選ぶ.md) | 変更したファイルや依存関係から、関係するテスト候補を探す | テスト全体の一覧を読み、無関係なテストまで候補にする必要がなくなる |
| [構文チェックを軽い検証に使う](構文チェックを最初の確認に使う.md) | 使える構文解析器があれば、テスト前に構文上の誤りを確認する | 成功した大量の解析結果を読む代わりに、エラー箇所を確認できる。構文が正しいことだけでは動作確認にならない |

### 繰り返す説明や判定をまとめる

| 手法 | すること | 読む量が減る理由 |
|---|---|---|
| [規則の確認先を絞る](今回の変更に関係する規則を確認する.md) | 機械で判定できる規則と、人が意味を判断する規則を分ける | 全規則の説明を読む代わりに、機械の判定結果と必要な規則だけ確認できる |
| [文書の重複を管理する](文書の同じ説明を一か所にまとめる.md) | 詳細を一つの原典に置き、他の文書からそこへ案内する | 同じ説明が複数箇所にある場合の読み比べや、食い違いの確認を減らせる |
| [定型文と定型ファイルを生成する](決まった文章やファイルをひな型から作る.md) | ライセンス表記などの定型内容を、決めた元データから生成する | 過去の例や書き方を読み直して、同じ形式の文章を作る作業を省ける |

どれから取り入れるかは[導入優先度](導入優先度.md)を参照してください。各手法は専用ツールなしでも実践できます。検索や定型作業を自動化したい場合だけ、[手法とツールの対応表](手法と補助ツールの対応表.md)から任意の補助ツールを選び、詳しい使い方はそのREADMEで確認してください。これらは「Context Routing」「Context Engineering」などと呼ばれることがありますが、名前を覚えるより、利用者が用意するものとAIへ渡すものを決めるのが先です。
