# 手法一覧

このページは、AIに読ませる量を減らすための手法を、できるだけ簡単な言葉でまとめた目次です。

名前を覚える必要はありません。大事なのは、**何をして、AIに何を読ませなくて済むようにするのか**です。

基本は次の3つだけです。

1. 機械で調べられることは、AIに読ませる前に機械で調べる
2. 毎回同じようにやる作業は、手順やツールにまとめる
3. 必要な部分だけAIに読ませる

## 一覧

| 手法 | 具体的に何をするか | なぜコンテキストが減るか |
|---|---|---|
| [現状メモ](現在の状態を短くまとめる.md) | 今できること、制約、未実装を短い1枚の文書にまとめる | AIが毎回README、Issue、履歴を読み直して現状を調べなくて済む |
| [作業用メモ](作業用メモ.md) | 今回の作業目的、必要な資料、変更対象、完了条件だけを1か所にまとめる | 作業を始めるたびにrepository全体から必要情報を探さなくて済む |
| [参照先の目録](参照先の目録.md) | source・test・docs等の原典を、本文ではなくpointer中心の小さい候補一覧にする | 候補を探すためにrepository全体を広く読み直さなくて済む |
| [読む候補の優先付け](読む候補の優先度を付ける.md) | taskとの関連を最優先にし、sizeやchurn等はrouting粒度を決める補助signalとして使う | 大きいだけの無関係fileを読まず、必要な大fileは全文より先に絞り込める |
| [通常contextから外す](通常は読まないものを決める.md) | generated・logs・vendor・cache・history等をdefaultでは読まず、必要時だけtask-specificに戻す | 毎taskで大量の派生物や補助情報を読まずに済む |
| [作業別の案内表](作業別の案内表.md) | 「この種類の作業なら、この文書・source・testを見る」と決めておく | 関係ないdirectoryや文書を順番に探さなくて済む |
| [探索を止めるルール](探索を止める条件を決める.md) | 必要な情報が揃ったら、それ以上検索しない条件を決める | 「念のため」で追加検索や再読を続けるのを防げる |
| [必要情報のチェック](確認する根拠の量を決める.md) | 作業に必要な根拠を先に決め、足りないものだけ探す | 既に十分な情報があるのに、さらに資料を集め続けなくて済む |
| [変更内容ごとの案内表](変更内容ごとの案内表.md) | 「設定変更ならここ」「API変更ならここ」のように、変更の種類と見る場所を対応付ける | 変更するたびに関連source・test・docsを探し直さなくて済む |
| [既存の設計境界で絞る](既存の設計境界で読む範囲を絞る.md) | projectがすでに持つ責務境界や正式な通信経路から、最初に読む範囲を決める | 無関係なsubsystemまで広く読んで境界を探し直さなくて済む |
| [場所ごとの指示](場所ごとの指示.md) | directoryごとに、その場所でだけ必要なルールを書く | repository全体の細かいルールを毎回全部読ませなくて済む |
| [変更内容ごとの検証選択](変更内容に応じて検証を選ぶ.md) | 変更内容に応じて、必要なtestや確認だけを選ぶ | 毎回すべてのtest手順や検証手順を考え直さなくて済む |
| [構文を安く先に確認する](構文チェックを軽い検証に使う.md) | 利用可能なparserでsyntax healthを先に確認し、その後必要なtest・compiler・runtime検証へ進む | 明白な構文エラーを安く先に見つけ、parse treeや正常fileを大量に読まずに済む |
| [変更に関係するtestだけ選ぶ](変更の影響範囲から検証対象を絞る.md) | 変更したfileや依存関係から、影響するtestを機械的に絞る | 関係ないtestやtest一覧を大量に読む必要がなくなる |
| [fileの役割表](ファイルとモジュールの役割表.md) | 各fileやmoduleが何を担当しているかを短く書いておく | file名だけでは分からない役割を、sourceを開いて確認しなくて済む |
| [ルールの振り分け](規則の確認先を絞る.md) | 自動で判定できる規則と、人が意味を確認する規則を分ける | 長い規約全文を毎回AIに読ませず、必要な規則だけ確認できる |
| [文書の重複を制御する](文書の重複を管理する.md) | 詳細仕様は原典へ寄せ、他文書は必要な短い説明とpointerを持つ | 同じ説明を何度も読ませることと、複数文書の更新driftを減らせる |
| [remoteの差分だけ先に見る](リモートとの差分を先に確認する.md) | 前回からremoteで変わった部分だけ先に確認する | repository全体をもう一度読み直さなくて済む |
| [コード構造の索引](コード構造の索引.md) | 関数、型、import、依存関係などを機械で調べ、検索できる形にしておく | 大きなsourceを最初から最後まで読ませず、必要な関数や関係だけ取り出せる |
| [定型文の自動生成](定型文と定型ファイルを生成する.md) | license、NOTICE、headerなど毎回ほぼ同じ内容を決まった元データから作る | 例文や書き方の説明を毎回AIに渡し、同じ文章を作らせなくて済む |

## もう少し具体的に知りたい場合

### 今回の作業に必要な情報だけ集めたい

- [現状メモ](現在の状態を短くまとめる.md) — projectの現在地を短く確認する。
- [作業用メモ](作業用メモ.md) — 今回の作業に必要な情報だけを1か所に置く。
- [参照先の目録](参照先の目録.md) — 候補となる原典をpointer中心のboundedな一覧にして、そこからworking setを選ぶ。
- [通常contextから外す](通常は読まないものを決める.md) — generated / logs / vendor / cache / history等はdefaultで外し、必要なものだけ戻す。
- [作業別の案内表](作業別の案内表.md) — 作業内容から、最初に見る場所を決める。
- [探索を止めるルール](探索を止める条件を決める.md) — 必要な情報が揃った時点で検索をやめる。
- [必要情報のチェック](確認する根拠の量を決める.md) — 足りない情報だけを探す。

### 変更する場所だけ知りたい

- [変更内容ごとの案内表](変更内容ごとの案内表.md) — 変更の種類からsource・test・docsを絞る。
- [既存の設計境界で絞る](既存の設計境界で読む範囲を絞る.md) — projectに明示済みの責務境界から最初のworking setを絞る。
- [fileの役割表](ファイルとモジュールの役割表.md) — どのfileが何を担当しているかを見る。
- [場所ごとの指示](場所ごとの指示.md) — 今いるdirectoryに必要な指示だけ読む。
- [remoteの差分だけ先に見る](リモートとの差分を先に確認する.md) — 他の人やAIが変えた部分だけ確認する。

### 大きなコードを全部読ませたくない

- [読む候補の優先付け](読む候補の優先度を付ける.md) — task relevanceを最優先にし、大きいfileは必要ならslice / symbol routingへ送る。
- [コード構造の索引](コード構造の索引.md) — 関数・型・依存関係を先に機械で調べ、必要な場所だけ読む。

### 必要な検証だけ行いたい

- [変更内容ごとの検証選択](変更内容に応じて検証を選ぶ.md) — 変更内容から必要な確認方法を選ぶ。
- [構文を安く先に確認する](構文チェックを軽い検証に使う.md) — parserが既に使える場合だけcheap validationとして利用し、syntax成功だけで完了しない。
- [変更に関係するtestだけ選ぶ](変更の影響範囲から検証対象を絞る.md) — 変更に関係するtestだけ実行候補にする。

### 同じ説明や作業を毎回AIにやらせたくない

- [文書の重複を制御する](文書の重複を管理する.md) — 詳細は1つの原典へ寄せ、他文書は短い説明とpointerにする。
- [ルールの振り分け](規則の確認先を絞る.md) — 機械で確認できる規則は機械に任せる。
- [定型文の自動生成](定型文と定型ファイルを生成する.md) — 毎回同じように作る文章やfileを自動生成する。

## どれを使えばよいか

全部を使う必要はありません。

困っていることから選びます。

```text
毎回どこを見るか迷う
  -> 作業別の案内表 / 変更内容ごとの案内表

既存architectureの境界は明確だが、最初の読む範囲が広い
  -> 既存の設計境界で絞る

大きなsourceを毎回読む
  -> コード構造の索引

必要な情報が揃っても検索を続ける
  -> 探索を止めるルール / 必要情報のチェック

毎回全部のtestを確認する
  -> 変更内容ごとの検証選択 / 変更に関係するtestだけ選ぶ

長いルールを毎回読む
  -> 場所ごとの指示 / ルールの振り分け
```

導入するか迷う場合は [`導入優先度`](導入優先度.md) を参照してください。

各toolが実際に何を実行するものかは、v1.1で用意するtool guideにまとめます。
