# 変更の影響から検証範囲を選ぶ

変更したコードと、それを使う箇所を手掛かりに、最初に実行するテストを選ぶ方法です。作業と無関係なテストを毎回すべて調べずに済みます。ただし、対象を狭めるのは必要な確認を省くためではありません。影響が広い変更や、範囲を確かめられない変更では、広いテストへ切り替えます。

## 例：CSVの日付読み込みを修正する

CSVの日付文字列を変換する`src/csv/date_parser.py`を直すとします。このパーサーだけを確かめて終わりにすると、読み込み処理と組み合わせたときの不具合を見逃すかもしれません。変更箇所と既存のテスト対応が分かるなら、まず次を実行します。

```text
変更した場所: src/csv/date_parser.py
最初に実行:   tests/csv/test_date_parser.py
追加で確認:   tests/csv/test_importer.py
```

この変更がCSV形式の共通仕様や公開APIを変えるなら、パーサーの利用側や互換性を確認するテストも加えます。どの機能が利用側か分からない、または依存関係を完全に追えない場合は、CSV機能全体のテストへ広げます。小さなテストだけが通ったことを、より広い影響まで確認できた根拠にはしません。

## テスト候補を見つける

まず、変更したファイル・機能とテストの対応を探します。既存の案内表、ディレクトリ構成、テスト名の付け方で対応が明らかなら、それを使います。コードやパッケージ間の依存関係が分かる仕組みがすでにある場合は、変更箇所を利用する側と、その利用側を確認するテストを候補へ加えます。

テストの実行記録（カバレッジ）が残っていれば、どのテストが変更行を通ったかを補助的に使えます。ただし、過去に通らなかった経路や、間接的な影響がないことまでは証明しません。カバレッジに出たテストだけを唯一の根拠にしないでください。

案内表や依存情報が古い・不完全かもしれない場合は、内容を原典や現在のコードと照らします。新しい検索やコード確認で対応が分かったらそのテストを候補に追加し、最後まで判断できなければテスト範囲を広げます。確信がないのに「影響なし」と決めないことが大切です。

## どこまで広げるか

| 変更 | 追加で確認する範囲 |
| --- | --- |
| 一つの機能内の実装 | その機能の回帰テストと直接の利用側 |
| 共通ライブラリや複数機能が使う部品 | 利用側を含む関連テスト、必要なら機能全体 |
| 公開API、設定形式、データ形式 | 作る側と使う側のテスト、互換性確認 |
| ビルド、依存関係、配布設定 | テストに加えて、作成した配布物の確認 |
| 依存関係やテスト対応を把握できない | 関連機能全体またはさらに広いテスト |

公開仕様、共有部品、認証・保存処理のように多くの箇所が使う機能は、利用先を含めた確認を選びます。コード生成、実行時の動的読み込みなどで影響先を静的に追えない場合も同様です。広い確認を実行できなければ、未確認の範囲を完了報告に残します。

テスト候補の確かさは「変更ファイルに対応するテストが明示されている」「依存関係から利用側を推定した」「動的な処理が多く影響先が不明」のように言葉で記録すれば足ります。数値の点数を設ける必要はありません。最後の場合は、関連機能全体へ広げるか、未確認だと明示します。

## テストに失敗したとき

最初に選んだテストが失敗したら、失敗箇所と変更内容を見て、直接関係する利用側のテスト、関連機能全体、全体テストの順で必要な範囲まで広げます。原因が無関係だと確認できないまま、結果を無視してはいけません。

最初のテストが成功しても、共通部品・公開仕様・配布物の変更や、影響先が不明な場合は追加の確認が必要です。一方、対象もテスト対応も明確な局所変更なら、全体テストを習慣で実行する必要はありません。どちらの場合も、選んだ範囲が今回の変更を確かめているかを見ます。

## 結果をどう残すか

完了報告には、実行した範囲と結果を短く書きます。広いテストを加えた理由、または加えなかった理由が分かれば、長いログを貼る必要はありません。

```text
検証:
- 対象テスト: 日付パーサーとCSV読み込み（18件成功）
- 関連全体: CSV機能のテスト（42件成功。共通仕様を変更したため実施）
- 未確認: なし
```

テストの選択は、検証方法そのものの選択とは別です。画面表示や作成済み配布物など、テスト以外の確認が必要かは[変更内容に応じて検証を選ぶ](変更内容に応じて検証を選ぶ.md)を参照してください。

## この方法が役立つ場合

テストが大きい・遅い、複数のアプリやパッケージがある、小さな修正でも毎回すべてのテストを調べている、といった場合に役立ちます。変更した場所から関係するテストへ進めるため、無関係な実行結果やログを読み込む量も減ります。

小さなプロジェクトで全テストがすぐ終わるなら、個別の対応表や影響解析の仕組みを作らず、全テストを実行する方が簡単です。対応表の更新が必要になったら、コードやテストの移動と同じ変更で直します。

## 補助ツール

このリポジトリには、変更ファイルからテスト候補を出すPython版とGo版、および既存の構造情報から利用側をたどるツールがあります。対応コマンド、設定形式、出力項目は、それぞれのREADMEに分けています。

- [Python版 affected-tests](../../tools/python/medium/affected-tests/README.md)
- [Go版 affected-tests](../../tools/go/medium/affected-tests/README.md)
- [source-structure-index](../../tools/common/large/source-structure-index/README.md)

すでにプロジェクトが依存関係やビルド対象を管理しているなら、その情報を再利用します。補助ツールは候補を見つける手段であり、現在のコードやテストとの照合、安全側へ範囲を広げる判断に代わるものではありません。
