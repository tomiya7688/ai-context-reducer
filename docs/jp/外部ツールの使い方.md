# 外部ツールを使って調査を短くする

外部ツールは、検索やコード構造の調査など、繰り返し必要になる作業を既存の専用プログラムに任せる方法です。適したツールがすでに使えるなら、同じ機能を簡易版として自作する前に利用を検討します。AIへ検索結果の全文を渡さず、今回必要な箇所だけを受け取れば、無関係な内容を読む量も減ります。

## 例：CSVの日付処理を調べる

小さな変更で「CSVの日付を変換するコードを探したい」ときは、全文検索で`date`や対象の関数名を検索し、見つかったコードとテストを確認できます。検索ツールが既にあるなら、別の検索プログラムを作る必要はありません。

一方、大きなリポジトリで「この関数を使う場所と、そのテストを調べたい」という作業が繰り返されるなら、シンボル索引や依存関係を調べる既存ツールが役立つことがあります。ツールの結果から関係するファイルやテストを選び、必要な箇所だけ原典で確かめます。巨大な検索結果や索引全体をAIへ渡さずに済み、AIは候補の読み比べではなく作業の判断に移れます。

## 使うツールを選ぶ

まず、何を早く正確に調べたいかを決めます。用途ごとの例は次のとおりです。

| 調べたいこと | 利用候補 | 結果をどう使うか |
| --- | --- | --- |
| 文字列や設定値がある場所 | `rg`などの全文検索 | 該当する行と周辺だけ読む |
| ファイルの場所や名前 | `fd`などのファイル検索 | 条件に合うパスから対象を選ぶ |
| 関数や型、構文の形 | `ast-grep`、Universal Ctagsなど | 候補の定義や利用先へ進む |
| ファイル間・機能間の依存 | 既存の構造索引やプロジェクトの依存情報 | 変更の利用先と関連テストを調べる |
| 行数・言語構成・Git履歴の大きさ | `scc`、`git-sizer`など | 全詳細ではなく問題のある集計だけ見る |

名前は候補例です。プロジェクトがすでに使っている検索、索引、解析、ビルドの仕組みが目的を満たすなら、それを優先します。使いたい道具を探すためだけに新しい道具を入れるのではなく、導入・更新・CIでの利用が負担に見合うかを考えます。

## 既存ツールを使うとき

既存のツールは、言語やファイル形式を正しく扱い、保守され、プロジェクト環境で使えるかを確認します。すでにビルドや依存関係を管理する仕組みがある場合、同じ解析を別実装で重ねません。高精度な索引や解析器を再利用すれば、簡易な自作処理では漏れる利用先を探せる場合があります。

ツールは候補探しを手伝いますが、結果が現在のソースやテストと合うかは確認します。索引が古い、走査が途中で止まった、対象言語を扱えないなどの状態なら、その結果だけで「他に影響はない」と判断せず、検索を補うか広い範囲を確認します。

## 使わない方がよい場合

小さなリポジトリで通常の検索だけで対象が見つかる、一度きりの作業で準備が大きい、導入によって新しい実行環境や保守が必要になる場合は、外部ツールを追加しない方が簡単です。コマンドラインや既存IDEの機能で足りるなら、それを使います。

ツールが見つからないときに自動でインストールはしません。実行環境やCIへの追加が必要なら、対応する人が利用条件、導入方法、ライセンスを確認してから判断します。具体的な製品をプロジェクトの推奨として紹介する場合は、[外部ツールの掲載基準](外部ツール掲載基準.md)も確認します。

## 結果を小さく使う

出力全体が大きい場合は、今回の質問に必要な検索結果・集計・警告だけを表示します。使った道具が何か、検索対象をどこまで調べたか、結果が途中で切れていないかも分かるようにします。結果を小さくするために、正しさに必要な内部調査まで途中で止めてはいけません。

解析結果は原典を探すための案内です。仕様の判断には正式な仕様を、動作の判断には現在のコードやテストを確認します。元の情報とツール結果が食い違う場合は、情報源を再確認し、古い索引や誤った候補をそのまま信頼しません。

## AIへの依頼例

> 目的に合い、現在使える検索・解析ツールを選んでください。最初に調べた範囲、途中で切れたか、関係する候補と理由だけを示してください。候補の元ファイルとテストを開いて確かめ、結果全体や索引全体は貼り付けないでください。
