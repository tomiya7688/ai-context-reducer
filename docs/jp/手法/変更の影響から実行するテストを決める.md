# 変更の影響から実行するテストを決める

変更したコードに関係するテストから実行し、影響が広い変更では確認範囲を広げます。ここでいうテストは、決めた入力に対してプログラムが期待どおり動くかを確かめる仕組みです。

## まず実行するテストを決める

まず、変更した場所とテストの対応表や、既存のコード依存関係を使います。

| 変更した場所 | まず実行するテスト | 範囲を広げる条件 |
| --- | --- | --- |
| `src/date/` | `tests/date/` | 日付の共通処理や保存形式も変更した |
| `src/settings/` | `tests/settings/` | 他の画面や保存処理にも影響する |
| 配布設定 | ビルドと配布物の起動確認 | 複数の環境や利用方法に影響する |

対応表がなければ、変更した関数を使う場所と関連テストを検索します。見つかった呼び出し元とテストだけでは影響を確認できない場合は、関連するフォルダー全体のテストへ広げます。

## AIへの指示例

```text
変更したファイルと、その処理を使う場所を確認してください。
変更箇所に対応するテストを先に実行し、結果と対象件数を報告してください。
共通処理、外部から使う約束、保存形式、配布方法を変更した場合や、影響先を特定できない場合は、関連範囲までテストを広げてください。
テストを絞った理由と、確認できていない範囲も書いてください。
```

## 範囲を広げる判断例

変更が一つの画面内に収まり、その画面専用のテストとの対応が明確なら、まずそのテストを実行します。共通の日付処理や保存形式を変えた場合は、それを使う他の機能のテストも加えます。

次の場合は、実行するテストを狭めすぎず、関連する広い範囲を確認します。

- 複数の機能から使われる処理を変更した。
- 外部から呼び出す方法、データ形式、通信内容を変更した。
- どのテストが変更箇所を確認するのか分からない。
- テストの対応表やコードのつながりが古い、または不完全である。

テストが失敗したら、まず失敗したテストとその処理を確認します。変更の影響先が分かった場合に、その範囲へ追加で広げます。狭いテストに成功しても、上の条件に当てはまる変更では広い確認を省略しません。

## なぜ確認する情報が減るのか

毎回すべてのテストを実行して大量の結果をAIに渡す代わりに、変更箇所に関係するテストから始めます。成功したテストの一覧やログ全文ではなく、実行した範囲・件数・失敗内容だけを残せます。影響が広いと分かった場合は必要な範囲を追加するため、確認不足を隠さずに不要な結果を減らせます。

## 導入する目安

テストが多い、実行に時間がかかる、または毎回広いログをAIへ渡しているなら、対応表を作る価値があります。小さなプロジェクトで全テストがすぐ終わり、迷うこともないなら、対応表や専用ツールを追加せず、AIに全テストを実行させれば十分です。

## 補助ツール

- 必要なら、`affected-tests`が変更ファイルに関係しそうなテストを一覧表示します。先に実行するテストを探すときに使えます。一覧だけで影響を確認できない場合は、AIに確認範囲を広げさせてください。
- 必要なら、`source-structure-index affected`が記録されたコードのつながりから影響しそうな場所を示します。変更が他のコードへ及ぶか調べるときに使えます。

どちらも関連テストの漏れや対応表の古さを完全には判定しません。影響が広い変更や不明な変更では確認範囲を広げてください。すでにプロジェクトで依存先を調べる仕組みがあれば、それを再利用できます。
