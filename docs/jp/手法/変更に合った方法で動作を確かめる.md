# 変更に合った方法で動作を確かめる

「日付の読み込みを直した」「画面を変えた」「配布用アプリを作り直した」では、確かめる場所が違います。依頼する人は変更に合う確認方法を決め、AIに対象と手順を伝えます。AIにどの変更にも同じテストを実行させるのではなく、正しくなったと判断できる確認を頼みます。

## 変更に合わせて確認する

| 変更したもの | まず行う確認 |
| --- | --- |
| 計算やデータ処理 | 変更した処理のテストを実行する |
| 時刻や乱数で結果が変わる処理 | 入力や時刻などの条件を固定して実行する |
| 画面の配置や見た目 | 自動テストに加え、必要なら画面を開いて確かめる |
| データの形式 | 代表的なデータを読み書きし、以前のデータも扱えるか確かめる |
| 配布用アプリ | 作成されたアプリが起動し、必要なファイルを含むか確かめる |
| 処理速度 | 同じ入力・同じ環境で変更前後を比べる |

たとえば画面の色だけを変えたなら、日付処理の全テストを実行する必要はないかもしれません。一方、配布用アプリを変えたのにソースコードのテストだけで終えると、配布後に起動するかは確認できません。

## テストが実際に確認した範囲を見る

テストや確認の表示が「成功」でも、今回の変更を調べていなければ根拠になりません。

- 実行したテストが0件なら、機能を確かめたことにはなりません。
- 関係ないフォルダーだけを調べた結果を、成功として扱いません。
- アプリ作成が成功しても、配布物に必要なファイルが入ったとは限りません。
- 画面の見た目が大切な変更は、画面を確認せずに完了とはしません。

何をどの範囲で確かめたかを短く記録します。大量の成功ログを全部残す必要はありません。失敗した場合は、原因を判断するのに必要な部分だけ追加で確認します。

## まず軽く確認し、必要なら広げる

コードの構文チェックがすぐ使えるなら、テストやビルドの前に実行すると、単純な書き間違いを早く見つけられます。ただし、構文が正しくても、動作や仕様が正しいとは限りません。[まず、コードの構文チェックをする](まず、コードの構文チェックをする.md)を参照してください。

変更が複数の機能に関わる、外部から使われる約束を変える、または影響先が分からない場合は、関連する範囲まで確認を広げます。テストが多く、今回実行するテストを決めにくい場合は、[変更の影響から実行するテストを決める](変更の影響から実行するテストを決める.md)方法を使えます。

時刻、乱数、環境設定で結果が変わる場合は、入力・設定・乱数の種・時間刻みなどを固定すると、同じ条件で再実行でき、実行ごとの差を大量に読み比べずに済みます。動作の原因を調べるときは、状態・イベント・判断結果など、今回の疑問に答える値を短い構造化ログに記録します。成功時は確認結果の要約だけを残し、失敗時は原因を判断する範囲だけを追加します。

完了報告には、確認した対象・結果・未確認の範囲を短く書きます。

```text
確認:
- 日付変換テスト: 12件成功
- 画面表示: 対象外
- 未確認: なし
```

変更が小さく、対象のテストが明確なら、そのテストとプロジェクトで決めた完了時の確認だけで足りることがあります。一方、正しさを確かめるのに必要な確認は、時間やログを減らすためだけに省きません。

## 確認用のファイルを残さない

保存・変換・書き出しの確認でファイルが作られる場合は、一時フォルダーを使います。確認用ファイルを通常の変更一覧に混ぜず、次の作業で誤ってAIに読ませないためです。

## AIへの指示例

```text
変更の種類に合う確認方法を表から選んで実行してください。
何を何件確認できたか、結果を短く報告してください。
変更が共通処理や複数機能に影響する場合は確認範囲を広げ、実行できなかった確認は未確認と書いてください。
確認用に作ったファイルは一時フォルダーへ置いてください。
```

## なぜ読む量が減るのか

変更に関係するテストと結果だけを調べ、必要のない全テストのログをAIへ渡さずに済みます。画面や配布用ファイルなど別の確認が必要な変更では、その対象を直接確認するため、短いログだけを根拠に誤って完了とはしません。

## 補助ツール

- 必要なら、[`validation-plan`](../../../tools/common/medium/validation-plan/README.md)が変更ファイルから、最初に行う確認の候補を示します。候補はプロジェクトのテスト手順や完了条件と照らして選んでください。

## 用語

- **Validation Routing / targeted validation**: 変更に合わせて、確かめたい性質に合う確認を選ぶ方法を、このように呼びます。
- **テスト**: 決めた入力でプログラムを動かし、期待した結果になるかを繰り返し確かめる仕組みです。
- **構文チェック**: プログラムの書き方に明らかな間違いがないか調べる確認です。動作が正しいかまでは分かりません。
- **配布用アプリ**: 利用者へ渡すために、プログラムや必要なファイルをまとめたものです。
