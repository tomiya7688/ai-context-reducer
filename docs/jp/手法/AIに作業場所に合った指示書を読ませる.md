# AIに作業場所に合った指示書を読ませる

AIに作業ルールを伝えるには、指示書を使います。まず変更するファイルを決め、そのファイルがある場所までのフォルダーを上から順にたどります。各フォルダーに指示書があれば、プロジェクト全体の指示から順にAIへ読ませます。別のアプリのフォルダーにある指示書は読みません。こうすると、今回の作業に関係する決まりを伝えつつ、関係のない手順を読ませずに済みます。

指示書は、プロジェクト全体用の一つだけでも、必要なフォルダーごとに分けても構いません。ファイル名はAIによって異なります。この例では `AGENTS.md` を使います。

デスクトップ版とウェブ版があり、設定画面の作り方や確認方法が違う架空のアプリを例にします。

## 例：AIにデスクトップ版の設定を直させる

利用者が「デスクトップ版の設定画面を直して」とAIに頼みました。対象のファイルは `apps/desktop/src/settings/config.py` です。このアプリでは、指示書を次のように置いています。

```text
project/
  AGENTS.md
  apps/
    desktop/
      AGENTS.md
      src/settings/
        AGENTS.md
        config.py
    web/
      AGENTS.md
```

変更するファイル `config.py` までのフォルダーを上からたどると、次の3つの指示書があります。AIにはこの順で読ませます。

- `project/AGENTS.md`：全体で守る設定ファイルの形式
- `apps/desktop/AGENTS.md`：デスクトップ版の確認方法
- `apps/desktop/src/settings/AGENTS.md`：設定処理の決まり

`apps/web/AGENTS.md` は変更するファイルまでのフォルダーにないため、読みません。これはウェブ版の指示書で、デスクトップ版の修正には関係しないからです。

## 指示書に書くこと

- 一番上の指示書：すべてのアプリで守る決まり
- アプリ内の指示書：そのアプリだけの作り方や確認方法
- 機能ごとの指示書：その機能だけで守る決まり
- 作業依頼：今回の目的と、完了したと判断する条件

共通の決まりを各指示書にコピーせず、その場所に固有の情報だけを書きます。共通ルールを変えたとき、何か所も直さずにすみます。

## まずは短い指示ファイルを使う

小さなプロジェクトなら、一番上に指示書を一つ置き、共通の決まりと詳しい資料の場所だけを書けば十分です。[AGENTS.mdのひな型](../../../templates/AGENTS.md)を使い、プロジェクトに合わない例は削除してください。

プロジェクトの機能や制限など、何度も伝える事実は[プロジェクト情報のひな型](../../../templates/PROJECT_CONTEXT.md)に分けて記録できます。作業ルールと事実を分けることで、作業に必要な情報だけをAIに読ませられます。

リポジトリ直下の `AGENTS.md` には、詳しい資料へのリンクだけでなく、読む作業の条件も書きます。

```markdown
- 機能や制限を確認するときは `PROJECT_CONTEXT.md` を読む。
- 保存処理を変更するときは `docs/data-format.md` を読む。
```

その作業を頼むとき、AIが `AGENTS.md` を自動で読まない製品なら、「`AGENTS.md` と、そこから今回の作業に関係すると分かった資料を読んでください」と依頼文にも書きます。

同じ手順を何度も使うなら、AIによっては手順を登録し、必要な作業で呼び出せます。たとえば、毎回同じ公開前の確認をするときに使います。登録場所や呼び出し方はAIによって異なるため、使っているAIの説明を確認し、作業を頼むときに登録した手順を使うよう伝えます。

```text
全体の決まり: AGENTS.md
画面作業の決まり: apps/desktop/AGENTS.md
繰り返し使うリリース確認: 登録済みの公開前確認手順
```

## 内容が食い違ったとき

全体の指示書はプロジェクト全体の条件、下位フォルダーの指示書はその場所に追加される条件を説明します。たとえば全体の指示書が「保存形式を変えない」と定めているなら、デスクトップ版の指示書だけでその条件を無断で取り消してはいけません。作業依頼は今回の目的と完了条件を示しますが、長く有効な決まりを黙って無効にするものではありません。

ただし、指示の優先順位は使うAIやプロジェクトの規則によって異なります。矛盾を見つけたら、独自の順序で片方を選ばず、該当する仕様や原典を確認します。それでも決められない場合は、実装前に矛盾点を依頼する人へ伝えさせてください。

## 指示を大きくしない

- 入口の指示には、全作業に必要な短い決まりと、詳しい説明の場所だけを書く。
- 特定フォルダーだけの決まりは、そのフォルダーの指示書へ分ける。
- 何度も使う作業手順だけを再利用用にまとめる。一度きりの作業は依頼文に書く。
- 同じ規則を複数の指示ファイルやスキルへコピーしない。
- 使われていない指示や古い例を定期的に削除・更新する。

新しい指示を加えたら、簡単な作業をAIに頼み、その指示を実際に読んだり呼び出したりするか確かめます。読み込んだファイルを表示できるツールならその記録を確認し、表示できない場合は、報告されたパス・変更差分・検査結果が指示書どおりか照らし合わせます。AIの自己申告だけで、自動で読まれたと判断しないでください。登録場所に置いただけでは、AIへ伝わったことにはなりません。ファイル移動やテスト変更に合わせて、指示書内のリンクとコマンドも更新します。

## 指示書を分けると役立つ場合

- デスクトップ版、ウェブ版など複数のアプリがある
- アプリや機能ごとに作り方や確認方法が違う
- 一番上の指示書が長くなり、AIに関係のない手順まで読ませている

## 分けなくてよい場合

小さなプロジェクトで、AIに必要なファイルや確認方法をすぐ伝えられるなら、指示書を分ける必要はありません。すべてのフォルダーに指示書を作らないでください。

## AIによる読み込み方の違い

AIによっては、決まった名前の指示書を自動で読みます。自動で読まない場合は、作業を頼むときに必要な指示書の場所を伝えてください。どの名前の指示書を読むかは、使うAIの説明で確かめます。

## AIへの指示例

```text
まず変更するファイルを特定してください。そのファイルがあるフォルダーまで上から順にたどり、各フォルダーにある `AGENTS.md` を上から読んでください。別のアプリのフォルダーにある `AGENTS.md` は読まないでください。自動で読み込んだ場合は、読んだファイル名を報告してください。
```

## なぜ読む量が減るのか

デスクトップ版の修正では、AIはプロジェクト全体、デスクトップ版、設定フォルダーの指示書を順に読みます。ウェブ版の指示書は読みません。そのため、今回の修正に必要な決まりを伝えながら、関係のない手順を読む量を減らせます。共通の決まりも一か所だけ直せば済みます。

## 補助ツール

- 必要なら、[`scoped-guides`](../../../tools/common/small/scoped-guides/README.md)が、対象ファイルの親フォルダーにある適用候補の指示書を探し、パスと理由だけを一覧にします。指示書を手作業でたどる代わりに使えます。

## 用語

AIが必要な指示書を作業対象の場所に応じて読むように分ける方法を、「階層型コンテキスト（Hierarchical Context / scoped instructions）」と呼びます。AIによっては、登録して繰り返し呼び出せる手順を「スキル」と呼びます。
