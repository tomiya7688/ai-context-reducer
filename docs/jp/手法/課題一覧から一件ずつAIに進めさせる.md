# 課題一覧から一件ずつAIに進めさせる

文書の修正など同じ進め方の作業が続くと、毎回「残っている課題を選び、直して、確認して、報告して」と説明するのが手間になります。課題の一覧と進め方を先に渡しておけば、その後は「次」という短い合図で、一件ずつ頼めます。

ただし、「次」だけでは何をしてよいか決まりません。どの一覧を見るか、どの順番で選ぶか、一回にどこまで進めるか、何が起きたら止まるかを最初に決めてください。

## 使うとよい場合

- 同じ確認・報告の手順で進める修正が複数あり、一件ずつ結果を見たいときに使えます。
- 例えば、説明不足を課題として記録し、次の依頼では残っている一件を直してもらう作業に向いています。
- 一度きりの小さな修正なら、対象と完了条件を直接伝える方が簡単です。
- 何を作るかや、作業同士の前後関係が決まっていなければ、まず調査や設計判断を一件の課題にします。大きな依頼をそのまま「順番に全部実装」と頼まないでください。

## 使うときの手順

### 1. 課題を一か所へまとめる

既存の課題管理を使うか、例えば `docs/tasks/queue.md` に一覧を作ります。別の一覧を重ねて管理する必要はありません。各課題には、目的、変更範囲、完了条件、確認方法、先に必要な作業を記載してください。

次は、一覧の書き方を説明する架空の例です。優先度は1が最優先とします。

| ID | 優先度 | 作業 | 先に必要な作業 | 状態 |
| --- | ---: | --- | --- | --- |
| T01 | 2 | 保存失敗の再現条件を特定する | なし | 未着手 |
| T02 | 1 | 保存失敗の不具合を修正する | T01 | 未着手 |
| T03 | 3 | 案内文の壊れたリンクを直す | なし | 未着手 |

例えばT01の詳しい内容は、`docs/tasks/T01.md` に次のように保存できます。Issueを使う場合は、その本文へ同じ項目を書きます。

```markdown
# 保存失敗の再現条件を特定する
- 目的: どの入力・操作で失敗するか確認する
- 対象: Issueの報告例と、設定の保存処理
- 今回はしない: 保存形式の変更、動作の修正
- 完了条件: 再現する入力・操作・期待と実際の結果を記録し、T02へ渡せる
- 確認方法: 報告された手順を試し、結果を実行環境とともに記録する
- 先に必要な作業: なし
- 参照先: 実際のIssue、仕様、対象コードのパス
```

一件は、変更や調査の結果を独立して確認できる大きさにします。別々に合否を判断できる不具合は分けられますが、同じ仕様と検査でしか確認できない数行の修正を、行ごとの課題へ分ける必要はありません。

新しく見つかった別の問題は、目的と完了条件を付けて課題に記録します。Issueの作成が許可範囲外なら、作成用の本文を報告してください。現在の一件へ黙って追加しません。

### 2. 「次」で呼び出す手順を保存する

例えば `docs/ai/next-task.md` に、次の指示を保存します。一覧の場所、同順位の選び方、実行範囲、上限は自分のプロジェクトに合わせて変えてください。

```text
あなたは、このプロジェクトの課題を一件ずつ進める担当です。
「次」と依頼されたら、次の手順を一回だけ実施してください。

1. docs/tasks/queue.md と、関係する最新の変更・作業記録を確認する。
2. 前回の課題が確認待ち・作業途中なら、その課題を再開する。
   結果または続けられない理由を報告して終了し、新しい課題は選ばない。
3. 未完了で、他の担当が着手しておらず、前提が満たされた課題を候補にする。
   優先度の数が小さい順、同順位なら登録が古い順に一件だけ選ぶ。
4. 選んだID、目的、変更範囲、完了条件、前提を確認した根拠を短く示す。
5. その一件の範囲を実施し、指定された確認を行う。
6. 結果と根拠、未確認事項、課題の状態を記録し、報告して終了する。
   自動で次の課題へは進まず、次の合図を待つ。

実行範囲: 対象ファイルの編集と、課題で指定された確認。
外部への書込み、PR作成、マージなどは、事前に明示された許可の範囲に従う。
必要な許可がなければ、その操作の前に対象と理由を示して確認する。
すでにある許可を毎回取り直さず、「次」を新しい許可の追加とは扱わない。

一回の対象は一件。同じ失敗に対する修正と確認は、例えば2回を上限にする。
新しい根拠が得られない場合は、上限前でも止めて状況を報告する。
仕様の判断が必要、根拠が不足、変更が許可範囲を超える場合は、
その判断に依存する作業を止め、確認できた事実と必要な質問を返す。
着手できる課題がなければ、完了なのか、前提・回答待ちなのかを報告する。
```

「2回」は設定例であり、どの作業にも適した値ではありません。一件の中に必要な編集や検査が複数あることと、同じ失敗へのやり直しを無制限に続けることを分けてください。失敗した検査を弱めて、完了に見せることもしません。

### 3. 保存先をAIに伝える

最初の依頼では、一覧と手順を明示します。

```text
今後「次」と送ったら、docs/ai/next-task.md の手順を一回実施してください。
課題一覧は docs/tasks/queue.md です。
まず両方を読み、対象と進め方を確認してください。
今回は、着手できる一件を進めてください。
```

継続して使うなら、AIが読む入口の指示書から「『次』で課題を進める依頼では `docs/ai/next-task.md` を読む」と参照させます。`AGENTS.md` などを自動で読むかは利用する環境で確認してください。自動で読まれなければ、依頼にパスを添えます。

ファイルを読めないチャットには、手順、最新の一覧、今回の課題本文と必要な資料を添付・貼り付けます。新しいチャットで「次」とだけ送っても、前のチャットで決めた条件が届くとは限りません。[チャットを分けるときの引継ぎ](../AI利用/作業ごとにAIの役割とチャットを分ける.md)も使えます。

### 4. 毎回、着手できる一件を確認させる

一覧の例では、T02は最優先でもT01の結果が必要です。T01とT03が着手可能なら、優先度が上のT01を選びます。T01が終わり、再現条件の記録を使える状態になった次の回で、T02を選べます。

先に必要な作業は、その課題の記載だけでなく、受け取る仕様・コード・確認結果からも確かめさせます。Issueが閉じていても、別の作業との重複で閉じただけかもしれません。必要な結果がどこにあり、今回使う版に反映されているかを確認します。

課題同士が互いの完了を待っている、優先順が矛盾する、仕様が未確定、といった場合は理由を報告させます。番号の若さや作業の簡単さだけで優先度を変えさせません。次の依頼では一覧と関連する変更を更新して確認させ、前回の候補をそのまま使い回しません。

### 5. 完了・確認待ち・中断を分けて報告させる

例えば `docs/tasks/T01-result.md`、または元のIssueに、次の形式で結果を残させます。記録先への書込みも、決めた許可範囲に従います。

```markdown
- 選んだ課題と理由:
- 行ったこと・変更した場所:
- 確認した対象の版・コマンドや操作・結果・根拠の場所:
- 完了条件ごとの結果:
- 未確認・未解決:
- 状態: 完了 / 確認待ち / 中断
- 次に必要な判断や作業:
```

必要な確認がすべて終わった場合だけ完了とします。CIなど共有先の自動検査を待っている、実行環境がなく確認できない、といった場合は確認待ちです。仕様の選択が必要なら中断し、選択肢と判断に足りない条件を示させます。作業一覧の状態も合わせます。

PRは変更を取り込むための提案です。PRを作ったことだけで、完了条件を満たしたとは扱いません。レビューやマージまでが完了条件なら、必要な確認と既存の許可に従ってそこまで進めます。途中の結果は途中として残してください。

あなたは報告を差分、元資料、確認結果と照合し、必要なら訂正を頼みます。未確認が残る場合は、何をもって再開できるかも記録します。全件完了した場合は終了し、新しい合図があっても存在しない作業を作りません。

## Issueを使う場合の例

このリポジトリで「不足している手法はIssueへ」「次」と進める場合も、基本は同じです。Issueは、目的と完了条件を記録し、状態を追うための課題票として使います。

1. 不足を見つけたら既存Issueとの重複を確認し、目的・対象・完了条件を書いて登録します。
2. 「次」の依頼で最新のIssueとPRを確認し、優先順と前提を満たす一件を選ばせます。
3. その文書、必要な翻訳、案内リンクなど、一件の完了条件に必要な範囲を変更させます。
4. 確認結果と残りを記録し、決めた完了条件を満たした時点でIssueの状態を更新します。
5. 報告を受け取った後、あなたが次の合図を送ります。

課題を選んだ後、最初に何を読むかは[作業の種類ごとの案内](作業の種類ごとに、AIに最初に読む場所を伝える.md)で決められます。本書は「次にどの課題を一件進めるか」、その案内は「選んだ作業でどこから読むか」を扱います。

## 自動で繰り返す場合との違い

ここまでの方法は、あなたの合図ごとに一件だけ進めます。AIが一件の中で検索、編集、確認を繰り返すことと、合図なしで次々と課題を始めることは別です。

複数の課題を自動で進めたい場合は、対象一覧、最大件数、全体の時間や利用量の上限、失敗時の扱い、人へ戻す条件を別に決める必要があります。例えば「指定した三件まで、仕様の判断が必要になったら終了」と指定できます。時間や利用量を取得できない環境では、その上限を守れたとは扱わず、件数など確認できる上限を使います。

手順の文書だけでは、時間になったら起動したり、会話終了後も動き続けたりはしません。自動で起動する仕組みと、作業中に停止条件を確かめる仕組みが必要です。

## なぜ繰り返す説明を減らせるか

一度決めた手順を参照すれば、毎回長い依頼文を作り直す必要がなくなります。一件の目的、読む資料、確認結果を記録すると、次の回に長い会話や全課題の詳細を読み直さず、候補と今回必要な本文へ進みやすくなります。

一覧の確認や結果の記録にも入力が必要です。同じチャットを長く続けると履歴も蓄積し、細かすぎる課題は管理の手間を増やします。「次」という入力が短いだけでは、AIが使う総量が減ったとは言えません。[使用量の記録方法](../AI利用/作業ごとのコンテキスト使用量の目安を作る.md)で、履歴・確認・やり直しを含む量と、必要な品質を保てたかを比べてください。

## 補助ツール・機能

- **課題管理の一覧・絞込み:** 状態、優先度、先に必要な作業から候補を探せます。本文を開く前の選別に使えますが、前提が満たされたかは結果でも確認します。
- **短い指示を保存して呼び出す機能:** 同じ選択・確認・報告の手順を再利用できます。対応した環境では、手順の参照を毎回貼る手間を減らせます。
- **作業回数を制限する実行機能:** 対応した環境では、決めた回数や条件で処理を終了できます。実際に何を数え、失敗や中断をどう扱うか確認して使います。

## この進め方について

残った作業を一覧へまとめたものは**バックログ**、先に必要な作業を待ってから着手する関係は**依存関係**と呼ばれます。優先順と依存関係から着手できる作業を一件選び、結果を記録する運用です。

AIが結果を受け取り、次の操作を決めて実行する繰り返しは、**エージェントの作業ループ**と呼ばれます。[ReActの論文](https://arxiv.org/abs/2210.03629v3)は、判断と操作を組み合わせ、外部から得た結果を次の判断へ使う方法を紹介しています。[1] 本書のIssue運用や「次」という合図を提案・検証した論文ではなく、コンテキスト削減の根拠として数値を転用しません。
