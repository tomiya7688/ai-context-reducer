# AIに無駄な推論と再試行をさせない

AIにコードの修正を頼んだとき、簡単な変更なのに長い検討が続いたり、同じエラーが出るコマンドを何度も実行したりすることがあります。**考える量を何でも減らすのではなく、今回の作業に必要な判断と検査は残し、進展のない繰り返しを減らす**方法を紹介します。

あなたは、まず今回の作業がどれほど難しいかを判断し、AIに「何を確認できたら次へ進むか」「同じ失敗が続いたら何を報告するか」を伝えられます。ただし、AIの内部で使う推論の量を指定できるか、作業の途中経過を観測できるかは製品やモデルによって違います。

このページで扱うのは、**推論の強さの調整、考えるのを終える条件、進展のない再試行の防止**です。 **重大な方針の分岐や行き詰まりで別のAIから反例や助言を得たいとき**は、[難しい判断だけ別のAIに相談する](難しい判断だけ別のAIに相談する.md)を参照してください。別モデルに相談すると追加の入出力が生じるため、相談そのものを一律の節約方法とは扱いません。資料を探すところで調査を止める方法は[AIに調査を止めさせる条件を決める](AIに調査を止めさせる条件を決める.md)、以前の作業履歴から浪費を調べる方法は[AIの作業履歴から無駄な読み込みを見つけて改善する](AIの作業履歴から無駄な読み込みを見つけて改善する.md)で詳しく説明しています。

## まず、何が繰り返されているかを区別する

**推論**とは、AIモデルが受け取った情報を使い、答えや次にすべきことを判断する処理です。推論に使ったトークン数（文章を処理するときの小さな単位）を提供元が報告する場合がありますが、**AIが表示した文章の長さが、そのまま内部の推論量になるわけではありません**。

**コーディングエージェント**は、AIモデルだけでなく、ファイル検索・編集・コマンド実行などの機能を組み合わせて作業します。そのため、次の二つは別です。

| 観測する問題 | 具体例 | 最初に試せること |
| --- | --- | --- |
| モデルが必要以上に推論する | 一行の設定変更でも、複数の設計案を長く比較する | 作業に合う推論設定を選ぶ。変更と確認の範囲を明示する |
| エージェントが同じ行動を繰り返す | 同じ入力・同じファイルのまま、同じエラーになるコマンドを再実行する | 前回から変わったことを確かめさせ、進展がなければ止める |

AIの内部の考え方をすべて読めるとは限りません。一方、実行したコマンド、変更差分、テストの結果は、使っているエージェントに記録がある場合に確認できます。**見える記録だけで「内部で同じことを考えた」と断定しないでください。**

## 方法1：仕事の難しさに合う推論の強さを選ぶ

AIのモデルや利用サービスに推論の強さを選ぶ設定があるなら、あなたは仕事の内容と必要な正確さに合わせて選べます。

| 今回の作業 | 最初に検討する設定 | 必要なら強くする条件 |
| --- | --- | --- |
| ファイル名の候補探し、短い文章の分類、単純な書式の修正 | 低めの推論設定 | 読む対象や分類条件が曖昧で、誤りが出る |
| 関係するコードが見えている小さな修正 | 低～中程度 | 変更が他の機能にも影響する、テストで失敗する |
| 不具合の原因調査、複数の設計案の比較 | 中～高程度 | 原因候補が多い、仕様が矛盾する、重要な判断が必要 |
| 認証、データの破損、広範囲な変更 | 正確さと検証を優先 | 省いた推論や検証によって危険が生じる |

この表は**試し始めるための考え方**であり、すべてのモデルで同じ設定名・同じ結果になるという意味ではありません。

例えば[OpenAIのAPI](https://developers.openai.com/api/docs/guides/reasoning)では、対応モデルの `reasoning.effort` で推論の強さを調整できます。[Claude API](https://platform.claude.com/docs/en/build-with-claude/effort)でも対応モデルの `effort` を設定できます。ただし、対応する値、初期値、変更できる場所はモデルやサービスによって違います。**あなたが使うコーディングエージェントの画面や設定に項目がなければ、依頼文に「推論を少なく」と書くだけで内部の推論量を確実に変更できるわけではありません。**

推論設定と、どこまでファイルを閲覧・編集・実行できるかの違いは、[AI利用でよくある質問](../AI利用/よくある質問.md#どのモデルや編集方法をどんな作業に使えばよいか)も参照してください。

### 作業全体に予算を伝える場合

「一回の回答でどれくらい考えるか」と「調査・編集・検査・報告という作業全体にどれくらい使うか」は違います。

[Claude APIのタスク予算（ベータ版）](https://platform.claude.com/docs/en/build-with-claude/task-budgets)では、一部の対応モデルに、ツール呼出しやその結果も含む作業全体の**目標となるトークン予算**を伝えられます。しかし、この予算は**助言的な目安であって強制停止の上限ではありません**。現時点でClaude Codeの通常の利用画面には対応していません。すべてのAIで共通に設定できるものではないため、必要なら使っている製品の公式資料を確認してください。

## 方法2：必要な根拠がそろったら、追加の検討を終える

AIに作業を始めさせる前に、あなたは「何が分かれば変更できるか」「何が確認できれば終わりか」を決められます。判断できる根拠がそろった後まで、同じ候補を理由なく比較し続けさせる必要はありません。

例えば「保存した設定が再起動後も残るように直す」仕事なら、次が重要です。

1. AIが、保存と読み込みを担当するコード、関係する仕様、テストを特定する。
2. AIが、問題を再現できる条件と、変更してはいけない既存の動作を確認する。
3. AIが必要な修正を行い、**保存・再起動・読み込みの動作を確認するテスト**を実行する。
4. あなたが変更差分と検査結果を確かめ、完了条件を満たしたら終える。

すでに検査が通り、変更範囲と仕様にも問題がなければ、AIに「さらに五つの別案を検討する」「同じ理由を何度も説明し直す」といった仕事まで追加しないようにできます。

ただし、**検査に失敗した、根拠が足りない、変更の影響先が不明、必要な承認がない**場合は、考えるのを止めて「成功」と報告させてはいけません。その時点で何が不足しているかを明らかにし、必要なところだけ追加で調べさせます。

## 方法3：進展のない再試行を検出して止める

同じ失敗を繰り返したときは、あなたがAIに「もう一度」だけを指示するのではなく、**前回から何が変わったか**を確かめさせます。モデルの内部の推論を読む必要はありません。

次は説明用の架空の例です。

| AIの操作 | 観測した結果 | 次にすべきこと |
| --- | --- | --- |
| ① テストコマンドを実行する | 設定ファイルが見つからず失敗 | 指定した場所とエラーの原因を調べる |
| ② 設定やコマンドを直さず、同じものを再実行する | 同じエラーが出る | 進展なし。前回との差分を確認して中断する |
| ③ 設定ファイルの場所を正しく指定し、再実行する | 前と異なる結果になる | 新しい結果を確認し、必要な作業を続ける |

**同じコマンドが二回出たら必ず無駄、という意味ではありません。** 通信や時刻によって変わる不具合の再現、断続的な失敗の確認、修正後の再テストは必要になる場合があります。判断するのは、コマンドの文字列だけでなく、入力、対象ファイルの版、環境、結果、再試行の目的です。

AIに進展がないと判断させたら、次の行動を選ばせます。

- 新しい根拠を調べられるなら、その場所を一つ示して調査する。
- 原因が分かったなら、入力やコードを直してから実行する。
- 追加の情報や権限が必要なら、推測や制限の回避をせず、あなたへ報告して止まる。

実行回数に上限を設けたい場合も、数値は作業によって変えてください。失敗を隠すためにテストを飛ばしたり、権限を無断で変更したりしてはいけません。

## 方法4：必要な検証と、重複した自己確認を区別する

AIに毎回「計画を三回作り、すべてのテストを繰り返し、最後にさらに自己評価する」と指示すれば、かえって時間とトークンが増えることがあります。

[Microsoft Researchの2026年の研究](https://www.microsoft.com/en-us/research/publication/agent-skills-can-be-harmful-an-empirical-study-of-skill-induced-failures-in-llm-agents/)は、エージェントに追加の作業手順を与えた場合に生じた**307件の失敗・効率悪化**を調べました。このうち過剰な検証に関係する事例は67件でした。これは調査した特定の実験例の内訳であり、一般のAI作業の67％が無駄だという意味ではありません。

あなたはAIに「今回の変更で壊れる可能性がある部分を調べ、その部分を確認できるテストを選んで実行する」と頼めます。**本当に必要なテストは省かず、同じ結果が得られているのに理由なく繰り返す検証だけを減らす**ことが重要です。検査範囲の決め方は[変更に合った方法で動作を確かめる](変更に合った方法で動作を確かめる.md)を参照してください。

## AIへの依頼文（あなたがAIに送る文章）

次の例は、設定保存の不具合を直す場合に使えます。あなたが必要に応じて、目的や対象を書き換えてください。

~~~text
目的: 保存した設定が、アプリの再起動後も残るように直す。

最初に保存と読み込みのコード、関係する仕様、既存テストを調べてください。
問題の再現条件と、変更してはいけない動作を確認してから修正してください。
完了条件に必要なテストを実行し、変更差分と結果を報告してください。

すでに確認した事実だけで判断できるなら、同じ調査や設計案の比較を繰り返さないでください。
同じ入力・同じ環境・同じエラーの再試行が続く場合は、
前回から変わったことと、新たに分かったことを先に報告してください。

進展がなく、次に調べる根拠もない場合は作業を中断し、
試した内容、未確認事項、次に必要な情報を報告してください。
必要なテストや安全確認は省略しないでください。
~~~

この依頼文によって**推論トークンの上限が強制されるわけではありません**。AIが実際にどの操作を行ったかと、必要な検査を終えたかをあなたが確認してください。

## 既存研究は何を減らしたのか

研究では、モデルが答えに至るまでに生成する途中の推論が長くなりすぎる状態を **Overthinking（過剰な推論）** と呼ぶことがあります。研究によって、問題の難しさの判断方法や、途中で推論を止める仕組みは異なります。

| 研究 | 何を変えるか | 報告された結果と限界 |
| --- | --- | --- |
| **[TALE（2025）](https://aclanthology.org/2025.findings-acl.1274/)** | 問題の難しさに応じて推論に使う予算を調整する | 評価条件では推論のトークン使用量を減らしたが、正確さの低下も一部報告した。すべての作業で同じ効果になるわけではない |
| **[REFRAIN（2026）](https://aclanthology.org/2026.acl-long.1256/)** | モデルの途中の推論で、結論を変えない反復が増えてきたら終了を判断する | 4種類の評価課題・2系統のモデルで、標準的な推論との比較によりトークンを20～55％削減し、正答率を維持または改善した |
| **[Sonata（2026）](https://proceedings.iclr.cc/paper_files/paper/2026/hash/96dd7b14cde7e0a5194eceedafb2f249-Abstract-Conference.html)** | モデル内部の情報から問題の難しさを予測し、推論の予算を配分する | 対象モデルと評価課題では推論トークンを20～60％削減し、正答率を維持した条件がある |
| **[ASAG（2026）](https://proceedings.mlr.press/v306/li26ev.html)** | モデル内部で情報のどこに注意を向けているかを調べ、追加の推論が役立つか判断する | Qwen3-8Bを使った研究条件では、生成トークンを約40％減らしながら平均正答率を改善した |

これらの数値は**各論文のモデル・問題集・比較条件に限られます**。ObaPickや一般のコーディング作業で実測した削減率ではありません。

特に、Sonataはモデルの内部情報を読む予測器を使い、ASAGはモデル内部の注意の情報を使います。REFRAINも推論の途中で終了を判断する仕組みを必要とします。**あなたが普段使うCodexやClaude Codeの外部画面・APIから、これらの研究をそのまま有効化できるとは限りません。** モデル内部の推論の全文を取得できないサービスでは、同じ手法を簡単な指示文だけで再現したと主張しないでください。

TALEからは「簡単な仕事には必要以上の推論予算を与えない」、REFRAINなどからは「必要な判断が済んだら、さらに考え続けるべきか見直す」という考え方を学べます。エージェントで実際に試す際は、**推論の設定、調査の終了条件、外部の操作履歴**という確認可能な部分から始めます。

## 本当に無駄を減らせたか確かめる

あなたは、同じ程度の難しさの作業について、変更前と変更後を次の条件で比較できます。

| 記録すること | 確認する理由 |
| --- | --- |
| 目的、対象コードの版、使ったモデルと設定 | 条件が変わったために結果が違う可能性を区別する |
| 必須テストの成否、修正結果、手戻りや人の追加作業 | トークンだけ減って品質が落ちた変更を成功としない |
| モデルの入出力トークンと、取得できれば推論用トークン | 実際に削減した量を確認する。見えない値は未計測とする |
| コマンド実行回数、失敗の繰返し、全体の作業時間 | モデルの内部とは別に、エージェントの無駄な行動が減ったか調べる |

推論に使ったトークンが出力の内訳として報告される場合、出力トークンへもう一度加算してはいけません。入力を再利用したキャッシュの内訳も同様です。測定方法は[作業ごとのコンテキスト使用量の目安を作る](../AI利用/作業ごとのコンテキスト使用量の目安を作る.md)を参照してください。

**必要な根拠やテストを削ったことで短くなった結果は成功ではありません。** 失敗が増える、理由のない中断が増える、同じ作業をやり直すなら、設定や停止条件を見直してください。
