# 一つの指摘から、同じ問題をAIに探させる

文書の一か所で「誰が操作するのか分からない」と指摘して直しても、別のページに同じ説明不足が残っていることがあります。毎回あなたが場所を探して指摘する代わりに、直した例と判断基準をAIへ渡し、決めた範囲の他の場所も調べさせられます。

「似た文章を全部直して」だけでは、引用した依頼文や意味の違う説明まで変えてしまう場合があります。何が問題か、どこを調べるか、似ていても対象外になるものを先に決めてください。

## 使う場面と判断基準

- 同じ説明不足、同じ条件で起きるコードの誤り、同じ設定の更新漏れを繰り返し指摘している場合に使えます。
- 一件の例から、他の箇所にも当てはめられる条件を説明できる場合に向きます。「なんとなく読みづらい」だけなら、先に何が判断できないかを具体化してください。
- 同じ単語があるだけでは、同じ問題とは限りません。読む人、実行者、入力条件、設定を使う場所などの文脈も確認させます。
- まず一つの問題と一つの範囲から始めます。異なる問題を同時に渡す場合は、基準と結果を問題ごとに分けてください。

## 使うときの手順

### 1. 問題の例、理由、対象外を渡す

文書なら、例えば次のように伝えます。パスや見出しは架空の例なので、実在するものへ置き換えてください。

```text
指摘例: docs/users/save.md「操作」の「設定を確認する」
問題: 読者への手順なのに、人が確認するのかAIに確認させるのか分からない。
この手順ではAIが設定を確認するため、人には「AIに設定を確認させる」と説明する。
調査範囲: docs/users/ 内の日本語Markdown
対象外: AIへ渡す依頼文の引用、ツール自体の動作説明、別の読者向けの仕様書
```

例の前後もAIに読ませ、なぜその箇所が問題かを確かめさせます。AIへの依頼文で「設定を確認してください」と書くことは、引用の読み手がAIなので、この基準では対象外です。単に「確認する」をすべて置き換える作業にしません。

コードや設定でも、同じように条件を分けられます。

| 対象 | 問題の条件 | 似ていても対象外の例 |
| --- | --- | --- |
| コード | 省略可能と仕様で決まったキーを、ない場合の処理なしで読み出している | 必須キーを読み、ない場合はエラーにする仕様の処理 |
| 設定 | 接続先を変更したのに、現行の実行環境で使う設定だけ古いまま | 過去版を再現するテスト用データ、移行前の説明例 |
| 文書 | 人が読む操作手順で、AIへ任せる操作の実行者が不明 | AIへの依頼文の引用、ツールが行う処理の説明 |

初期値や新しい接続先は例から推測させず、仕様や変更の記録から確認させてください。

### 2. 検索前に、確認基準を短く言い直させる

AIには「該当する条件」「対象外」「判断に必要な根拠」「調査範囲」を返させます。解釈が複数ある場合は、検索を始める前に質問させてください。あなたが基準を確認してから、その範囲の調査へ進めます。

繰り返し使う場合は、例えば `docs/review/actor-clarity.md` に基準を保存できます。

```markdown
# 操作の実行者が分かるかの確認基準

- 対象: docs/users/ の日本語Markdownにある、人へ向けた操作手順
- 該当: AIへ任せる操作なのに、その実行者が本文や前後から分からない
- 対象外: AIへの依頼文の引用、ツール自体の動作説明、仕様書
- 根拠: 対象読者、前後の説明、その操作を担当する人やAIの記述
- 修正方針: 読者に何をさせるか分かる表現へ直す。内容を推測して足さない
- 確認した指摘例: docs/users/save.md「操作」
```

基準を広げるときは、追加する対象と対象外を決め直してください。元の一件では分からない条件までAIに一般化させません。今回だけなら、同じ項目を依頼文に書くだけでも使えます。

### 3. 調べる一覧と、確認した範囲を記録させる

大きな範囲なら、フォルダーやファイル種類ごとに区切ります。例えば `docs/review/actor-clarity-results.md` に、基準と結果を結び付けて記録させます。

```markdown
# 同じ問題の調査結果

- 基準: docs/review/actor-clarity.md
- 調査時点の版、または作業開始時の状態:
- 対象ファイル一覧:
- 除外した場所と理由:
- 検索した範囲:
- 内容を基準に照らして確認した範囲:
- 未確認のファイル・節と理由:

| 区分 | ファイル・行または見出し | 判断理由と根拠 | 修正対象として確認済みか |
| --- | --- | --- | --- |
| 確実に該当 / 要確認 / 対象外 | | | |
```

検索したことと、内容を読んで基準に照らしたことを分けてください。検索で一致しなかったファイルも、意味の違う書き方で同じ問題を含む可能性があります。隠れたファイル、生成物、検索が除外した場所、読めなかったファイルは、対象か対象外かを明記します。

行番号は編集でずれるため、関数名、設定名、見出しなども添えさせると後で探せます。途中で基準や対象ファイルが変わったら、どの基準でどこまで確認したかを残して、影響する箇所を再点検させてください。

### 4. 候補を根拠付きで返させる

| 区分 | 意味 | 文書の例 |
| --- | --- | --- |
| 確実に該当 | 問題の条件と根拠がそろっている | 人向けの手順で、AIが担当する操作なのに実行者の説明がない |
| 要確認 | 条件の一部や根拠が不明 | 前後を読んでも、人が行うかAIへ任せるか決まっていない |
| 対象外 | 似ているが、合意した条件に該当しない | AIへの引用依頼文なので、AIへ「確認する」と指示している |

「確実に該当」も、修正を始めてよいという意味とは別です。候補の場所と前後、判断理由をあなたが確認し、修正してよい候補を指定してください。意味が不明なら質問させ、推測で一括修正させません。大量の対象外は代表例と除外理由を短く示し、必要な判断の根拠は省かないでください。

### 5. 修正後も、同じ基準で再確認させる

修正を頼むときは、確認済みの対象と変更してよい範囲を指定します。AIには変更一覧を作らせ、差分が今回の問題を直す内容か確認させます。

同じ検索と、基準に基づく内容の確認をもう一度行わせてください。単語が消えたことだけで完了にしません。修正した箇所が意味を保ったまま基準を満たすか、ほかの候補や要確認箇所が残っているかも点検させます。コードや設定なら、変更に合った既存の検査とテストの結果も確認します。

再確認の時点でファイルが変わっていれば、増えた箇所や変更された箇所も確認対象に戻します。未確認の範囲があるときは「調べた範囲で残る該当は○件、未確認はこの場所」と報告させます。宣言した対象一覧をすべて基準に照らして確認した場合だけ、その範囲の全件確認と書かせてください。それでも、あらゆる問題が存在しない保証にはなりません。

## AIへの依頼例

次の例は調査だけを頼むものです。実在する指摘例と保存先へ置き換えてください。

```text
次の指摘と同じ問題が、指定範囲のほかの場所にもないか調べてください。
指摘例: docs/users/save.md「操作」の「設定を確認する」
問題: 人への手順なのに、AIへ任せる操作の実行者が分からない
範囲: docs/users/ 内の日本語Markdown
対象外: AIへの依頼文の引用、ツール自体の動作説明、仕様書

まず該当条件、対象外、必要な根拠を短くまとめてください。
解釈が複数ある場合は質問し、私が基準を確認するまで全体検索は始めないでください。
確認後、docs/review/actor-clarity.mdへ基準を保存してください。

対象ファイル一覧を作り、候補は前後と根拠を読んで判断してください。
確実に該当・要確認・対象外に分け、場所と判断理由を
docs/review/actor-clarity-results.mdへ記録してください。
検索した範囲と内容確認した範囲、除外と未確認を分けて報告してください。
この依頼では変更せず、候補一覧だけ返してください。
```

候補を確認した後なら、続けて次のように頼めます。

```text
結果一覧のうち、確認済みと指定した候補だけ修正してください。
要確認や対象外は変更しないでください。
修正した場所と変更内容を示し、同じ基準で修正箇所と残る候補を再確認してください。
必要な検査結果、残る問題、内容確認済みと未確認の範囲を報告してください。
```

ファイルを読めないチャットには、指摘の前後、基準、対象の一覧と必要な本文を添付するか貼り付けます。パスだけでは内容は渡りません。AIが見ていないファイルを調査済みと扱わせないでください。

繰り返す確認は、例えば `AGENTS.md` へ「利用者向け操作説明を変更するときは `docs/review/actor-clarity.md` を読み、変更箇所へ適用する」と短く参照を置けます。詳細や過去の候補一覧を入口へコピーしません。指示書を自動で読まない環境では、そのパスと使う条件を依頼文で伝えます。

## 説明の修正と、同じ問題の調査を使い分ける

一か所の説明を直すときは、読者が理解できない点を見つけ、その箇所の説明を補います。その指摘が他の場所にも当てはまる場合は、本書の手順で基準と範囲を決め、候補を確認してから修正します。

読む人に何が伝わらないかの基準を作るときは、[読者が理解できる説明に直す](読者が理解できる説明に直す.md)の例も使えます。コードを新しく増やす前の再利用判断は、[AIに既存コードを調べさせ、似た役割の追加を防ぐ](AIに既存コードを調べさせ、似た役割の追加を防ぐ.md)で説明しています。

## コンテキスト使用量が減る理由と限界

一件の指摘と確認基準を再利用すると、人が場所ごとに同じ問題を説明し直す往復を減らせます。範囲と条件を決めてから調査すれば、無関係な資料を読ませる量も抑えられます。候補と根拠を短く残すことで、後から調査の経緯を会話全体から探し直す負担も減らせます。

調査、候補の確認、再点検にも入力が必要です。範囲を広げすぎたり、対象外の全文を毎回出したりすると使用量が増えます。必要な根拠や確認は省略せず、同じ説明と無関係な読み込みを減らしてください。この依頼方法の発見精度やコンテキスト削減量は実測していません。

## 補助ツール

- **文字列検索:** 例と同じ語や処理を含む場所を候補として挙げます。別の言い回しや、同じ語を使った別の意味は、本文を読んで確かめます。
- **構造を使ったコード検索:** 関数や処理の形から候補を探します。コードの確認に使えますが、仕様上の例外や使う条件までは判定できない場合があります。
- **類似コードの検出:** 似たコードのまとまりを示します。同じ問題かは、入力条件や使う側も調べて判断します。
- **Gitの差分表示:** 修正した場所を表示します。確認済みの候補だけ変わったか、意味の違う変更が混ざっていないか点検できます。

## この手法について

[Wuほかの論文](https://proceedings.mlr.press/v306/wu26bk.html)は、一つの修正例から誤りの特徴を作り、コード全体の似た不具合を探す研究を報告しています。[1] 同じ原因が複数のコード箇所に現れる不具合を、論文では **Recurring Pattern Bugs（繰り返すパターンの不具合）**と呼びます。

論文は、コードのつながりなどを調べる仕組みと、文章を生成・解釈するAI（LLM）を組み合わせて評価しています。ここにある一般的なチャットへの依頼文や、文書・設定への適用を検証したものではありません。論文の成績を、この依頼方法の発見精度や削減量として使いません。
