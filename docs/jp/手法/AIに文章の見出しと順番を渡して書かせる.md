# AIに文章の見出しと順番を渡して書かせる

AIに操作説明を何本も書かせると、ある説明には準備がなく、別の説明には成功したかどうかの確認がない、といった違いが出ることがあります。先に「目的、準備、操作、結果の確認」の順番と、それぞれに書く内容を渡せば、毎回同じ構成で本文を作らせやすくなります。

## 使う場面と判断基準

- 同じ種類の文書を繰り返し書く場合に使えます。機能ごとの操作説明や変更提案で、毎回必要な情報をそろえたい場合が例です。
- 見出しがあるだけでは内容が抜ける場合は、各見出しに「何を書けば満たしたことになるか」も指定してください。操作の説明なら、実行者・画面・ボタン名・操作後の状態です。
- 一度だけの短い回答なら、必要な項目を依頼文に直接書く方が簡単です。文書ごとに構成が大きく違う場合も、一つのひな型に全部詰め込まず、その文書に必要な構成を決めてください。

定型の文章に名前や日付を入れる用途には、[決まった文章やファイルをひな型から作る方法](https://github.com/tomiya7688/ai-context-reducer/blob/main/docs/jp/決まった文章やファイルをひな型から作る.md)が使えます。次の違いで選べます。

| 作りたいもの | 渡すもの | 本文を作る方法 |
| --- | --- | --- |
| 決まった告知文の日付や製品名を変える | 固定の文章と差し替える値 | 専用プログラムで値を入れる |
| 同じ構成で機能ごとの操作説明を書く | 見出し・各項目の内容・事実を確認する資料 | AIに資料を読ませて本文を書かせる |

## 使うときの手順

### 1. 短い構成をファイルに置く

[DOCUMENT_OUTLINE.md](../../../templates/DOCUMENT_OUTLINE.md)を自分のプロジェクトへコピーし、例えば `templates/operation-guide-outline.md` として保存してください。英語の文章には[英語版](../../../templates/DOCUMENT_OUTLINE.en.md)も使えます。

操作説明なら、次の構成から始められます。角括弧の中は、AIに書かせる内容の説明です。完成した本文では、その説明を実際の内容に置き換えます。

```markdown
# [操作の名前]

## 目的
[誰が、何をできるようになる説明かを書く。]

## 準備
[操作前に必要な画面、ファイル、設定を書く。準備が不要と確認できたら「事前準備は不要です」と書く。]

## 操作
[実行者、操作する画面、ボタンや入力値を順に書く。]

## 結果の確認
[どの画面や値を見れば成功と判断できるかを書く。]
```

この例では四つの見出しを必須にします。準備がないことと、準備が必要か分からないことは別です。分からない項目を空欄にしたり、見出しごと消したりしないように指定してください。

### 2. ひな型、資料、出力先を指定して頼む

今回の読者、説明する機能、事実を確認できる資料を依頼文に添えます。以下のパスは例なので、実在するファイルへ置き換えてください。

```text
設定を保存する操作説明を書いてください。
読者はこのアプリを初めて使う人です。
ひな型: templates/operation-guide-outline.md
事実を確認する資料: docs/specs/settings.md の「保存と読込」
出力先: docs/users/save-settings.md

まず、ひな型と指定した資料を読んでください。
見出しの名前と順番を保ち、角括弧の説明を資料に基づく本文へ置き換えてください。
操作では誰がどの画面で何を押すか、結果の確認では何を見れば成功かを書いてください。
事実が不足して完成できない場合は、先に不足した項目を質問してください。
下書きだけを求めた場合は、その箇所を「要確認: 確認したい事実」と残してください。
想像で操作や値を埋めないでください。
見出しの追加や削除が必要だと思ったら、本文を変える前に理由を伝えてください。
保存前に、必須見出しと順番、各項目の内容、ひな型外の追加を確認してください。
確認後、完成した本文を指定先へ保存してください。
要確認が残る下書きは、未完成と報告してください。
```

ファイルを読めないチャットでは、ひな型と必要な資料を添付するか、本文を貼り付けてください。その場合は「出力先へ保存」を「完成した本文を全文出力」に置き換えます。パスを書くだけでは、そのチャットにファイルの内容は渡りません。

同じプロジェクトで繰り返し使う場合は、例えば `AGENTS.md` に次の一文を置けます。自動で読まれない環境では、依頼文でこのファイルも読むよう伝えてください。

```text
操作説明を作成・更新するときは templates/operation-guide-outline.md を読み、
そこにある見出しと項目の内容に従ってください。対象読者と事実の資料は今回の依頼で指定します。
```

### 3. 項目が満たされているか確認させる

AIに次の四点を確認させ、あなたも操作や結果が資料と合うか確認してください。

| 確認項目 | 合格の例 | 修正が必要な例 |
| --- | --- | --- |
| 必須見出しと順番 | 目的→準備→操作→結果の確認がそろっている | 「結果の確認」がない |
| 項目の内容 | 操作に画面とボタン名、結果に確認する値がある | 「適切に操作する」だけで手順がない |
| 不明な事実 | 資料を確認するか、質問して解決した | 実在するか不明なボタン名を作った |
| ひな型外の追加 | 合意した項目だけがある | 指示していない長い概要や付録が増えた |

「要確認」が残るものは下書きです。必要な事実を渡して埋めさせるか、確認できる資料を指定するまで、完成とは扱わないでください。構成がそろっていても、事実の正しさや読みやすさまで保証されるわけではありません。説明の不足は[読者が理解できる説明に直す](読者が理解できる説明に直す.md)でも確認できます。

### 4. ひな型を増やしすぎない

見出しは、読者が目的を理解し、操作を実行し、結果を判断するために必要なものへ絞ってください。例えば日付だけ差し替える告知に「操作」「結果の確認」を加える必要はありません。

今回の用途で役割がない見出しは、執筆前に削除を決めます。資料が足りない必須項目は残してください。同じ見出しが毎回使われないなら、ひな型自体の見直しや用途別への分割を検討できます。機能名、読者、資料の場所は今回の依頼に書き、詳しい共通ルールは別の指示書への参照にすると、ひな型と `AGENTS.md` の肥大化を抑えられます。

## コンテキスト使用量が減る理由と限界

短い構成を再利用すると、見出しの欠落や順番の違いを毎回説明する会話を減らせます。AIには今回の構成と必要な事実だけを渡せるため、構成を推測させるために過去の完成文書を何本も読ませる必要も減ります。

ひな型の本文も入力として消費されます。長いひな型や大量の参考例を毎回渡すと、使用量が増えることがあります。事実を確認する資料は省略せず、構成の指示と修正のやり取りがどれだけ減ったかで効果を判断してください。このリポジトリでは削減量を実測していません。

## 補助ツール

- **エディターの見出し一覧:** 文書内の見出しを順に表示します。必須見出しの欠落や、予定外の見出しの追加を人が確認するために使えます。
- **Gitの差分表示:** 変更前後の文章を表示します。ひな型から見出しが削られた箇所や、指示していない説明が増えた箇所を探せます。

## この手法について

出力の構成と埋める箇所を先に示し、AIにその形で内容を生成させる手法を **Template Pattern** と言います。[Whiteほかの論文](https://arxiv.org/abs/2302.11382)で紹介されています。論文は、指定した形の前後に余分な文章が出る場合や、構成を制限することで有用な説明も落ちる場合を挙げています。

この文書の保存場所、不足した事実の扱い、完成後の確認手順は、プロジェクトで使うための具体例です。論文がコンテキスト使用量の削減を実証したという意味ではありません。
