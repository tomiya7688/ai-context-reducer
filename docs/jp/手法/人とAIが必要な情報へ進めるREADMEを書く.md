# 人とAIが必要な情報へ進めるREADMEを書く

READMEを読んでも使い始め方が分からない、AIへ変更を頼むたびに仕様や作業ルールの場所を説明し直す、といった場合は、READMEを入口として整理します。冒頭には用途と最初の試し方を短く書き、詳しい操作、仕様、開発手順へ案内します。

AIに作業を頼む人にも、どの資料を渡せばよいかが分かる見出しを用意してください。リンクを置いただけでAIが自動で読むとは限らないため、読む場所は依頼や指示ファイルでも伝えます。

## 何をREADMEに残すか決める

| 読む人の目的 | READMEに書くこと | 詳しく確認する場所の例 |
| --- | --- | --- |
| 何に使うか知る | 用途、対象、主な制限や公開状況 | 必要なら機能の説明 |
| 一度試す | 最初の操作と期待する結果 | `docs/getting-started.md` |
| 操作や仕様を調べる | 何が分かるかを添えたリンク | `docs/usage.md`、`docs/csv-format.md` |
| 質問や不具合報告をする | 実際に使っている窓口と案内 | `docs/support.md` や既存の問い合わせ先 |
| AIに変更を頼む | 作業ルール、関係する仕様、確認手順の場所 | `AGENTS.md`、`docs/development.md` |

これらは配置例です。既存の文書や窓口を使い、同じ情報のために別ファイルを増やす必要はありません。小さなプロジェクトなら、一つのREADMEに短くまとめても構いません。

同じ長い説明を何度も読んでいる、仕様のコピーが食い違う、初見の人が次のページを選べない場合に分けることを検討します。リンクをたどる手間の方が大きい短い説明は、その場に残してください。

## 使うときの手順

### 1. 読む人と、最初に試すことを決める

例えば「CSVは使ったことがあるが、このツールの操作は知らない人が、日付の整形を一回試せる」を目標にします。用途、対象、必要な環境、入力例、操作、期待結果を、既存の説明や実際の動作で確かめます。

存在しない起動コマンド、未対応の機能、使っていない問い合わせ窓口をAIに作らせないでください。不明な項目は要確認と残します。利用者向けなのか開発者向けなのかで、最初に案内する手順も変わります。

### 2. 詳細の置き場所を確かめ、短い案内を書く

次は架空のCSVツールの配置例です。既存の構成を、必ずこの形へ変えるという意味ではありません。

```text
README.md                  目的、試し方、次に読む場所
AGENTS.md                  AIに適用する作業ルールと参照先
docs/getting-started.md     必要な環境、導入と最初の操作
docs/usage.md               操作の詳しい説明
docs/csv-format.md          対応する日付とCSV形式の仕様
docs/development.md         開発と確認の手順
docs/support.md             問合せ先と報告に必要な情報
```

リポジトリ直下の `README.md` は、例えば次のように書けます。見本の説明とリンク先は、自分のプロジェクトで実在するものへ置き換えてください。末尾のリンク定義のパスは、上の架空の配置に対応しています。

```markdown
# CSV日付整形

CSVの日付を YYYY-MM-DD にそろえるツールです。
対応する入力は [CSV形式の仕様][format] を確認してください。

## 最初に試す

[導入と最初の操作][start] に沿って、見本のCSVを一つ処理してください。
見本の 2026/10/17 が 2026-10-17 になれば、最初の操作は完了です。

## 詳しい使い方と問い合わせ

- [操作の説明][usage]: 設定とエラーの対処を確認できます。
- [問い合わせ先][support]: 不具合の報告先と、添える情報を確認できます。

## AIに変更を頼むとき

作業を頼む際は、まず [作業ルール][rules] を読ませてください。
CSV形式の変更なら [形式の仕様][format]、確認方法は [開発手順][development] を渡してください。
別の作業では、関係する資料だけを追加してください。

[start]: docs/getting-started.md
[usage]: docs/usage.md
[format]: docs/csv-format.md
[support]: docs/support.md
[rules]: AGENTS.md
[development]: docs/development.md
```

「概要」「その他」だけでなく、「最初に試す」「AIに変更を頼むとき」のように、次の行動が分かる見出しにします。リンクも「こちら」だけにせず、何が分かるかを書きます。

同じプロジェクト内のリンクは、READMEから見た相対パスで書けます。`docs/csv-format.md` は、READMEと同じ場所にある `docs` フォルダー内のファイルです。別フォルダーの文書からリンクする場合は、その文書の場所を基準に直します。

詳しい仕様、操作、作業ルールは、それぞれの内容を確認できる文書に残します。READMEには短い目的と参照先を置き、仕様の全文を写しません。機能変更やファイル移動で案内が古くなったら、リンクと短い説明も更新します。

### 3. AIが読む指示から、必要な節と資料へ案内する

上のプロジェクトで `AGENTS.md` を使うなら、例えば次の短い案内を書きます。

```text
最初の作業では README.md の「AIに変更を頼むとき」を確認する。
CSVの日付形式を変える場合は docs/csv-format.md を読み、利用側への影響を確認する。
確認を行う場合は docs/development.md の、今回の変更に関係する手順を読む。
関係のない資料を、リンクされているという理由だけで一通り読まない。
既に確認した同じ版の指示書は、リンクの往復で読み直さない。
```

ここには詳しい仕様をコピーせず、読む条件と場所を置きます。既存のルールは保ち、案内を短く追加してください。どの指示ファイルが自動で読まれるかはAIの環境によって異なるため、設定や読込み記録で確認します。

自動では読まれない場合や、一度だけ頼む場合は、依頼で指定します。

```text
CSVの日付形式を変更したいです。まず AGENTS.md と、
README.md の「AIに変更を頼むとき」を読んでください。
そこから docs/csv-format.md と、今回の変更に対応する確認手順へ進んでください。
必要な利用側も確かめ、読んだ資料と選んだ理由を短く示してください。
READMEへ詳しい仕様をコピーしないでください。
```

ファイルを読めないチャットには、該当節、適用するルール、必要な仕様やコードを添付・貼り付けます。パスだけでは本文は渡りません。READMEの案内と仕様やコードが食い違えば、元の資料で現在の事実を確認させ、どこが古いか報告させます。

### 4. AIにREADMEを書き直させるときは、材料と範囲を渡す

```text
初めてこのツールを使う人が、一回試して結果を確かめられるREADMEにしてください。
読者はCSVを使ったことがありますが、このツールの操作は知りません。

既存README、導入・操作・仕様・開発の説明、問い合わせ先を確認してください。
用途、最初の操作、期待結果、詳しい説明、問い合わせへの入口を短く示してください。
AIに変更を頼む人には、作業ルールと変更内容に合う仕様・確認手順を案内してください。
詳細の全文はコピーせず、実在する相対リンクでつないでください。

不足した情報や未確認のコマンドは作らず、不足として報告してください。
既存の必須項目を保ち、見出しや範囲を変える必要があれば理由を示してください。
今回はREADMEの案と必要な案内リンクだけを変更し、実装や仕様は変えないでください。
最後に、確認した資料、リンク先、不足、未確認の操作を報告してください。
```

構成が毎回変わるなら、[見出しと順番を先に渡す方法](AIに文章の見出しと順番を渡して書かせる.md)も使えます。READMEの整理と、プロジェクト自体の設計変更を同時に頼む必要はありません。

### 5. あなたが案内先と実際の内容を確かめる

- 初見の人が、用途、最初の操作と期待結果、詳しい説明、問い合わせ先を見つけられるか確認します。
- 各リンクが存在するだけでなく、開いた先に約束した説明があるか確かめます。
- AIへ一つの作業を頼み、読んだルールや資料を、表示される作業記録や返答と照合します。
- 実行できなかった操作や読めなかった資料は未確認として残します。リンク検査だけで、操作の成功やAIの読込みまで確認済みにしません。

## なぜ探索と読込みを減らせるか

目的別の短い入口があれば、人は使い始め方や問い合わせ先を探し直さずに済みます。AIへは今回の節と必要な参照先を伝えられるため、無関係な操作説明や長い履歴を毎回渡す必要が減ります。詳細を一か所で保つと、同じ説明同士の食い違いを調べる手間も抑えられます。

リンク先を読む量や、案内を保つ手間は残ります。毎回すべてのリンク先を読ませれば、量は増える場合があります。READMEを短くしただけで使用量が減ったとは断定せず、必要な根拠を保ち、実際に読んだ範囲や記録できる使用量で比べてください。

## 補助ツール・機能

- **見出しから作る目次:** 読みたい節へ移動できます。長めのREADMEで入口を探すときに使えます。
- **Markdownの表示機能:** 見出しやリンクを記号で書く形式（Markdown）を、読者に見える形で確認できます。配布先や利用する環境で読めるか確認するときに使えます。
- **リンクの検査:** 存在しないリンク先を探します。移動後の案内漏れの発見に使えますが、説明内容や操作結果は別に確認します。

## この整理について

READMEから目的別に詳しい説明へ案内し、作業の指示から必要な場所を読ませる整理です。リンクを置くことと、AIへ読むよう伝えることを組み合わせます。GitHubは用途、利用開始、支援先、相対リンクを案内し、Googleも短い概要と利用方法・連絡先・関連文書への案内を挙げています。[GitHubの説明](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes)、[Googleの説明](https://google.github.io/styleguide/docguide/READMEs.html)。

学び始める説明、目的を達成する手順、仕様の参照、背景の説明を分ける整理は、[Diátaxis](https://diataxis.fr/)で紹介されています。これは文書を整理する考え方であり、本書の見本や依頼文の削減効果を測定したものではありません。
