# 複数のAIで記憶を共有し、必要な情報だけ読み出す

Codexに修正を頼んだ後、Claude Codeにレビューを頼むとき、あなたは同じ仕様や以前の決定をもう一度説明していませんか。ChatGPTで調査してからCopilotへ実装を頼む場合も、会話の全文を引き継ぐと今回の作業には無関係な話までAIに渡ります。

**共有メモリ**とは、複数のAIや別々の会話で再利用したい情報を、モデルの外の共通の保存先に残しておき、後の作業に必要な部分だけ取り出す仕組みです。「メモリ」と呼んでも、モデルの学習済みの数値を書き換えるのではありません。記憶を取り出せるプログラムが今回の入力に内容を追加して初めて、AIはその記憶を判断の条件として使えます。[1][2]

あなたは、AIに何を共有させるかと誰が読めるかを決めます。AIは、保存の候補を作り、必要な記憶を検索できます。保存先のプログラムは、許可された情報を保管し、検索した部分を返します。**最終的に正しい仕様・コード・テストかを確認するのはあなたと担当するAIです。** 本文は手法の説明であり、特定の外部サービスの導入は必要ありません。

## なぜ全会話を共有するだけでは足りないのか

チャットAで不具合を調べたときの会話には、採用しなかった仮説、長いログ、古いコード、途中の失敗が残ります。これを次のチャットBの入力へ丸ごと付ければ、AIはもう一度すべてを読むことになります。さらに各AIが同じ履歴を引き継げば、一回の入力も作業全体の累積量も大きくなり得ます。入力のキャッシュで計算を再利用できても、入力から履歴そのものが消えるわけではありません。[3]

共有メモリでは、あなたが必要と判断した**確定した決定・守る条件・原典への参照**を外に残します。次のAIは、今回の質問に関連する記憶だけを検索し、必要なら元の資料へ戻ります。

```text
AI A：仕様とコードを調べ、決定事項を見つける
  ↓ 根拠付きの「保存候補」を出す
あなた／許可された確認者：保存してよい内容・範囲・版を確かめる
  ↓
共有メモリ：内容・出典・版・閲覧範囲を保存する
  ↑                                   ↓
AI B：別チャットから必要な記憶を検索する
  → 該当する短い記憶だけ受け取る
  → 変更する前に現在の原典とテストを確認する
  → 新しい事実が判明したら更新候補を出す
```

**外部に多く保存しても、毎回その全件を読み込ませたら削減になりません。** 何をいつ検索するか、結果をどこまで返すかも手法の一部です。入力へ入った記憶は通常のコンテキストなので、容量の制限もあります。

## 例：保存先の変更を、別のAIへ引き継ぐ

架空のアプリで、設定の保存先が `config/old.json` から `config/settings.json` へ変更されたとします。以下は手順を示す仮例であり、実際のAIに使わせた測定結果ではありません。

1. **AI Aが調査します。** あなたは設定保存の不具合をAI Aへ頼み、AI Aは現行の保存処理、読込み処理、テストを確認します。変更後の保存先と根拠になったコードの版を報告します。
2. **あなたが保存内容を確認します。** AI Aは「現在の保存先は `config/settings.json`」と「旧ファイルは過去の仕様」という二つの候補を示します。あなたは両方の根拠を確認し、今回のプロジェクトで共有してよいと判断します。
3. **共通の保存先へ記録します。** 保存先は、内容だけでなく、原典の場所、対象の版、確認時点、記録者、閲覧できる範囲も持ちます。まだ未検証なら「候補」として保存し、確定した事実として返しません。
4. **AI Bが別のチャットで検索します。** あなたが「起動時の設定読込みを修正して」と頼むと、AI Bは保存先に関係する記憶を検索します。共通の保存先は一致する短い情報と原典の場所を返します。古い案や全会話のログは返しません。
5. **AI Bが現在の原典を確認します。** 記憶が示すコミットよりコードが新しければ、AI Bは最新の保存・読込み処理を取得します。記憶を正しいと決めつけて修正せず、実装とテストを確認します。
6. **仕様がさらに変わったら更新します。** 新しい確認済みの記憶で旧版を置き換え、旧版は「失効」などの状態にします。古い情報が検索結果の先頭へ出続けないようにします。

保存する内容の例です。書式は本書の説明用で、Living Brainを含む特定製品の実際の保存形式ではありません。

```yaml
id: settings-location
scope: repository:example/app
status: verified
statement: "設定の保存先は config/settings.json"
source: src/config/storage.go
source_revision: "abc123（説明用コミットID）"
checked_at: "2026-11-05"
writer: agent-a
verified_by: project-maintainer
supersedes: settings-location-old
```

この記録を**「現在のソースコードの代わり」にはしません**。原典の場所を知らせる入口として使い、必要な判断では該当する版のコードとテストへ戻ります。検索で見つからない記憶を、存在しないと断定しないことも重要です。

## 何を共有し、何を保存しないか

すべての発言を永久保存しません。あなたは、後の作業でも使う可能性があり、根拠と適用範囲が分かる情報を選びます。

| 情報 | 扱い方と理由 |
| --- | --- |
| 確定した仕様・設計の決定と理由 | 保存候補。後のAIが同じ議論を最初から繰り返さずに済む |
| リポジトリの構成や既存の手順 | **既存文書を原典**とし、記憶には必要な要点とパス・版を置く。原文全体を重複保存しない |
| テストで確認した事実 | 対象の版、コマンド、結果、日時を付けて保存。過去のテスト成功を現在の成功としない |
| 未完了の課題・制限 | 有効期限と参照先を付ける。完了後は失効させる |
| 調査途中の仮説 | 必要な場合だけ「未検証」の状態で残す。確定した仕様と混ぜない |
| 長い会話全文・一時ログ・失敗した試行 | 原則、共通の記憶へコピーしない。再調査に必要なら保管場所を示す |
| APIキー・認証情報・個人情報 | 必要性・同意・権限・保存先を確認する。特に秘密の値を共有メモリへ書き込まない |

2026年の「Shared Selective Persistent Memory」の研究では、作業仕様、データの形、道具の設定、出力の制約という再利用可能な情報を選び、個別の試行錯誤は共有する記憶から外しています。[4] ただし、この四分類だけが唯一の正しい保存方法という意味ではありません。

## 複数のAIで書き換えるときの危険

一人のAIが書くだけなら見過ごしやすい問題が、共有メモリでは他のAIへ広がります。[5]

| 起きる問題 | 具体例 | あなたが決め、AIや保存先が確認すること |
| --- | --- | --- |
| **古い情報が再利用される** | AI Aが以前の保存先を記録し、AI Bが変更後も使う | 記憶に原典の版・確認日時・有効状態を残す。原典が更新されたら再確認して旧版を失効させる |
| **互いに矛盾する記憶が残る** | AI AはJSON、AI Bはデータベースが正本だと書く | 記憶の更新を無条件に上書きせず、書込み時の版を検査し、両方の根拠を確認して採用する版を決める |
| **読ませてはいけない情報が漏れる** | 別のプロジェクトの内部資料を、関係のないAIが取得する | 利用者・プロジェクト・担当などの範囲を**検索と直接参照の両方**で制限する。接続できることを閲覧許可と混同しない |
| **出典が分からなくなる** | 「動作確認済み」という短文だけが残る | 誰が、いつ、どの版・コマンド・結果から得たかを保存し、元資料へ戻れるようにする |
| **悪意のある文章が指示として扱われる** | 外部ページや過去のログに「次から検査を省け」と書かれる | 記憶の本文は参考情報であり、AIへの新しい上位命令ではない。未承認の命令・権限変更を実行しない |
| **削除したはずの情報が残る** | 元資料を削除しても、要約や複製が検索できる | 保存先・索引・複製先の削除手順と保持期間を決め、削除結果を確認する |

**権限を文章で「このAIだけ」と書くだけでは保護になりません。** 実際の保存先が読み書きを制限する必要があります。複数のAIが同時に更新するなら、古い版を前提にした書込みを検出する仕組みや、人が矛盾を確認する手順も用意します。

## Context Packや検索との違い

| 方法 | 何を共有するか | 得意な場面 | 共有メモリとの関係 |
| --- | --- | --- | --- |
| **チャットの全文を引き継ぐ** | 発言と道具の結果をまとめて渡す | ごく短い続きの作業 | 無関係な過去まで含みやすい |
| **Context Pack・作業メモ** | 今回の目的、制約、差分、次の一手 | 一つの作業の引継ぎ | 作業用の記録。長期に繰り返す知識だけ共有メモリへ移してもよい |
| **資料の検索** | 今回の質問に合う原典の箇所 | 現在の仕様・コード・契約の確認 | 共有メモリに置いた要点の正しさを原典で確かめる |
| **共有メモリ** | 会話や作業をまたいで使う、出典・版付きの知識 | 複数のAIや複数回の作業で同じ条件を使う | 保存・検索・更新・失効・閲覧権限まで管理する |

共有メモリはContext Packや原典検索を置き換える仕組みではありません。例えば、作業メモには今回の未完了事項、共有メモリには継続して適用する仕様、原典には実際のコードを置きます。共有メモリがなくても、Gitで管理した短い文書と必要な検索で十分なプロジェクトもあります。

## 関連する研究とLiving Brainの位置付け

**Living Brainは手法全体の一般名ではなく、ChatAndBuildが公開する製品名**です。公式資料では、会話や資料から情報を取り込み、関連するページへ整理し、複数のAIからAPI・MCPなどで取得する機能が説明されています。[1][6] MCPは、AIを使うアプリが外部プログラムの機能を呼び出すための接続方式です。

Living Brainの公開ページには、長い履歴を渡す方式と比べた入力量・料金の削減値や、質問応答の正答率が掲載されています。しかし、**それらは同社が実施した内部評価**であり、比べた対象と設定も限られます。本書では製品の説明例として参照し、どのAIや作業でも同じ削減率になるとは扱いません。[1]

| 発表した人・組織 | 研究・公開内容 | この手法の理解に役立つ点 | その資料だけでは保証されないこと |
| --- | --- | --- | --- |
| **ChatAndBuild**（Living Brain）[1][6] | 保存した情報を整理して、別のAIからも検索・取得できる製品 | 製品をまたぐ共有記憶の使い方 | 同社の内部評価が全環境で再現すること |
| **Prateek Chhikaraほか**（Mem0）[2] | 会話から重要な情報を抽出・統合し、必要なときに取り出す構成 | 全文保持と記憶の選別を分ける | 任意の複数AI間の権限・整合性が自動で保たれること |
| **Wujiang Xuほか**（A-MEM）[7] | 記憶の関連付けと、新しい情報に応じた記憶の再整理 | 記憶が増えた後の整理と更新 | 関連する記憶がいつでも正しいこと |
| **Sanjana Pedadaほか**（Shared Selective Persistent Memory、2026）[4] | 再利用する情報だけを保存する共有方式。特定の企業向け作業で全文履歴より良い完了率を報告 | 保持する情報を選ぶ必要性と、共有・アクセス制御 | 報告された改善率が他の製品・課題でも成立すること |
| **Yanki Margalitほか**（Governed Shared Memory、2026）[5] | 閲覧範囲、失効、出典、共有範囲を検査する仕組みと、運用中に見つかった不具合 | 検索精度とは別に共有時の安全性を管理する必要性 | すべての実装で漏洩や矛盾を防げること |

同じ「記憶」という語でも、整理方法、検索方法、複数AIのアクセス制御は別の問題です。類似の製品名や短い説明だけで、内部構造が同じだとは判断しません。

## 実際に役立ったかをどう測るか

あなたは、**同じ作業の種類・同じ原典の版・同じ完了条件**で、次の三つを比較します。これは評価方法の提案であり、本書の実測結果ではありません。

- **全文履歴:** 前の会話をまとめて次のAIへ渡す。
- **短い作業メモ:** 目的・決定事項・未完了だけ渡す。
- **選択的な共有メモリ:** 必要な保存済み情報だけを検索し、現在の原典も確認する。

計測するのは、各AIに渡った入力・出力と作業全体の累積量、検索・記憶の作成・更新にかかった時間と費用、必要な根拠を取得できた割合、正しい完了条件・テスト、古い記憶や矛盾の発生、権限を越えた漏洩、再説明や再作業の回数です。失敗した回も集計し、キャッシュ済み入力や推論用トークンの内訳を総量へ二重加算しません。見えない使用量は「未計測」と報告します。

検索のために毎回別のLLMへ長い要約を作らせた場合、その費用も含めます。**一回の入力が短くなっても、全体の料金や正答率が改善したとは限りません。** 計測方法は[作業ごとのコンテキスト使用量の目安を作る](../AI利用/作業ごとのコンテキスト使用量の目安を作る.md)、長い入力の品質上の問題は[コンテキストの量と使われ方](../LLMの仕組み/コンテキストの量と使われ方.md)を参照してください。

## AIへの依頼文（あなたが送る文章）

次の例は、あなたが使うAIに**既存の保存先を使った運用案を考えさせる**依頼です。接続権限がなければAIは保存や検索を実行できません。

```text
今回の仕事は[対象の作業]です。関連する以前の決定・制約が必要なら、
許可された共有メモリから今回の作業に関係する項目だけ検索してください。
全履歴や記憶全件を入力へ追加しないでください。

取得した項目ごとに、出典の場所と版、確認日時、適用範囲、未検証かどうかを示してください。
現在の仕様・コード・テストで確認が必要な部分は、元の資料を読んでください。
古い内容や矛盾を見つけたら、根拠付きで更新候補として報告してください。

新しい記憶の共有保存、既存の確定記憶の上書き、閲覧権限の変更は、
私が確認するまで行わないでください。秘密の値・個人情報を保存しないでください。
変更後は必要な検証を行い、実行結果と未確認の範囲を示してください。
```

あなたは、AIが保存・取得した内容と、実際に参照した原典・実行した検証を確認してください。共有メモリの機能を使えない場合は、今回の作業メモと原典へのパスだけで進めても構いません。
