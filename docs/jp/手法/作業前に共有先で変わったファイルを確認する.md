# 作業前に共有先で変わったファイルを確認する

GitHubなど、複数の人やAIが同じプロジェクトを更新する場所があります。手元にあるファイルは、そこにある最新の内容とは限りません。

> **作業を始める前に、共有先の変更情報を取得し、変わったファイルを確認します。関係する変更を読んでから、修正に入ります。**

変更内容を調べる操作と、手元のファイルへ反映する操作は別です。確認しただけでは、手元のファイルは書き換わりません。内容を見て、必要だと判断した変更だけを反映します。

## 例：別の人が日付処理を直していた

CSVの日付の読み込み不具合を直そうとしている間に、別の人も日付処理やそのテストを変更したとします。修正を始める前に、共有場所の更新情報を取得し、日付処理とテストが変わったか調べます。変わっていれば、その変更内容を読んでから修正します。無関係な画面の変更は読む必要がありません。

## Gitを使う場合

### 1. 共有先の変更を確認する

まず、手元に作業中の変更がないか確認します。

```sh
git status --short
```

何も表示されなければ、手元に記録前の変更はありません。表示があれば、その変更を消したり上書きしたりせず、残したまま確認を続けます。

次に共有先の最新情報を取得します。

```sh
git fetch
```

これは共有先の変更情報を手元に取得するだけで、作業中のファイルは書き換えません。取得した情報から、変わったファイルの一覧を見ます。

```sh
git diff --name-status 'HEAD...@{upstream}'
```

比べる場所が設定されていないという表示が出たら、ここで止まり、どの共有場所と比べるか確認します。名前を推測して続けてはいけません。関係するファイルが見つかったら、そのファイルの変更内容を読みます。

```sh
git diff 'HEAD...@{upstream}' -- path/to/file
```

`path/to/file` は一覧に出たファイル名に置き換えます。変更内容が短い一覧だけでは分からない場合は、ファイル全体や関連するテストも確認します。

### 2. 確認した変更を手元へ反映する

確認した変更を手元にも反映すると決めたら、まず未保存の作業が残っていないか確認します。

```sh
git status --short
```

何か表示されたら、先にその作業を保存してから進めます。自分の作業を保存できない場合は、反映を止めます。

未保存の作業がなく、共有先の更新を今の作業の続きとして反映できる場合は、次のコマンドを使います。

```sh
git merge --ff-only '@{upstream}'
```

このコマンドは、共有先の更新をそのまま続きとして反映できる場合だけ進みます。手元と共有先に別々の変更がある場合は自動で混ぜず、どちらをどう合わせるか決めてから作業します。反映すべきか分からない場合も、勝手に実行せず確認を続けます。

## 最初に見る情報

共有先から新しい変更を取得した後は、まず変更の概要を見ます。概要には、更新の短い説明、変更されたファイル、変更量、必要なら短い差分の抜粋を含められます。差分とは、変更の前後で追加・削除された行の表示です。概要で影響が分かれば、関係する差分と直接の依存先だけを読みます。変更の意図や結果が分からないときは、対象ファイル全体、設計資料、テストへ広げます。短い概要だけで判断を確定しないでください。

差分の抜粋を短くした場合は、省略した範囲があることを明記し、必要なときに元の差分を確認できるようにします。短い表示は変更箇所を見つける入口であり、完全なレビューの代わりにはなりません。

## 毎回行うこと

- 作業を始める前に共有先の変更情報を取得する
- 変わったファイルを調べ、今の作業に関係する変更内容を読む
- 内容を確認した後で、必要な変更だけ手元へ反映する
- 手元に未保存の作業がある、または手元と共有先に別々の変更がある場合は、自動で上書き・混合しない

Git以外の仕組みを使う場合も、共有場所の変更を確認する操作と、手元のファイルへ反映する操作を分けます。

## AIへの指示例

```text
作業を始める前に、共有先の変更情報を取得してください。
変わったファイルのうち、今回の作業に関係するものだけを開いて内容を確認してください。
手元の未保存変更は上書きしないでください。共有先の変更を手元へ反映するのは、変更内容と未保存の作業があるかを確認した後にしてください。
どの共有場所と比べるか分からない、手元と共有先に別々の変更がある、または上書きのおそれがある場合は、手元への反映を止めて、未保存の作業と変更内容を報告してください。
```

## なぜ読む量が減るのか

変更されたファイル名を先に見て、今回関係する変更内容だけを読みます。共有先の変更を全部読み直したり、手元の変更を誤って失ったりする危険を減らせます。

## 用語

Gitは、複数の人の変更を記録して共有する仕組みです。この文書でいう「共有先」は、GitHubなど、変更を共有している場所です。`fetch` は共有先の変更情報を手元に取得する操作で、作業中のファイルは書き換えません。`merge` は取得して確認した変更を手元のファイルへ反映する操作です。

- **Remote Delta / delta-first review**: 前回確認した状態から共有先で変わった箇所を先に見る方法を、このように呼びます。

## 補助ツール

- 必要なら、[`remote-delta`](../../../tools/common/medium/remote-delta/README.md)が共有先との差分を要約します。要約だけで判断せず、関係する差分は元の内容も確認してください。
