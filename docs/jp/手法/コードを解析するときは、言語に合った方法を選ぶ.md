# コードを解析するときは、言語に合った方法を選ぶ

AIにコードの調査を頼むときは、使っている言語だけで調べ方を決めず、「何を知りたいか」に合わせて確認の深さを選びます。まず簡単な方法を使い、答えが出ない場合や正しさの確認が必要な場合に、次の段階へ進みます。

## 知りたいことに合わせて選ぶ

| 知りたいこと | まず使う方法 | それだけでは足りない場合 |
| --- | --- | --- |
| ファイルや処理がどこにあるか | ファイル名や処理名を検索する | 関連する言葉や呼び出し元も検索する |
| 変更した処理がどこから使われているか | 関数やファイルのつながりを調べる | 実際のコードと呼び出し元を開いて確かめる |
| 使っている言語や設定で書き方が正しいか | その言語に対応した構文確認を使う | プロジェクトの設定を使うビルドや型の確認を行う |
| 実行すると期待した動きになるか | 関連するテストを実行する | テストで再現できない場合は、アプリを実行して確かめる |

たとえば、処理の場所を探すだけなら検索で足ります。型の間違いやプロジェクトの設定を含めて確かめるには、対象の言語や設定を扱える確認方法が必要です。利用者に見える動作を確かめるなら、コードを調べるだけでなくテストやアプリの実行まで進みます。

## 使える環境に合わせる

すでに使える検索機能、エディター、コンパイラー、テストを優先します。コンパイラーは、プログラムを実行できる形に変換し、書き方や型の問題を報告する道具です。対応する道具がない場合は、検索などで分かる範囲を調べ、実行やビルドを確認できなかったことを明記します。今回の作業のためだけに大きな開発環境を追加する前に、確認したい内容と導入・保守の手間を比べてください。

軽い解析は実行環境がなくても使えることがありますが、場所の候補を示すだけで、動作・型・ビルドの正しさは確かめません。深い解析ほど常に良いわけではありません。必要な根拠が得られたら止め、結果を全件AIに渡さないようにします。小さなプロジェクトで対象とテストが分かっているなら、専用の解析を挟まず原文を確認します。

確認結果は、AIに渡す前に必要な範囲へ絞ります。成功した全ファイルの一覧や長いログではなく、今回の変更に関係する問題箇所、テスト結果、未確認の条件を伝えます。

## AIへの指示例

```text
まず、今回知りたいことに合う一番簡単な方法で調べてください。
場所を探すだけなら検索し、処理のつながりを知りたい場合は呼び出し元を確認してください。
書き方や型の正しさは利用できる言語別の確認方法で調べ、動作の正しさは関連テストや実行で確かめてください。
使える確認方法がない場合は、推測で成功とせず、分かったことと未確認のことを報告してください。
結果は変更に関係する箇所だけに絞ってください。
```

## なぜ読む量が減るのか

質問に答えるだけの検索で済むときに、プロジェクト全体の解析や長いビルド結果までAIに渡さずに済みます。検索だけで正しさを確認できない場合は、コードのつながり、言語別の確認、実行へ順に進むので、必要なテストや動作確認を省かずに情報を絞れます。

## 補助ツール

- 必要なら、[`language-setup`](../../../tools/common/small/language-setup/README.md)がプロジェクトの言語と利用できる実行環境を調べ、実行する候補を示します。
- 必要なら、[`language-run`](../../../tools/common/small/language-run/README.md)が対応する軽量解析を実行し、結果をファイルに保存します。結果は全件ではなく、今回の問いに必要な候補だけをAIに渡してください。

## 用語

- **lightweight search / dependency analysis / language-specific analysis**: それぞれ、名前などで場所を探す軽い解析、ファイル間の参照や依存関係の解析、言語ごとのコンパイラーなどを使う検査を指します。
- **構文確認**: プログラムの書き方に明らかな間違いがないかを調べることです。実行時の動作までは分かりません。
- **型の確認**: 数値や文字など、値の種類が処理の受け渡しで合っているかを調べることです。
- **コンパイラー**: プログラムを実行できる形に変換し、書き方や型の問題を報告する道具です。
