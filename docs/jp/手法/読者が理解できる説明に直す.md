# 読者が理解できる説明に直す

AIの説明を読んで「それは何を指すのか」「誰がやるのか」「結局どうすればよいのか」と聞き返すことが続くなら、書かせる前に読者と目的を伝え、返す前に説明の不足を確認させます。

たとえば「設定を適切に処理します」だけでは、設定を保存するのか、読み込むのか、利用者が操作するのか分かりません。「設定画面で『保存』を押すと、アプリが入力した値を設定ファイルへ書き込みます」なら、操作する人とアプリの動きが分かります。以下の操作やファイル名は、架空のアプリを使った例です。

## 使う場面を決める

- **初めて使う人向けの説明書**: 操作する場所、操作の順番、成功したときの表示が分かるか確認させます。
- **開発者向けの設計説明**: どの処理が何を担当するか、なぜその構成にしたか、守る条件が分かるか確認させます。
- **作業報告**: 何を変え、何を確かめ、何が未確認かを区別して書かせます。

読者が専門家で、用語の意味を共有している場合は、既知の用語を毎回説明し直す必要はありません。意味を追える文章まで全文を書き直させると、確認する差分も増えます。読者が理解や操作に困る文・段落を対象にしてください。

## 1. 完成した文章を誰が読むか伝える

依頼文に、次の3点を書きます。

| 決めること | 設定の保存方法を説明する場合 |
|---|---|
| 読む人 | このアプリを初めて使う利用者 |
| すでに知っていること・説明が必要なこと | 画面のボタンを押せる。設定ファイルや開発用語は知らない |
| 読んだ後にしてほしいこと | 自分で設定を保存し、保存できたか確かめる |

```text
読む人: このアプリを初めて使う利用者。
前提知識: 画面の操作はできるが、開発用語は知らない。
読後の目的: 設定を保存し、保存できたか自分で確かめられる。
根拠にする資料: [設定画面の仕様書のパス、または添付した資料]

この読者に必要な言葉の説明と操作手順を含めて、設定の保存方法を書いてください。
操作や結果は、指定した資料で確認できる内容を使ってください。
資料にない動作や条件を、推測で補わないでください。
```

読者によって説明する内容が大きく変わるのに、誰が読むか決まっていない場合は、AIに先に質問させます。短い下書きで、仮定しても修正が容易な場合は、「初めて使う利用者向けとして書きます」のように仮定を示させ、依頼者がその読者でよいか確認します。

## 2. 曖昧な対象と実行者を確認させる

AIに、文章と必要な仕様書などを渡し、次の点を分けて確認させます。

| 確認する点 | 問題を見つけるための問い |
|---|---|
| 指している対象 | 「これ」「それ」「この処理」は、本文のどの名前を指すか |
| 誰が行うか | 利用者が操作するのか、AIにさせるのか、アプリが自動で行うのか |
| 言葉の意味 | この読者が知らない略語や専門語を、説明の代わりに使っていないか |
| 操作と結果 | 何を入力・操作し、何が起きたら成功か分かるか |
| 理由と条件 | 判断に必要な理由、前提、例外が抜けていないか |

同じものを段落ごとに「設定情報」「データ」「入力」と呼ぶと、別のものに見えることがあります。対象が同じなら呼び名をそろえさせます。逆に、直前の「保存ボタン」を「このボタン」で受けていて迷わない場合は、具体名を毎文繰り返す必要はありません。

前の会話だけに書かれた対象名や条件も、文章の読者に必要なら本文へ補います。文章の意味を保ち、周囲の文章に頼らず読める形へ直す考え方は、[Choiらの論文](https://aclanthology.org/2021.tacl-1.27/)でも扱われています。研究上の名称は末尾に記します。

## 3. 足りなさそうな情報が、本当に抜けているか確かめさせる

AIに、まず「初めて読む人が追加で聞きそうなこと」を挙げさせます。その後、その答えが本文、または本文から案内された読者が開ける参照先に書かれているか確認させます。

AIだけに渡した仕様書に答えがあっても、読者向けの説明は不足したままです。仕様書で正しさを確かめたうえで、必要な答えを本文へ補うか、読者が開ける参照先を示します。操作に不可欠な手順や成功の表示は、操作を説明する箇所に書きます。

たとえば「保存できたか、どこで判断するのか」という疑問が出ても、次の段落に「保存が完了すると『保存しました』と表示される」とあれば、追加説明は不要です。操作する場所の説明から離れすぎて見つけにくいなら、案内を近くへ移す方法もあります。

本文にない答えを補う前に、指定した仕様書や実際の操作で確かめさせます。確かめられない内容は、説明に作り足さず、依頼者へ確認する項目として残します。

誰・何・なぜ・どうやって・結果・例外の全項目を、毎文に追加させる必要はありません。読者が目的の操作や判断を行うために必要な情報だけを補います。

## 4. 問題のある文・段落だけ直させる

AIに、問題がある箇所、読者が困る理由、根拠の場所を示させてから、その文・段落だけを修正させます。修正後は、元の文章にあった条件や意味が変わっていないか確認させます。

最後に、指定した読者として読み直させ、目的の操作や判断に必要な情報がそろっているか確認させます。操作説明なら、人が実際に手順を試す確認も役立ちます。AIが「分かりやすくなった」と報告したことだけで、実際の利用者が理解できたと判断しないでください。

## 普段は、説明を作ったAIに短く確認させる

前の4段階は、通常は説明を作ったAIに続けて行わせます。問題候補を見つけた後、本文や読者が開ける案内先に答えがあるか確かめ、不足が確認できた箇所だけ直させてください。

確認結果を受け取る場合は、次のように問題のある箇所だけを短く報告させます。

```text
「設定を確認します」：確認するのが利用者かアプリか分からない。
起動仕様に合わせて「起動時にアプリが設定ファイルを確認します」に修正。
「保存先を選ぶ場所」：本文と案内先に説明がなく、根拠資料でも確認できない。
確認が必要：保存先はどの画面で選べるか。
```

各文の全項目に合格・不合格を付けたり、確認のために全文を繰り返したりする必要はありません。問題がなかった箇所の言い換えもさせないでください。

出力は依頼時に次のどちらかを指定します。

- **確認結果を見たいとき**：問題の位置・理由・修正案と、確認が必要な点だけを返させます。全文や同じ内容の別形式を重ねて出す必要はありません。
- **完成した文章が欲しいとき**：確認の長い記録を省き、修正後の全文だけを返させます。変更していない部分も含め、依頼した文章は省略させません。根拠を確認できず完成を妨げる不足があれば、その質問を短く添えさせます。

## 重要な説明では、別の会話で読者役に確認させる

次のいずれかに当たる場合は、説明を書いた会話の外でも確認すると、書き手が知っていることを省略していないか見つけやすくなります。

- 初めて使う人へ公開する導入・操作説明。
- 同じ説明について、何度も聞き返されている。
- 書き手と読者の前提知識が大きく違う。
- 誤解すると、実装を間違えたり操作を取り違えたりする。

新しい会話を開き、読者・前提知識・読後の目的と、完成した説明を渡してください。参照先があるなら、読者が開けるものだけを渡します。書き手だけが知っている過去の会話や内部仕様は渡さず、次のように頼みます。

```text
読む人：[想定読者]
前提知識：[知っていること]
読後の目的：[できるようになってほしいこと]

次の説明と、そこから案内された読者が開ける資料だけを読んでください。
目的を達成するために追加で知る必要があることを、箇所と質問だけで返してください。
答えを推測したり、説明全文を書き直したりしないでください。
[完成した説明]
```

返ってきた質問を、説明を書いたAIへ渡します。本文ですでに答えている質問は追加せず、実際の不足だけを根拠資料で確認して直させてください。根拠が分からない点は利用者への確認事項として残します。

これは読者の理解を試す追加の確認です。別の会話でも本文を読み直すため、その分の入力と出力が増えます。短い内部メモや読者の知識がそろっている説明では、まず普段の確認を使ってください。別のAIが理解できても、人が操作できることまで確認した結果にはなりません。

## 7種類の修正例

以下は、架空のアプリとAIへの調査依頼を使った説明用の例です。アプリには設定画面があり、ファイルを選んで「読み込み」を押すとアプリが設定を読み込み、値を画面へ表示します。保存先を選んで「保存」を押すと設定が保存され、「保存しました」と表示される、という前提にしています。実際の文書を直すときは、自分のプロジェクトの仕様や動作で事実を確認してください。

### 1. 「これ」の参照先が分からない

- **修正前**：「アプリはこれを読み込み、その後これを表示します。」
- **読者が確定できないこと**：読み込む対象と、表示する対象は何か。
- **修正後**：「アプリは選択した設定ファイルを読み込み、その後設定値を画面へ表示します。」
- **直した箇所**：二つの「これ」を、それぞれの対象名に置き換えました。

### 2. 誰が行うか分からない

- **修正前**：「利用者が設定ファイルを選び、『読み込み』を押します。そのファイルを読み込み、設定値を表示します。」
- **読者が確定できないこと**：後半の読み込みと表示も利用者が行うのか。
- **修正後**：「利用者が設定ファイルを選び、『読み込み』を押します。アプリがそのファイルを読み込み、設定値を表示します。」
- **直した箇所**：実行者が変わる二文目に「アプリが」を補いました。対象が分かる「そのファイル」は残しています。

### 3. 英単語の列挙では動作が分からない

- **修正前**：「AIの調査では routing / scope / evidence / fallback を使います。」
- **読者が確定できないこと**：AIに何を渡し、どこまで調べさせるのか。答えが見つからなければどうするのか。
- **修正後**：「AIに最初に読む資料と調べる範囲を伝え、資料のどの記述を根拠にしたか返させます。その範囲で答えが見つからなければ、次に読む資料を選ばせます。」
- **直した箇所**：英単語の列挙を、利用者の指示とAIにさせる動作へ置き換えました。

### 4. 抽象的な動詞だけで操作が分からない

- **修正前**：「設定を適切に処理してください。」
- **読者が確定できないこと**：読者が実際に何を操作すればよいか。
- **修正後**：「設定画面で保存先を選び、『保存』を押してください。」
- **直した箇所**：「適切に処理」を、操作する場所と操作内容へ置き換えました。

### 5. 使う場面と必要な入力が抜けている

- **修正前**：「『読み込み』を押してください。」
- **読者が確定できないこと**：いつ押すのか、どのファイルを対象にするのか。
- **修正後**：「ファイルに保存した設定を使うときは、設定画面でそのファイルを選び、『読み込み』を押してください。」
- **直した箇所**：元の操作の前に、使う場面とファイル選択を補いました。

### 6. 成功したか判断できない

- **修正前**：「設定画面で保存先を選び、『保存』を押してください。」
- **読者が確定できないこと**：何を見れば保存が終わったと判断できるか。
- **修正後**：「設定画面で保存先を選び、『保存』を押してください。『保存しました』と表示されたら完了です。」
- **直した箇所**：操作文は変えず、成功の表示を一文だけ補いました。

### 7. 具体名を足しすぎて同じ説明を繰り返している

- **修正前**：「利用者は設定画面の保存ボタンを押します。利用者が設定画面の保存ボタンを押すと、アプリは設定画面の設定値を保存します。」
- **読者が確定できないこと**：対象や実行者の不足はありません。この例は、同じ場所とボタン名を繰り返して読みにくくなっています。
- **修正後**：「設定画面で保存ボタンを押してください。アプリが入力した設定値を保存します。」
- **直した箇所**：繰り返している対象名を省き、読者への操作指示とアプリの動作説明を分けました。動作や条件は変えていません。

## 修正前後で聞き返しが減ったか確かめる

文章が長くなったことだけでは、説明が改善したか分かりません。読者と読後の目的を固定し、説明だけでは答えを決められない質問が減ったかを比べてください。

### 1. 比べる文章と読者をそろえる

同じ内容の修正前・修正後を保存し、読者の前提知識と目的を決めます。たとえば「アプリを初めて使う人が、設定を保存して完了を判断できる」です。根拠資料を使って、修正後の操作や条件が正しいことも別に確認します。

確認用の文章は `docs/explanation-check/before.md` と `docs/explanation-check/after.md`、読者・目的・結果は `docs/explanation-check/results.md` に置くと、AIに渡す対象と記録場所を指定できます。単発なら添付や依頼文に貼るだけでも構いません。確認が終わり、記録が不要になったファイルは残し続ける必要はありません。

### 2. 説明だけでは答えられない質問を集める

最初は自分で本文を読み、次の質問に答えがあるか確認する方法で始められます。別の人に読んでもらう場合も、想定読者の前提知識をそろえます。

- 何を指しているか。
- 誰が実行するか。
- その言葉は何を意味するか。
- 具体的に何をするか。
- いつ、どの入力に対して使うか。
- 何を確認できれば完了か。

目的の達成に必要な質問だけを対象にします。同じことを聞く質問は一つにまとめ、本文や読者が開ける案内先に答えがあるものは数えません。修正前で見つけた質問を修正後でも確認し、修正後に新しく生じた疑問も加えます。

AIに確認させる場合は、[別の会話での読者確認](#重要な説明では別の会話で読者役に確認させる)と同じ渡し方を使います。修正前と修正後は別の新しい会話へ渡し、片方の文章や書き手の過去の会話をもう片方へ渡さないでください。利用者が両方の質問をまとめ、各文章から答えが取れるか確認します。

```text
対象：[before.md または after.md のパス、または添付した文章]
読む人：[想定読者]
前提知識：[知っていること]
読後の目的：[できるようになってほしいこと]

対象の文章と、本文から案内された読者が開ける資料だけを確認してください。
目的を達成するため、追加で聞かないと答えを決められないことを
「文章の箇所 / 質問」の形で返してください。
本文に答えがあるものや同じ質問は省き、答えは推測しないでください。
質問がなければ「追加質問なし」と返してください。
```

### 3. 残った質問と実際のやり直しを記録する

利用者が質問を確認し、修正前・修正後の両方について、どの箇所に答えがあるか、または不足しているかを記録します。たとえば上の例6では、修正前に「保存完了の表示は何か」が残り、修正後には「保存しました」という答えがあります。これは説明用の例で、AIや利用者を使った実測結果ではありません。

`results.md` に、次の表をケースごとに記入できます。空欄や未計測はゼロとして扱わないでください。

| 記録すること | 修正前 | 修正後 |
|---|---|---|
| 確認日時・確認者、AIなら使ったモデルと設定 | [記入] | [記入] |
| 追加質問が必要だった内容と数 | [記入] | [記入] |
| 本文や案内先に見つかった答えの箇所 | [記入] | [記入] |
| 実際に同じ内容を説明し直した回数 | [未計測なら未計測] | [未計測なら未計測] |
| 文章の修正を頼んだ往復の回数 | [未計測なら未計測] | [未計測なら未計測] |
| 誤った説明・必要な操作や条件の抜け | [記入] | [記入] |

追加質問の候補数と、実際に会話で聞き返された回数は別です。AIの候補だけを使った確認は、読者が実際に理解したことや、再説明が減った実測結果として扱わないでください。質問が減っても、間違った操作や条件を加えていたら改善したと判定しません。

### 4. 読む量の削減は、測れた範囲だけ述べる

最初の説明に対象名や操作を補うと、一回の出力は長くなる場合があります。狙いは、意味不足による後の質問・再説明・修正を減らすことです。読者が知っている言葉が違えば、必要な説明量も変わります。

追加質問だけを比べた場合は「この読者と例では、説明だけで答えられない質問が減った」と述べます。実際の会話を記録した場合だけ、再説明や修正の往復が減ったかを述べてください。

トークン数を取得できる環境なら、最初の依頼から完成までの入力・出力と、追加の確認に使った分を含めて比較します。同じモデル・設定・作業条件で測り、一回の出力だけを会話全体の削減量として扱わないでください。トークン未計測なら「総トークンが減った」「何％削減した」「必ず減る」とは書きません。数例の結果を、すべての読者や作業へ当てはめることも避けてください。

## 一度の依頼で使う場合

[短い確認手順のひな型](../../../templates/WRITING_GUIDE.md)を添付するか、AIが読める場所へ保存してパスを指定します。今回だけの条件は次の依頼へ記入してください。

```text
添付した確認手順（または [保存した手順のパス]）に従って説明を確認してください。
対象：[説明文または文書のパス]
読む人：[想定読者]
前提知識：[知っていること、説明が必要なこと]
読後の目的：[理解・判断・実行してほしいこと]
根拠：[仕様書、実際の操作結果など]
出力：[問題箇所だけの確認結果 / 修正後の全文]
```

## 何度も使う場合の置き場所

[ひな型](../../../templates/WRITING_GUIDE.md)をプロジェクト内の `docs/writing-guide.md` へコピーし、共通の読者が決まっていれば追記します。文書ごとに読者が異なるなら、その文書の冒頭や今回の依頼に読者と目的を指定してください。

利用中のAIが自動で読む指示ファイルに、この手順を使う場面と参照先を書きます。たとえば `AGENTS.md` に対応しているAIなら、リポジトリ直下のファイルへ次のように書けます。

```text
説明書・設計説明・作業報告を書くときは、docs/writing-guide.mdを読んでください。
今回の文章の読者と目的を確認し、説明の不足がある文・段落だけを直してください。
```

自動読込の設定がない場合は、毎回の依頼で `docs/writing-guide.md` を読むよう指定します。共通手順の全文を複数の指示ファイルへコピーせず、一か所を更新すれば済む形にしてください。

## なぜ会話で読む量を減らせるのか

対象や操作が分かる説明を最初に返せると、「それは何か」「誰が行うか」という聞き返しと再説明を減らせる可能性があります。会話の続きをAIへ渡すときに、同じ説明や修正指示を何度も含めずに済みます。問題のない段落を再生成しなければ、読み比べる修正案も増やしません。

確認や補足で最初の依頼と回答が長くなることもあります。毎回全文を別のAIに検査させると、追加の読み込みも必要です。実際に聞き返しが減ったか、読者が操作や判断を行えたかを見て、必要な確認だけ残してください。トークン数を測っていない場合は、コンテキスト使用量が減ったと断定しません。

## 補助ツール

- [doc-duplicate-hints](../../../tools/common/medium/doc-duplicate-hints/README.md) — 文書の重複箇所を候補として示します。補足を書き足した結果、同じ説明を複数箇所へ置いていないか探すときに使えます。説明が分かりやすいかは判定しません。

## この手法について

文章の意味を保ちながら、周囲の文章にある対象名や必要な条件を補い、その文章だけでも理解できる形へ直すことを、Choiらは **Decontextualization（文脈独立化）** と呼んでいます。[1]

この文書では、その考え方を参照して対象名や条件の不足を確認し、読者の指定・不足の再確認・問題箇所だけの修正を組み合わせています。ここにある依頼例の効果や、会話全体のトークン削減率を、同論文が検証したわけではありません。

別の読者が説明を受け取って作業を続けられるか、という観点は [Westらの論文](https://aclanthology.org/2026.eacl-long.386/)でも扱われています。[2] 同論文の **Tandem Training** は、強いモデルの学習中に弱いモデルへ部分的に生成を引き継がせ、正しい答えへ続けられるようにする学習手法です。本書の別会話での読者確認は、その観点を参考にした利用手順であり、この学習手法を実行するものではありません。
