# AIに既存コードを調べさせ、似た役割の追加を防ぐ

設定ファイルを読む `readSettingsFile` があるのに、AIが `SettingsLoader` や `loadConfigData` を追加し、同じ読み込み処理が増えることがあります。名前の書式をそろえても、同じ仕事をする部品が増える問題は解決しません。

関数は呼び出せる処理のまとまり、クラスは処理や状態をまとめる単位、変数は値を名前で扱うためのものです。

新しいコードを書かせる前に、必要な仕事を言葉にし、それを既に担当する関数・クラス・変数を探させます。見つけた部品が今回の条件に合うかを調べてから、そのまま使う、広げる、新しく作る、のどれにするか決めさせてください。

## 使う場面と判断基準

- 既存機能へ画面やコマンドを追加するとき、同じ役割の関数やクラスが繰り返し増えるときに使えます。
- 名前を探すだけでは見つからない場合は、入出力、扱うデータ、呼び出す機能、関連するテストも手掛かりにします。
- 同じ形のコードでも、使う条件や変わる理由が違えば、別々に保つ方がよい場合があります。重複を減らすことだけを目的に、一つの部品へまとめないでください。
- 一度だけの小さな変更なら、候補と判断を依頼への返答に短く示させれば足ります。後で再開する作業だけ、判断メモを保存してください。

## 使うときの手順

### 1. 名前より先に、追加したい仕事と条件を伝える

例えば「設定を読むクラスを作って」ではなく、次を伝えます。

```text
コマンドから設定ファイルを読み、設定の内容を表示できるようにしてください。
ファイル形式は既存の画面と同じJSONです。
不正なファイルを読んだときの扱いと、画面からの読み込み動作は変えないでください。
まず既存の読み込み処理を調べ、今回使えるかを判断してください。
今回の範囲はコマンド側と、必要な共通処理・対応テストです。
```

「何を受け取り、何を返すか」「失敗時にどうするか」「何を変えないか」が分かれば、名前が違っても同じ仕事の候補を探せます。ファイル形式や必須条件は、プロジェクトの仕様で確認した内容を渡してください。

### 2. 候補の定義、使う側、テストを調べさせる

以下は架空のプロジェクトの例です。パスは自分のプロジェクトにあるものへ置き換えてください。

| 探す手掛かり | 調べさせる場所 | 分かること |
| --- | --- | --- |
| 設定を読む仕事 | `readSettingsFile`、`loadConfig` のような名前と「設定」「JSON」「ファイル読込」などの語 | 名前が違っても関係しそうな候補 |
| ファイル形式や失敗時の動作 | `docs/specs/settings.md`、候補の実装と対応テスト | 必要な入力・結果・エラーに合うか |
| 実際に使われる場所 | 呼び出し元、作られる場所、読み込み先 | どの機能が使い、何を前提にしているか |
| 同じ状態を持つ変数 | 値を作る場所、更新する場所、捨てる場所 | 誰が管理し、いつまで保持する値か |
| 設計上の担当範囲 | 共通処理の説明と、機能間の利用ルール | 今回の場所から使ってよい部品か |

候補を見つけただけで「再利用可能」と判断させないでください。定義と使う側を開き、関連テストを確認させます。非公開の部品を無理に外へ出したり、画面専用の部品をコマンドから使って担当範囲を崩したりしないことも条件です。

探す範囲は今回の機能と、その共通処理から始めます。別の機能にも同じ仕事があると分かったら、その候補へ広げます。検索で見つからなかったことだけを「プロジェクト全体に存在しない」証明にはしません。検索範囲と未確認箇所を報告させてください。

### 3. そのまま使う、広げる、新しく作る、を比べさせる

| 判断 | 基準 | 設定読み込みの例 |
| --- | --- | --- |
| そのまま使う | 入力・返す値・失敗時の動作・利用してよい場所が合う | 共通の `readSettingsFile(path)` をコマンドから呼ぶ |
| 既存の部品を広げる | 同じ仕事のまま不足を補え、既存の利用側の約束を保てる | 読み込み結果に必要な情報を加える。ただし既存利用側への影響を確認する |
| 新しく作る | 仕事や必要な条件が違い、既存部品の変更が担当範囲や既存動作を壊す | ネットワークから設定を受け取る処理を、ファイル読込とは別に置く |

既存の部品を広げるなら、変わる入力や結果を使う場所を探し、今までの呼び出し方と動作が保たれるか確認させます。違う仕事を切り替える条件を大量に足すだけの「共通部品」にしないでください。

新しく作る場合は、既存候補では不足する条件、新しい部品の仕事、使う側、名前を説明させます。例えばネットワークから受け取る処理は別でも、取得後のJSONの解釈は既存部品を使えるかもしれません。分ける場所と使える部分をそれぞれ判断します。

変数も、同じ値が入っているだけでは同じ役割とは限りません。`savedSettings` が保存済みの値、`draftSettings` が編集中の値なら、取消操作で前者へ戻すために区別している場合があります。一つにして同じ値を共有すると、編集途中に保存済みの状態まで変わる恐れがあります。作る時点・更新する人や処理・破棄する時点まで確認してください。

類似したコードを必ず一つにすべきとは限りません。[KapserとGodfreyの論文](https://plg.uwaterloo.ca/~migod/papers/2008/emse08-ClonePatterns.pdf)も、重複の理由、安定性、担当範囲、分かりやすさを確認してから整理を判断する必要を述べています。[1]

### 4. 判断と根拠を短く残し、AIへ手順を渡す

中断・引継ぎがあるなら、例えば `docs/work/reuse-plan.md` に次の項目を保存させます。短い作業なら同じ項目を返答に示させるだけでも使えます。

```markdown
# 今回の既存コードの使い方

- 追加したい仕事と変えない条件:
- 確認した候補（定義・使う側・テストのパスと関数名や見出し）:
- 判断: そのまま使う / 広げる / 新しく作る
- その判断にした理由と、他の案では足りない条件:
- 新しい名前と役割（追加する場合）:
- 影響する既存の使う側:
- 変更後に実行する既存の確認:
- 不明点と未確認範囲:
```

依頼にはメモの保存先、仕様の場所、変更してよい範囲を指定します。次はコピーして使える例です。

```text
コマンドから設定ファイルを読んで表示する機能を追加してください。
仕様: docs/specs/settings.md「読込形式とエラー」
既存の画面の動作を保ってください。まず関連する作業ルールを読んでください。

編集前に、同じ仕事を持つ既存の関数・クラス・状態変数を検索してください。
名前だけでなく入出力、扱うデータ、失敗時の動作も手掛かりにしてください。
候補の定義、使う側、関連テスト、担当範囲の説明を確認してください。
そのまま使う・広げる・新しく作る案を比べ、
docs/work/reuse-plan.mdへ判断と根拠を短く保存してください。
新しく作るなら、既存候補では足りない条件と新しい名前・役割を示してください。
名前やコードが似ているだけで、別の仕事や状態を一つにまとめないでください。
調査で仕様や担当範囲の矛盾が見つかったら、関係する変更を進めず質問してください。

依頼の範囲で実装し、変更後は追加した名前と役割を一覧にしてください。
既存との役割・処理の重複、既存利用側への影響、依存の向き、状態の共有を点検してください。
変更に合う既存テストと、値の種類や呼び出し先の整合を調べる型・参照の確認を実行し、結果と未確認箇所を報告してください。
未実行や対象外を成功と報告しないでください。
```

ファイルを読めないチャットには、仕様、候補の定義と使う側、関連テスト、差分を添付するか貼り付けてください。パスだけでは内容は渡りません。まず候補の探し方をAIに挙げさせ、あなたが検索結果を渡し、必要な箇所を追加で渡す進め方も使えます。実行できない確認は、あなたが結果を渡すか未実行として残します。

繰り返す場合は、例えば `AGENTS.md` に「関数・クラス・共有状態を追加するときは、既存候補と使う側を調べ、再利用・拡張・新設の判断を示す」と置けます。詳しい手順は保存した案内へ参照させ、規則全文や以前の候補一覧を毎回コピーしないでください。自動で指示書を読まないAIには、その場所を依頼で指定します。

### 5. 追加した名前と役割を差分で点検させる

変更後は、新しい関数・クラス・変数だけでなく、変更で役割を広げた既存部品も一覧にさせます。例えば次のように報告させます。これは実行結果ではなく、架空の例です。

```text
追加: showSettingsCommand — 読み込んだ設定をコマンドの出力へ表示する。
再利用: src/settings/readSettingsFile.ts の readSettingsFile — ファイルを読む。
重複確認: ファイル読込は既存関数へ任せ、別のSettingsLoaderは追加していない。
既存利用側: 設定画面の呼び出し方と、読込エラーの扱いは変更していない。
状態: savedSettingsとdraftSettingsは保存済みと編集中の別状態のため維持。
確認: 対応テストと型・参照の検査を実行して成功。
未確認: 実際の画面操作。
```

あなたも報告された定義・使う側・差分を照合してください。点検では、次を区別します。

- 名前の違いだけで同じ処理を追加していないか。
- 名前が似ていても別の仕事をする部品を統合していないか。
- 既存部品を広げたことで、今までの入力・結果・エラーが変わっていないか。
- 本来別々の状態を共有したり、使ってはいけない機能へ依存したりしていないか。
- テストや型の確認が今回の新しい使い方と、影響する既存の使い方を扱っているか。

検索や型の確認だけでは、同じ仕事かどうかを判定できません。確認できない条件は残し、「重複なし」「既存機能に影響なし」と断定させないでください。

## コーディングルールとの使い分け

[AIにコードの決まりを読ませ、変更後に確かめさせる](AIにコードの決まりを読ませ、変更後に確かめさせる.md)は、適用する規則と確認方法をAIへ伝える手順です。この文書は、規則が「既存部品を使う」としている場合などに、どの部品を使うべきか、使えないならどうするかを調べる手順です。命名検査の成功だけで、この判断を済ませません。

## コンテキスト使用量が減る理由と限界

定義・使う側・テストを候補から絞って読むことで、無関係な全ファイルを渡して部品を探させる量を減らせます。再利用した箇所と新設の理由を短く記録すれば、後から似た処理を読み比べたり、追加を取り消すために説明を繰り返したりする負担も抑えられます。

調査とメモにも入力を使います。候補を無制限に集めたり、以前の候補の本文を毎回渡したりすると逆効果です。判断を左右する条件と根拠へ絞り、必要な実装・テストは省略しないでください。この手順でのAIの判断品質やコンテキスト削減量は実測していません。

## 補助ツール

- **名前や本文の検索:** 関数名、データ名、処理の語から候補を探します。同じ名前がない場合も、同じ役割の候補を探す入口に使えます。
- **エディターの定義・使用箇所検索:** 宣言と、その要素を使う場所へ移動できます。既存部品を変えたときの影響先を探すために使えます。動的な呼び出しなどは見つからない場合があります。
- **関数・型の一覧:** ファイル内の関数やクラスなどの場所を示します。大きなファイルから候補を絞るために使えます。
- **類似コードの検出:** 似たコードの場所を示します。重複候補を探せますが、同じ役割か、統合すべきかは元コードと使う側で判断します。
- **Gitの差分表示:** 新しい名前や処理と既存部品の変更を表示します。追加や役割の変化を点検するために使えます。

## この手法について

既にある部品を別の作業でも使うことを**ソフトウェア再利用**、似たコードのまとまりが複数の場所にあることを**コードクローン**と呼びます。[1] 本書は、再利用の前に用途や条件を確認するためのAIへの依頼手順です。

参考にした論文は、重複コードの理由と保守への影響を調べたものです。ここにある依頼文や、AIによる判断精度・コンテキスト削減量を検証した研究ではありません。
