# 調査前に、原因を判断する確認項目を決める

不具合の調査をAIに頼むと、「念のため」と関係する資料を次々に読み、修正になかなか進まないことがあります。依頼する人は、修正に進むために必要な情報を先に決めて依頼に書きます。AIはその情報を調べ、足りない場合だけ調査範囲を広げます。

## 例：表データの日付が1日ずれる

依頼する人は、AIに次の点を確認するよう伝えます。

- どんな入力で、どんなずれが起きるか
- 日付を変換するコードがどこにあるか
- 同じ入力を確かめるテストがあるか
- 直した後、どの結果になれば正しいか

依頼に「この項目が分かったら、追加の調査を止めて修正に進む」と書いておけば、AIは必要な情報を確認した時点で修正を始められます。

```text
先に確認する
  - 不具合の再現条件
  - 日付を変換するコード
  - 関連するテストと正しい結果

必要になったら確認する
  - 周辺機能のコード
  - 古い変更履歴
  - プロジェクト全体の説明書
```

## 調べるたびに理由を確かめる

AIに追加でファイルや履歴を調べさせる前に、依頼する人は「何がまだ分からないのか」「それを知ると何を判断できるのか」を確認します。調べる理由があるなら、その疑問に答える範囲だけをAIに確認させます。判断が変わらないなら、調査を広げるよう頼みません。

## 確認を増やす場合

最初に決めた範囲を越えて調べるのは、次のような場合です。

- コードとテストの動きが食い違っている。
- 原因が分からず、隣の処理を確認する必要がある。
- 今回の変更が別の機能にも影響する。
- 完了を判断するための確認方法が見つからない。

追加で確認した資料から必要な情報が得られたら、さらに範囲を広げず、修正や動作確認へ進みます。影響がないと分かった履歴や資料を、念のため読み続ける必要はありません。

## 作業を始める前に短く書く

今回だけの確認項目は、作業依頼に直接書きます。複数日にまたがる場合は[作業メモのひな型](../../../templates/CONTEXT_PACK.md)を `CONTEXT_PACK.md` として保存し、次に作業するAIへそのパスを伝えます。同じ確認項目を別の作業でも使う場合は、`AGENTS.md` や `docs/` 内の作業案内に置いて参照させます。

```text
今回確認すること:
- 不具合の再現条件
- 日付を変換するコード
- 関連するテスト

追加で調べる条件:
- コードとテストが食い違っていたら、呼び出し元も確認する
```

小さな作業なら、こうした一覧を別の文書にする必要はありません。作業メモに数行書くか、頭の中で確認すれば十分です。

## AIへの指示例

```text
次の項目を確認してください。
- どんな入力で、どんなずれが起きるか
- 日付を変換するコードがどこにあるか
- 同じ入力を確かめるテストがあるか
- 直した後、どの結果になれば正しいか

これらを確認しても原因や修正後の結果を判断できない場合は、何が足りないかを説明し、その点に関係する場所だけ追加で調べてください。すべて分かったら調査を止め、修正に進んでください。
```

## なぜ読む量が減るのか

先に判断に必要な条件を決めると、「念のため」という理由だけで関係の薄い資料を読み続けずに済みます。必要な根拠が得られなければ追加調査するため、確認不足のまま完了にはしません。

## 用語

- **確認の範囲**: 作業を判断するために、AIが読むコード、テスト、説明書などの範囲です。
- **必要な根拠**: 作業の判断や、直ったかどうかを確かめるために必要な入力例、コード、テスト結果などです。
- **Evidence Budget**: 作業の判断に必要な根拠を先に決め、それを確かめる範囲で調べる考え方を、このように呼びます。

## 補助ツール

- 必要なら、[`acceptance-extractor`](../../../tools/common/medium/acceptance-extractor/README.md)が作業メモから目的・必須事項・完了条件を取り出します。抜けがないか原文と照らして確認してください。
