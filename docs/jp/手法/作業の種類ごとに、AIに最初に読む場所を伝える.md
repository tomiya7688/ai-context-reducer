# 作業の種類ごとに、AIに最初に読む場所を伝える

たとえば「表データの日付ずれを直す」作業では、AIに日付を扱うコード、関連テスト、日付の決まりを確認させます。画面の色を変える作業なら、画面のコードと画面の確認方法を伝えます。作業ごとに最初に読む場所を決めてAIに渡せば、プロジェクト全体を探させずに済みます。

## 作業ごとに読む資料と確認方法をまとめる

作業の種類と、AIに最初に確認させる場所を対応づけます。

| 作業 | AIに最初に確認させる場所 |
| --- | --- |
| 表データの日付処理を直す | 日付の決まり、日付を扱うコード、日付処理のテスト |
| 設定画面を変える | 設定画面のコード、設定の保存処理、画面のテスト |
| 通信の形式を変える | 通信形式の説明、送受信するコード、対応するテスト |

実際のプロジェクトに合わせて、一覧には具体的なファイル名やリンクを書きます。まだ場所が分からない場合は、作業名だけで決めつけず、関連するコードとテストを探してから載せます。

同じ一覧を繰り返し使うなら、`docs/作業別の確認先.md` に保存し、リポジトリ直下の `AGENTS.md` からリンクします。依頼文には「今回の作業に合う行だけを見てください」と書けば、AIは一覧全体を読まずに済みます。変更別の確認表がすでにある場合は別の表を作らず、その表へ作業例を加えてください。一度だけの作業なら、最初に読む場所を依頼文へ直接書きます。AIへの入口から資料を参照させる方法は[基本手順](AIに作業を頼むときの基本手順.md)にもまとめています。

## AIに渡す作業内容を短くまとめる

長い作業をAIに頼むときは、すぐに調査を始められるよう、次の点を依頼に書きます。

- 何を変えるか
- 変えてはいけないこと
- 最初に確認する資料やファイル
- 何を確かめたら完了か
- 詳しい依頼や仕様の原文がある場所

短いまとめだけで判断できない点があれば、AIに依頼や仕様の原文も確認させます。短いまとめは原文の代わりではありません。

## 複数の作業から次に行うものを選ぶ

未完了の作業がたくさんある場合、すべてをAIに読ませて選ばせる必要はありません。プロジェクトで優先順が決まっているなら、その順に今回AIへ頼む作業を決めます。

```text
最優先の作業 → 次に優先する作業 → その次の作業
```

優先順の名前や並び方は、プロジェクトの決まりに合わせます。順番が決まっていない場合は、AIに決めさせず、依頼する人が決めて伝えます。

「次」の合図で一件ずつ頼む場合は、[課題一覧から一件ずつAIに進めさせる](課題一覧から一件ずつAIに進めさせる.md)で、一覧・優先順・一回の範囲・停止条件を決めてください。この案内は、選んだ作業で最初に読む場所を決めるために使います。

## 変更箇所を先に取得します

別の人やAIが同じ共有先を更新している場合は、作業を始める前に自分で最新変更を取得するか、作業を頼むAIに取得させます。変更されたファイル名と概要を確認し、今の作業に関係する差分だけをAIに読ませます。関係がない変更まで全て読み直す必要はありません。

```text
共有先の最新変更を取得
  → 変更されたファイル名と概要を確認
  → 今回の作業に関係する変更を読む
  → 作業を始める
```

取得した変更を手元の作業へ取り込むのは別の操作です。手元に未保存の変更がある、同じファイルを別々に変更している、または取り込むと作業が上書きされる可能性がある場合は、いったん止めて状態を確認します。確認方法の詳しい説明は[作業前に共有先で変わったファイルを確認する](作業前に共有先で変わったファイルを確認する.md)を参照してください。

## 作業を渡す前に、結果を確かめる

変更の確認は、人が行うか、AIに依頼します。画面を変えた場合は画面を開き、配布ファイルを変えた場合は配布用ファイルを確認します。AIに確認を頼むときは、対象と方法を伝えてください。確認後、次の人やAIに作業を渡します。

報告には、実行した確認とその結果を短く書きます。確認していないことや、対象がなく実行されなかったテストは、成功したように扱いません。失敗したときは、原因を判断するために必要な部分だけ記録します。

## AIへの指示例

```text
表データの日付ずれを直してください。
最初に日付の決まり、日付を扱うコード、関連テストを確認してください。
コードとテストが食い違う場合や、別の処理への影響が分からない場合だけ、呼び出し元も調べてください。
同じ入力で日付が正しく表示されることを確認してください。
```

## どこまで決めるか

まずは作業別の一覧を手で用意し、何度も同じ場所を探す作業から使います。自動で作業を選ぶ仕組みや、依頼文・報告文を自動で作る仕組みは、同じ手間が繰り返し発生し、仕組みの手入れより負担が大きいと分かってから追加します。

## なぜ読む量が減るのか

作業の種類に合う行をAIに渡すと、プロジェクト全体から読む場所を探させずに済みます。表には場所だけを書き、詳しい説明は必要な資料を開いて確認させます。

## 用語

- **原文**: 要約のもとになった作業依頼や仕様書そのものです。
- **Task Routing（作業別案内）**: 作業の種類ごとに、最初に確認する説明・コード・テストを対応させる方法を、このように呼びます。

## 補助ツール

- 必要なら、[`change-router`](../../../tools/common/medium/change-router/README.md)が変更ファイルから、先に見るテストや文書の候補を示します。候補は案内表や原典で確かめてください。
