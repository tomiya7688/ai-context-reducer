# まず、コードの構文チェックをする

プログラムの書き方に間違いがないかを調べ、見つかったファイルだけを直します。これは動作確認の前に使える簡単な確認です。書き方が正しくても、処理の内容や実行結果まで正しいとは限りません。

## 使う場面

対象の言語に対応した確認手段がすでにあり、ビルドやテストより早く実行できるときに使います。複数ファイルを一括編集した後や、コードを自動生成した後などに、基本的な書き間違いを先に見つけられます。

使える確認手段がない場合は、これだけのために開発環境を追加しません。プロジェクトで普段使っているビルドやテストを行い、どの確認を実行できなかったか伝えます。

## AIへの指示例

```text
変更したプログラムに、すでに使える書き方の確認方法があれば実行してください。
確認できたファイル数と、問題が見つかったファイル・行を報告してください。
書き方の確認に成功しただけで、動作も正しいとは判断しないでください。
変更内容に合うテストやビルドも行い、実行できなかった確認は未確認と書いてください。
```

## 確認結果の見方

書き方の確認で分かるのは、主に記号や文法の誤りです。次のことを確かめるには、別の確認が必要です。

| 確かめたいこと | 使う確認 |
| --- | --- |
| データ型や呼び出し方法が正しいか | コンパイラーや型の確認 |
| 処理結果が仕様どおりか | 関連するテスト |
| アプリが実行できるか | 起動や操作の確認 |
| 配布用ファイルが正しいか | 作成した配布物の確認 |

結果が「問題なし」でも、対象ファイルを実際に確認できていたかを見ます。対象が0件、言語が未対応、確認手段の実行に失敗した場合は、成功とは報告しません。

## なぜ読む量が減るのか

問題のあるファイル名と行だけをAIに渡せば、関係する箇所から修正させられます。問題のないファイルの解析結果や全ファイルの一覧は渡さず、後続のテストやビルドを省略せずに実行させて、結果を短く報告するよう依頼します。

## 補助ツール

- 必要なら、`syntax-health`がすでに利用できる構文確認の仕組みで問題のあるファイルを一覧にします。コードの構文をまとめて確認するときに使えます。構文確認の仕組みを自動で追加するものではありません。

プロジェクトのコンパイラーやエディターで同じ確認ができるなら、そちらを使えます。
