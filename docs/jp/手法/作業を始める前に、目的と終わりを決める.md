# 作業を始める前に、目的と終わりを決める

AIに実装を頼む前に、何を変えるか、守ること、終わりの目安を短く伝えます。引き継ぐ人やAIは、その記録と関係する資料を読んで作業できます。

## 何を決めるか

作業に関係する項目だけを、未完了作業の一覧、作業メモ、設計説明のいずれかに書きます。

1. **目的**: 誰のどんな困りごとを解決するか。
2. **変更する範囲**: どの機能やファイルを変えるか。
3. **守ること**: 変えてはいけない動きや、他のプログラムとの約束。
4. **終わりの目安**: どのような動きになり、何を確かめたら完了か。
5. **読む資料**: 詳しい決まりや今回の依頼がどこにあるか。
6. **人が見ること**: 自動では判断できない使いやすさや見た目など。

一度の作業なら、この項目を依頼文に書きます。別の会話へ引き継ぐ作業では[作業メモのひな型](../../../templates/CONTEXT_PACK.md)を `CONTEXT_PACK.md` として保存し、次のAIへの依頼にファイルのパスを書きます。複数の作業で共通するルールは、今回限りのメモではなく `AGENTS.md` から参照する文書に置きます。

## AIへの指示例

```text
目的: 設定画面で選んだ言語を保存する。
変える場所: 設定画面と設定の保存処理。
守ること: すでに保存された設定を壊さない。
終わりの目安: 選んだ言語が保存され、アプリを開き直しても残る。関連テストが通る。
読む資料: docs/settings.md、今回の作業依頼。
人が見ること: 画面の文が読みやすいか。

この条件を読んでから作業してください。書かれていない条件を推測で決めず、重要な点が不明なら先に質問してください。
```

小さな修正なら、作業依頼に目的と確認方法だけ書けば十分です。数日にわたる作業や複数人での引き継ぎなら、守る条件と読む資料も書きます。仕様が変わったら記録も直し、古い決定と新しい決定を混ぜないようにします。

## なぜ読む量が減るのか

目的や完了条件をAIに伝えないと、AIは過去の会話や広い範囲のコードから意図を推測し、どこまで直すかやテストを何度も判断し直します。短い記録を渡せば、必要な資料と確認方法から作業させられます。機械で繰り返し確認できる条件は自動テストに任せ、結果を短くまとめてAIに渡せば、長い手順や成功ログを毎回読ませずに済みます。

## 自動確認へ加える目安

同じ確認を何度も行う、壊れると利用者に影響する約束がある、配布用ファイルの中身を確かめる必要がある場合は、自動確認に加える価値があります。自動確認とは、変更を共有する前にコンピューターがビルドやテストを実行して問題を探す仕組みです。手入れや実行にかかる負担が、減らせる確認時間を上回るなら追加しません。使いやすさなど、機械が正しく判断できないことは人が確認します。

## 作業を始めた後に前提が変わったら

大切な条件が足りない、または記録とコードが食い違うと分かったら、推測で続けず、記録を直してから作業します。完了に必要な確認ができない場合は、できたことにせず未確認として伝えます。
