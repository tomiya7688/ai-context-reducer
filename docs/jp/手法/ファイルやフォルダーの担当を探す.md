# ファイルやフォルダーの担当を探す

「この不具合は、どのフォルダーから調べればよいのか」を毎回探しているなら、仕事の種類ごとに主な場所と担当を短くまとめます。たとえば「文書のリンク切れを調べる」なら、リンクを確かめる実装と、その動作を確かめるテストへ案内します。

全ファイルの一覧を作る必要はありません。繰り返し探している仕事から始め、実際のコードとテストで確認できた代表的な場所を載せます。表は調査の入口であり、現在の動作や変更の正しさは元のコードやテストで確かめます。

## 例：支払い済みなのに督促メールが届く

請求書の支払いが済んでいるのに、支払いを求めるメールが届く不具合を直すとします。次の表は、架空の請求アプリを例にしたものです。

| 仕事の種類 | 主な場所 | 担当 |
| --- | --- | --- |
| 請求と支払い | `src/invoices/` | 請求書と、支払い済みかどうかを記録する |
| 督促 | `src/reminders/` | 支払いが済んでいない請求書を選び、督促メールの内容を作る |
| メール送信 | `src/email/` | メールを送る |
| 動作確認 | `tests/reminders/` | 支払い済みの請求書には督促メールを作らないことを確かめる |

この不具合なら、まず「督促」の行にある `src/reminders/` と「動作確認」の行にある `tests/reminders/` を見ます。督促メールを作る条件と、その条件を確かめる方法が分かるからです。支払い済みかどうかの情報が間違っていそうなら「請求と支払い」を、正しいメールが作られているのに届かないなら「メール送信」を調べます。

このように、問題の内容に合わせて調べる場所を選べます。すべてのファイルを開いて担当を推測する必要はありません。

## 使う場面と判断基準

| 今の状態 | 取り入れ方 |
| --- | --- |
| 同じ機能を直すたびに、実装やテストの場所を探し直している | その機能の行から作る |
| フォルダー名だけでは、何を担当するか判断できない | 処理と利用箇所を確かめ、担当を一文で書く |
| 既存の設計文書や作業別の案内に、同じ担当と確認先がある | その案内を使い、不足する場所だけ補う |
| 数個のファイルを見れば担当とテストが分かる | 既存の案内に数行書けば足りる。専用の表は増やさない |

ファイルが大きい、変更回数が多いという理由だけで行を増やさないでください。**その仕事を始める人が、最初の実装と確認先へ進めるか**を基準にします。

## 実際のコードから作る手順

### 1. 繰り返し探している仕事を一つ決める

最近の依頼やIssueから、たとえば「保存後に設定が残らない」「文書のリンク切れを直す」のように、調べたい動作を一つ選びます。「その他」「共通処理」だけでは開始場所を選べないため、まず利用者が依頼する仕事の言葉で分類します。

最初からプロジェクト全体の分類を完成させる必要はありません。今回の仕事で必要な行だけ作り、別の仕事でも案内が必要になったときに足します。

### 2. 既存の案内と処理の入口を探す

README、既存の担当表や設計文書を検索し、同じ案内がないか確かめます。候補がなければ、問題のエラー文、画面の項目名、処理名、実行コマンドなどでコードを検索します。

フォルダー名は候補を見つける手掛かりです。名前だけで「ここが担当」と決めず、見つけた処理がどこから呼ばれ、どの値やファイルを受け取り、何を返したり保存したりするかを確認します。

### 3. 実装とテストで担当を確かめる

AIに調査を任せる場合は、次をコードから確かめさせます。

1. 候補の関数やクラスの定義と、それを使う場所を開かせる。
2. 対象の動作をどの処理が決めているか、具体的な条件や入出力を挙げさせる。
3. 関連テストを開かせ、何を入力し、どの結果を正しいと判定しているか確認させる。
4. 別の処理へ委ねていると分かったら、その定義と関連テストまで追わせる。

テストを読めば、想定されている動作は分かります。現在そのテストが成功するかは、実行結果がある場合にだけ分かります。テストが見つからなければ「確認用テストは未特定」と記し、存在しないパスを埋めないでください。役割も確定できない場合は、確認できた事実と未確認の点を分け、確定した担当として載せません。

### 4. 例：このリポジトリの文書検査を調べる

以下は2026年10月18日時点のコードを読んだ例です。「文書のリンク切れや日英の対応漏れを直す」という仕事を選び、次を確かめます。読者のプロジェクトに同名のファイルを作る手順ではありません。

- [検査の実装](../../../.github/scripts/validate_documentation.py)の `load_mapping` は `docs/DOCUMENT_MAP.json` を読み、言語や登録内容を調べます。`validate` は登録された日英文書と、実在する文書を照合します。
- 同じ実装の `validate_relative_links` は文書中の相対リンクを読み、参照先が存在するかなどを調べます。
- [関連テスト](../../../.github/scripts/test_validate_documentation.py)の `test_missing_english_file_is_detected` は英語文書を削除してエラーを確かめ、`test_broken_relative_link_is_detected` は存在しない参照先を検出できるか確かめます。
- [GitHub上で検査を実行する設定](../../../.github/workflows/validate-documentation.yml)には、そのテストと文書検査を呼ぶ手順があります。

この確認から、たとえば次のようにまとめられます。

| 仕事の種類 | 主な場所 | 担当と確認先 |
| --- | --- | --- |
| 日英の文書対応を検査する | `.github/scripts/validate_documentation.py` | `load_mapping` と `validate` で登録内容と文書の存在を照合する。確認先は `.github/scripts/test_validate_documentation.py` |
| 文書の相対リンクを検査する | `.github/scripts/validate_documentation.py` | `validate_relative_links` で参照先を調べる。確認先は同じテストファイルのリンク切れのテスト |
| GitHub上で検査を呼び出す | `.github/workflows/validate-documentation.yml` | テストと文書検査の実行手順を定める。実行の成否は対応する実行結果で確認する |

`.github/` という名前から担当を推測したのではなく、読込先、判定処理、テストの期待結果、実行設定を根拠にしています。同じファイルが複数の仕事を担当していても構いません。全関数を表へ写す必要はありません。

### 5. 既存の案内へまとめ、AIが読む場所から参照する

既存の担当表があれば、そこへ確認済みの行を足します。新しく置く場合の保存先は、たとえば `docs/ファイルの担当表.md` です。表の近くに、確認した日付やコミット（コードの版を識別する番号）も書くと、後の変更と比べやすくなります。記載した版だけで、現在も正しいと保証されるわけではありません。

繰り返し使う場合は、利用中のAIが読むプロジェクト指示へ、適用条件と表のパスを短く書きます。`AGENTS.md` を読む環境なら、既存ルールを保って次のように足せます。

```text
実装やテストの場所を探すときは、docs/ファイルの担当表.md から
今回の仕事に関係する行を選んでください。
候補の実装と関連テストを読み、表が現在のコードと合うか確かめてください。
表にない関係が見つかったら、必要な処理まで調べる範囲を広げてください。
```

ファイルを置いたりリンクしたりするだけでは、AIが自動で読むとは限りません。指示ファイルの読込み設定を確認するか、依頼に表のパスを指定します。ファイルを開けないチャットなら、該当する行と必要なコード・テストを添付または貼り付けます。

## AIへの依頼例

初めて表を作らせる場合は、調査対象と完成の基準を渡します。

```text
対象は「文書のリンク切れを直す」仕事です。
既存のREADME、設計文書、担当表に同じ案内がないか先に調べてください。
実装の定義と利用箇所、関連テストを読み、
処理の入出力・判定条件とテストの期待結果を根拠に担当を整理してください。

仕事の種類、主な場所、担当、関連テストを短い表にしてください。
全ファイルや全関数は列挙せず、調査を始められる代表的な場所を選んでください。
確認したコードの版と根拠を示し、不明な担当や未特定のテストは断定しないでください。
既存の案内があればそこへまとめ、なければ docs/ファイルの担当表.md の案を作ってください。
今回はコード変更やテストの実行はせず、案と未確認事項を示してください。
```

完成の目安は、利用者が表から実装と確認先を開け、各行の担当をコードの処理とテストの期待結果で説明できることです。説明できない行は確定扱いにしません。

作成済みの表を使わせる場合は、次のように頼めます。

```text
保存した設定が再起動後に消える原因を調べてください。
docs/ファイルの担当表.md を読み、設定の保存・起動時の読込み・関連テストの候補を選んでください。
選んだ実装とテストを開き、担当表と合うか確認してください。
別の処理も関係すると分かったら、必要な場所へ調査を広げてください。
まず候補と根拠、表との食い違い、未確認の点を報告してください。
```

## 表と実際のコードが食い違うとき

古い表に合わせてコードを直すのではなく、現在の定義、利用箇所、関連テストを確認させます。動作の要件も食い違うなら、現行の仕様書やIssueで何を求めているか確かめさせてください。表だけでは、コードと仕様のどちらが誤っているか決められません。

表の案内が古いと確認できたら、移動先や現在の担当へ記述を直します。原因や担当が未確定なら、未確認として残し、その行で調査を打ち切らせないでください。担当の追加・移動・分割があった変更では、表も同じ変更で更新します。

変更の種類から確認先を整理したい場合は[変更内容ごとの案内表](変更内容ごとに読む場所と確認方法を一覧にする.md)、大きなソース内の定義や呼出し元を探す場合は[コード構造の索引](関数や使われている場所を探す.md)へ進めます。

## なぜ読む量が減るのか

繰り返す仕事の入口を残すことで、毎回フォルダーを順に開き、担当を推測する調査を減らせます。AIには関係する行から実装とテストへ進ませるため、無関係な機能のコードを渡す量も抑えられます。

表を作る最初の調査と、その後の更新には手間がかかります。別の処理が必要と分かったら追加で読ませ、必要な情報まで省かないでください。表が短くなっただけで使用量が減ったとは判断せず、実際の読込み記録や、計測できる場合は入力使用量を比べます。

## 補助ツール

- [responsibility-candidates](../../../tools/common/medium/responsibility-candidates/README.md)：コードのパスと大きさを表に並べ、担当欄を未記入にした下書きを作ります。記入漏れの候補探しに使えますが、仕事の分類や担当は確定しないため、必要な行を選んでコードとテストで確かめます。

## この手法について

仕事の種類ごとに主要な場所と担当を記録し、必要な実装やテストへ案内する一覧を、役割表（Responsibility Map）と呼びます。
