# AIにコードの決まりを読ませ、変更後に確かめさせる

AIが追加した関数名を毎回直したり、既にある処理をもう一つ作ったことを指摘したりしていませんか。「既存の書き方に合わせて」だけでは、AIが何を守り、何で確認すればよいか判断できない場合があります。

守る決まりを一か所に置き、AIに今回の変更へ適用させ、変更後の差分と照らして確認させます。名前や書式を機械で調べられる部分と、処理の意味を読まなければ判断できない部分を分けると、毎回すべてを人が指摘する負担を減らせます。

## 使う場面と判断基準

- 同じ命名、既存部品の再利用、依存関係の追加などを何度も指摘している場合に使えます。まず繰り返している決まり一つから始めてください。
- 既に短い指示書と検査が機能しているなら、それらへの参照と変更後の点検を依頼に加えるだけで足ります。同じ決まりを別のファイルへコピーしないでください。
- 今回だけの条件は依頼文に書きます。今後も守る決まりになったときに、共通の指示書へ移してください。
- 名前の書式や空白なら既存の自動検査を使えます。「この関数が適切な仕事をしているか」「既存部品を使えるか」は、実装と呼び出す側を確認させる必要があります。

## 使うときの手順

### 1. 既存の決まりと検査を探す

AIに、新しい規則を書かせる前に次の場所を調べさせてください。

| 探す場所 | 分かること | 確認する点 |
| --- | --- | --- |
| プロジェクトの指示書、`CONTRIBUTING.md` などの開発者向け説明 | 守る条件、適用範囲、作業手順 | 詳しい規則が別の文書にあるか |
| `.editorconfig` などの書式設定 | 空白や改行などの設定 | 使うエディターや検査がその設定に対応しているか |
| 検査の設定とコマンド一覧 | 自動で調べられる規則、実行方法 | 対象ファイルと有効な規則。置いてあるだけで実行されるとは限らない |
| 既存の実装とテスト | 部品の使い方、守る動作 | 古いコードが今の規則に違反している可能性もある |

このリポジトリの一般的な規則の探し方は[今回の変更に関係する規則を確認する](../今回の変更に関係する規則を確認する.md)、場所ごとの指示書の使い方は[場所ごとに作業ルールを分ける](../場所ごとに作業ルールを分ける.md)で説明しています。

### 2. 具体的な決まりを一か所に保存する

既存部品を使う規則で、どの部品を使えるか迷う場合は[AIに既存コードを調べさせ、似た役割の追加を防ぐ](AIに既存コードを調べさせ、似た役割の追加を防ぐ.md)の手順も使えます。

以下は架空のJavaScriptプロジェクトの例です。このリポジトリの規則ではありません。ファイル名やコマンドは、自分のプロジェクトに実在するものへ置き換えてください。

既に規則文書があるなら、その該当節を使います。ない場合は、例えば `docs/development/coding-rules.md` に次のように書けます。

```markdown
# コードの決まり

適用範囲: src/settings/ の手書きコード。自動生成されたファイルは編集しない。

- R1 必須: 関数名は loadSettings のように、最初の語を小文字、
  次の語の頭を大文字にする。外部で決められた名前は変更しない。
  書式は既存の命名検査で確認し、名前が処理の内容を表すかは差分で確認する。
- R2 必須: JSONファイルの読み込みを追加するときは、
  src/io/readJson.js の readJson を先に調べる。
  入力・返す値・失敗時の動作が合うなら使い、同じ処理を追加しない。
  合わない場合は、どの条件が違うかを根拠付きで報告する。
- R3 必須: 設定機能では、外部の依存パッケージを追加しない。
  必要だと判断したら理由を報告し、追加せずに止める。
  依存を記録するファイルの差分と、新しい読み込み先を確認する。

確認コマンド: package.json にある format:check、lint、test:settings を使う。
lintの設定に命名検査があることを確認する。なければR1の書式も差分で点検する。
```

「きれいな名前にする」より、「どこに適用するか」「何を守るか」「例外」「確認方法」を書く方が、AIも人も判断できます。R1などの番号は、点検結果を短く対応づけるための目印です。

人も読む開発者向け説明に詳しい規則を置き、AI用の入口には適用条件と参照先だけを書きます。例えばルートの `AGENTS.md` に、次の一文を置けます。

```text
src/settings/ のコードを変更するときは docs/development/coding-rules.md を読み、
変更前に適用項目を特定し、変更後に差分と各項目を照らして点検する。
```

既に別の名前の指示書が使われているなら、その入口を使ってください。ファイル名を `AGENTS.md` にするだけで、すべてのAIが自動で読むわけではありません。

### 3. 作業前と変更後にすることをまとめて頼む

```text
設定ファイルを読み込む機能を追加してください。
まず AGENTS.md と、対象フォルダーに適用される指示書を読んでください。
docs/development/coding-rules.md の適用項目、再利用する部品、
実行する既存の確認コマンドを短く挙げてから編集してください。
自動で読んだ指示書があれば、同じ本文を再度読む必要はありません。

変更後は、今回の差分をR1〜R3と照らして点検してください。
書式など既存の検査で確認できるものは、指定されたコマンドを実行してください。
処理の意味、再利用の可否、依存追加の有無はコードと差分でも確認してください。
違反を見つけたら今回の変更範囲で直し、その箇所に必要な確認をやり直してください。
検査を通すために規則や検査を無効にしないでください。
矛盾した必須規則があれば、該当箇所と矛盾点を示してください。
明示された優先順位で解決できなければ、影響する変更は進めず質問してください。
最後に、項目ごとの根拠、実行結果、未確認事項を短く報告してください。
実行できなかった検査や、対象外だった検査を成功と報告しないでください。
```

ファイルを読めないチャットでは、適用される規則、関連コード、検査結果を添付するか貼り付けてください。パスだけを書いても内容は渡りません。AIが実行できない検査は、あなたが実行して結果を渡すか、未実行として残します。

繰り返す点検手順は、例えば `docs/development/coding-check.md` に保存し、入口から「コードを変更したときに使う」と参照できます。手順を登録して呼び出せるAIなら、その登録機能も使えます。規則本文は複製せず、規則の場所と点検する順番を記載してください。

### 4. 検査結果と、意味の点検を分けて報告させる

| 項目 | 自動で確かめられること | 差分やコードで確かめること |
| --- | --- | --- |
| R1 命名 | 有効な命名検査があれば名前の書式 | `loadSettings` が実際に設定を読み込むか。外部で使われる名前を壊していないか |
| R2 再利用 | 検査があれば禁止した読み込み先など | `readJson` の入力・出力・失敗時の動作が今回と合うか。検索で見つけただけでは判断できない |
| R3 依存追加なし | 設定済みなら依存ファイルの変更検査 | 新しい読み込み先、依存ファイルや同梱コードの追加。依存ファイルだけ見ても十分とは限らない |
| 設定の動作 | 対象のテストに書かれた入力と期待結果 | テストが今回の変更と必要な失敗ケースを扱っているか |

例えば、AIから次のような点検結果を受け取ります。これは報告形式の例で、実際の実行結果ではありません。

```text
R1: loadSettingsを追加。名前の書式は命名検査で成功。
    関数本体と呼び出し元を確認し、設定読込を担当することを確認。
R2: src/io/readJson.jsのreadJsonを利用。
    入力・返す値・失敗時の動作を確認し、同じJSON読込処理は追加していない。
R3: 依存ファイル、追加ファイル、読み込み先の差分を確認。外部依存の追加なし。
確認: format:check、lint、test:settingsを実行して成功。
未確認: 実際の画面操作による動作確認。
```

「ルールを読みました」だけでは遵守の根拠になりません。あなたも報告された箇所を差分と照合してください。検査が全成功でも、検査対象外の規則、名前の意味、設計の適切さまで確認済みとは扱わないでください。

検査に失敗したら、今回の変更が原因か、作業前からの問題かを分けさせます。今回の違反は直し、既存の別の問題は場所と影響を報告させます。関係のないファイルまで整形・修正してはいけません。自動の書き換えを使う場合も、その差分を確認させてください。

## ルールを長くせず、食い違いを防ぐ

共通の規則は一か所へ置き、フォルダー固有の規則はその場所に追加します。必須と推奨を区別し、参考コードだけから禁止事項を作らせないでください。ルールの例外は、誰が認めたか、対象範囲、理由を記録し、別の作業へ広げません。

本文と検査設定が食い違う場合は、既に決まっている優先順位や例外を確認させます。決まっていないなら、人がどちらを正しい規則にするか決め、説明と設定をそろえます。AIに検査が通りやすい側を勝手に選ばせないでください。

毎回指摘する決まりだけを具体化し、古いパスや不要な例を更新・削除します。すべての機能の規則をルートへ詰め込まず、対象の規則と確認方法への短い案内にしてください。

## コンテキスト使用量が減る理由と限界

決まりと点検手順の場所を一度決めると、毎回長い規則を言い直したり、違反の指摘と修正を往復したりする必要を減らせます。機械で判定できることは検査に任せ、AIには問題箇所と今回適用する規則を読ませることで、無関係な規則や大量の成功ログを渡す量も抑えられます。

指示書の読み込みと点検にも入力を使います。すでに読み込まれた指示を再添付したり、全規則を報告へ丸写ししたりすると使用量が増えます。報告は項目と根拠・結果に絞り、失敗ログは診断に必要な部分を残してください。読む量を減らすために必須の検査や根拠を省いてはいけません。遵守や削減量は保証されず、このリポジトリでは削減量を実測していません。

## 補助ツール

新しい道具を入れる前に、プロジェクトで既に使っている設定と検査で足りるか確認してください。以下は使える仕組みの例です。

- **[EditorConfig](https://editorconfig.org/):** `.editorconfig` の設定を対応するエディターへ伝え、空白や改行をそろえます。コードの意味や規則全体の検査には使えません。対応していないエディターでは設定が適用されません。
- **[Prettier](https://prettier.io/docs/comparison):** 対応言語のコードの書式をそろえます。整形や書式の検査に使えますが、既存部品を再利用する判断までは行いません。
- **[ESLint](https://eslint.org/docs/latest/use/core-concepts/):** 設定された規則に沿ってJavaScriptなどのコードを調べ、違反を表示します。有効な規則と対象範囲に限って使えます。書式確認だけでは扱えない問題も検査できますが、プロジェクトのすべての決まりを判定するわけではありません。
- **[Gitのコミット前の処理](https://git-scm.com/docs/githooks):** コミット前などに既存の検査を呼び出せます。設定されて実際に呼ばれた検査だけが対象です。**[pre-commit](https://pre-commit.com/)** はその設定と実行をまとめるツールです。初回に検査用の環境やプログラムを取得する場合があるため、追加環境を減らしたい場合は導入済みの検査で足りるか先に確認してください。
- **共有先の自動検査:** 変更を送ったときに、設定された検査やテストを実行します。手元での実行忘れに備える用途に使えますが、設定した実行条件と検査範囲に限られます。未実行や対象外は成功とは別です。

## この手法について

自分が加えた変更を規則と照らして確かめることを**自己レビュー**と言います。コードを実行せずに書き方や構造を調べる検査を**静的解析**、そのうち規則違反などを指摘する道具を**リンター**、書式をそろえる道具を**整形ツール**と呼びます。共有先で変更に応じた検査を自動実行する仕組みは**CI（継続的インテグレーション）**と呼ばれます。

この文書は、既存の指示書、自己レビュー、自動検査を組み合わせた運用例です。特別な名前の新しい手法や、特定のAI製品が必要な方法ではありません。
