# 提示された設計案をプロジェクトの根拠で比較する

「A案とB案のどちらがよい？」とAIへ聞いたとき、一般的な長所と短所だけが返ってきても、今のプロジェクトでどちらを選ぶべきかは決まりません。必要なのは、候補を増やすことではなく、**同じ判断基準で、現在の仕様・コード・設定・テストを根拠に比べること**です。

この方法は、依頼者がすでに少数の候補を持っているときに使います。AIは候補ごとに必要な原典を調べ、確認できた事実、事実からの推論、まだ分からない点を分けて比較します。

AIへ最終決定まで任せる必要はありません。人が決める場合は、AIには根拠付きの推薦までを担当させます。

## 使う場面

次のようなときに使えます。

- 設定の保存先をJSONファイルにするかSQLiteにするか迷っている
- 既存の処理を拡張するか、新しいモジュールを作るか比べたい
- 同期処理のままにするか、非同期処理へ変えるか検討したい
- 二つか三つのライブラリ候補を、現在の制約に照らして選びたい
- 既に人が考えた案のうち、どれが現在の設計へ合うか確認したい

候補が一つしかなく、採用条件も明らかな小さな変更では、比較表を作る必要はありません。反対に、候補そのものが分からない場合は、この文書を使う前に目的と制約から候補を作る作業が必要です。

## 1. 候補と、変えられない条件を先に渡す

AIへ、少なくとも次の内容を渡してください。

- 比較する候補
- 達成したいこと
- 必ず守る条件
- 変えてよい範囲
- 候補を増やしてよいか
- AIは推薦までか、最終決定まで担当するか

たとえば、次のように依頼します。

```text
設定の保存方法を比較してください。

候補:
A) 現在のJSONファイルを使い続ける
B) SQLiteへ移す
C) サーバーへ保存する

目的:
設定項目を増やしても保守しやすくする。

必ず守る条件:
- 通信できない状態でも設定を読めること
- アカウント作成を必須にしないこと
- 既存利用者の設定を失わないこと

候補は増やさないでください。
まず比較に必要な仕様・コード・設定・テストを調べてください。
推薦はしてください。最終決定は私が行います。
```

候補を増やしてよいかを指定しないと、AIが比較途中で別案を追加し、最初に比べたかった案が埋もれることがあります。候補外の方法が必要だとAIが判断した場合は、勝手に採用せず「提示された案では条件を満たせない理由」として報告させます。

## 2. 一般論ではなく、今回の判断基準を作る

比較基準は、候補の一般的な特徴から先に作るのではなく、今回の目的と必須条件から作ります。

上の例なら、次のような観点が必要です。

| 判断基準 | 何を確認するか |
| --- | --- |
| オフライン利用 | 通信なしで読み書きできるか |
| 既存データとの互換性 | 現在の設定形式と移行処理がどうなっているか |
| 現在の実装との整合 | 既存の保存・読込処理を再利用できるか |
| 依存関係 | 新しいライブラリや実行環境が必要になるか |
| テストへの影響 | 既存テストのどこが変わり、新しい確認が必要か |
| 保守負担 | 追加するコード・移行処理・運用が何か |

「人気」「新しい」「高性能」といった一般的な言葉を、そのまま判断基準にしないでください。今回の要求に関係する意味へ落とします。

性能が本当に重要なら、「起動時の設定読込が何ミリ秒以内である必要があるか」のように、必要な条件と測定方法を確認します。測っていない性能へ、AIに勝手な点数を付けさせません。

## 3. 候補ごとに必要な原典を調べる

AIには、候補ごとに次のような原典を探させます。

- 現在の仕様
- 設計文書や決定記録
- 関連する実装
- 設定ファイル
- 呼び出し元
- 関連テスト
- 依存関係を管理するファイル
- 必要なら実行結果や計測結果

「A案の根拠はREADME、B案の根拠は一般知識」のように、候補ごとに根拠の質を変えないでください。同じ基準で比べる項目には、できるだけ同じ種類のプロジェクト内根拠を使います。

AIへは、調べた内容と一緒にファイル名や該当箇所も返させます。

```text
各候補を比べるために確認した仕様・コード・設定・テストを、
ファイル名と該当する節・関数名付きで示してください。
検索結果の一覧だけで判断せず、採用判断に使う箇所は原文を確認してください。
```

このリポジトリの[必要な確認を先に決める](../必要な確認を先に決める.md)も、判断に必要な根拠を先に決める方法として使えます。

## 4. 事実・推論・不明点を分ける

AIの比較結果では、少なくとも次の三つを分けてください。

### 確認できた事実

仕様、コード、設定、テスト、実行結果などから直接確認できることです。

例:

```text
事実: docs/settings.md に「通信なしで設定を読めること」が必須条件として書かれている。
事実: src/settings/store.py は現在JSONファイルを読み書きしている。
事実: requirements.txt にSQLite用の追加パッケージはない。
```

### 根拠からの推論

確認した事実を組み合わせて、候補への影響を考えた結果です。

```text
推論: C案のサーバー保存だけでは、通信なしで設定を読む条件を満たせない。
推論: A案は現在の保存処理を再利用できるため、移行作業はB案より小さい可能性が高い。
```

推論は事実と同じ欄へ混ぜません。「可能性が高い」「この条件なら」のように、どこまで確認できたかを残します。

### 不明点

資料を読んでも分からないこと、実測しないと決められないことです。

```text
不明: 設定件数が今後どこまで増える予定か。
不明: SQLiteへ移した場合の起動時間は未計測。
```

不明点が推薦を変える可能性がある場合は、AIに追加調査または利用者への質問を出させます。

## 5. 全候補を同じ観点で並べる

比較表は、候補ごとに違う長所を自由に列挙するのではなく、同じ行で見比べられる形にします。

架空のプロジェクトで、先ほどの原典を確認した後の例です。

| 判断基準 | A: JSON継続 | B: SQLite | C: サーバー |
| --- | --- | --- | --- |
| オフライン利用 | 現在の実装で対応 | 端末内DBなら対応可能 | サーバーだけでは必須条件を満たさない |
| 既存データ | 現形式を継続できる | JSONからの移行処理が必要 | ローカル設定から送信形式への移行が必要 |
| 現在の実装 | 保存・読込処理を再利用可能 | 保存層の変更が必要 | 通信・認証を含む新しい処理が必要 |
| 依存関係 | 追加なし | 利用するSQLite実装の確認が必要 | 通信先と認証方式が必要 |
| 未確認 | 設定数増加時の保守性 | 実データ量での性能 | サーバー運用条件 |

この表だけで結論を出さず、重要なセルには元の仕様やコードの場所を併記してください。

候補に点数を付ける場合は、評価尺度と重みを誰が決めたかを明記します。根拠のない「A=90点、B=75点」のような数字は比較を正確に見せるだけなので使いません。

## 6. 条件未達と不明点を先に扱う

必須条件を満たさない候補は、「総合点が少し低い案」と同じ扱いにしません。

上の例で「通信なしで使える」が必須なら、サーバーだけへ保存するC案は、そのままでは候補条件を満たしません。AIには次のように報告させます。

```text
C案は必須条件「通信なしで設定を読める」を満たしません。
この条件を変更しない限り、C案を推薦対象から外します。
```

また、どの候補も条件を満たさない場合は、無理に一つを推薦させません。

```text
提示されたA〜C案はいずれも必須条件Xを満たしません。
候補外の案を追加してよければ、条件を満たす方法を別途提案します。
```

## 7. 推薦には、推薦が変わる条件も付ける

AIの推薦は、次の形にすると確認しやすくなります。

```text
推薦: A案

理由:
- 必須条件のオフライン利用を現在の実装のまま満たす
- 既存データの移行が不要
- 新しい外部依存を追加しない

弱点:
- 設定項目が大きく増えた場合の保守性は未確認

推薦が変わる条件:
- 設定を複数プロセスから同時更新する必要が出る
- 現在のJSON形式では扱えない検索・更新要件が追加される
```

推薦だけでなく、どの前提が崩れると別案になるかを示すと、利用者は結論の適用範囲を確認できます。

## AIへの依頼例

```text
次の候補から、現在のプロジェクトに最も合う案を推薦してください。

候補:
A) ...
B) ...
C) ...

目的:
...

必ず守る条件:
...

変更してよい範囲:
...

候補は増やさないでください。
最終決定は私が行います。

まず、比較に必要な判断基準を目的と必須条件から整理してください。
次に、各基準を確認するための仕様、設計文書、コード、設定、テストを調べ、
判断に使ったファイルと箇所を示してください。

全候補を同じ基準で比較してください。
確認できた事実、事実からの推論、不明点を分けてください。
根拠のない点数や重み付けは使わないでください。

不明点によって推薦が変わる場合は、追加で確認する資料か質問を示してください。
必須条件を満たさない候補は明示してください。
すべての候補が条件を満たさない場合は、無理に一つを選ばないでください。

最後に、推薦、根拠、弱点、推薦が変わる条件、未確認事項をまとめてください。
```

## 人が推薦を確認する

最終決定を人が行う場合、少なくとも次を確認してください。

1. 依頼時に渡した候補が勝手に変わっていないか。
2. 必須条件が比較表から抜けていないか。
3. 全候補を同じ観点で比べているか。
4. 重要な主張にプロジェクト内の根拠があるか。
5. 事実と推論が混ざっていないか。
6. 測っていない性能や工数へ架空の数値を付けていないか。
7. 不明点で結論が変わる場合、その条件が示されているか。
8. 条件を満たさない案を、雰囲気のよい総合評価で残していないか。

推薦を採用した後、その理由を将来の作業でも使う場合は、[仕様や実装を決めた理由をAIに渡す](仕様や実装を決めた理由をAIに渡す.md)の方法で決定と理由を記録してください。この文書は**決める前の比較**を扱い、決定理由の文書は**決めた後の記録と再利用**を扱います。

## コンテキストを減らせる理由と限界

候補、目的、必須条件を先に決めると、AIは「考えられる全設計」を調べる必要がありません。比較基準を決めた後は、その基準を確認する仕様・コード・設定・テストへ調査を絞れます。

また、結論と根拠を一緒に返させると、「なぜAなのか」「Bはどこが駄目なのか」を後から何度も聞き直す量を減らせます。

ただし、読む資料を減らしたこと自体は正確さの証明ではありません。比較に必要な条件を落とした場合は、少ないコンテキストでも誤った推薦になります。重要な不明点が見つかったら、その点を解決する資料や実測へ範囲を広げてください。

## 既存の考え方との関係

複数の案を同じ条件で比べる考え方は、システム設計の**Trade Study（トレードスタディ）**でも使われます。NASAのSystems Engineering Handbookでは、代替案を要求・効果・コストなどの基準で評価し、データ源や不確かさを含めて判断を記録する考え方が説明されています。

大きなソフトウェアアーキテクチャの評価には、Software Engineering Instituteの**ATAM（Architecture Tradeoff Analysis Method）**があります。ATAMは性能、変更しやすさ、安全性など複数の品質特性の間にあるリスクやトレードオフを分析します。日常の二、三案の比較へATAMの全手順を持ち込む必要はありません。この文書では、「品質条件を明確にし、案ごとのリスクとトレードオフを同じ観点で見る」という考え方だけを使います。

採用後の判断を残す方法としては、**ADR（Architectural Decision Record）**があります。ADRは決定、その背景、結果を記録する文書で、候補を調べて比較する手順そのものではありません。今回の比較で人が決定した後に、必要ならADRや既存の設計文書へ結果を残してください。

- [NASA Systems Engineering Handbook: Decision Analysis / Trade Study](https://www.nasa.gov/reference/system-engineering-handbook-appendix/)
- [Software Engineering Institute: The Architecture Tradeoff Analysis Method](https://www.sei.cmu.edu/library/the-architecture-tradeoff-analysis-method/)
- [AWS Prescriptive Guidance: Architectural decision record process](https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/adr-process.html)
