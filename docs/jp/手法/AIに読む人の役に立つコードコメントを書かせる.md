# AIに読む人の役に立つコードコメントを書かせる

AIに「コメントを付けて」と頼むと、`値を取得する`、`結果を返す`のように、コードを言い換えただけの説明が増えることがあります。一方で、短くしようとして必須の宣言コメントを消したり、実装から推測した理由を事実として書いたりする場合もあります。

先にコメントの規則と読者を渡し、その人がコードだけでは分からない情報を書かせます。関数を使う人には入力や結果の約束を、実装を直す人には理由や守る条件を伝えると、必要な説明を絞れます。

## 使う場面と判断基準

- 他のコードから使われる関数なら、入力の単位、返す値、失敗時の動作など、使う側が知る必要のあることを書かせます。
- 実装の中に、順番を変えると壊れる処理、互換性のために残した分岐、単位や値の特別な意味があるなら、その条件と根拠を書かせます。
- 名前とコードからすぐ分かる説明は、コメントが必須でなければ追加しなくて構いません。必須なら削らず、その宣言の役割や入力・結果を短く具体化します。
- 古いコメントと実装が違う場合は、コメントを実装へ合わせるだけで済むか、実装が本来の仕様からずれているかを先に確認させてください。

## 使うときの手順

### 1. コメント規則と、読む人を指定する

AIに対象ファイルへ適用される指示書、コメント規則、近くのコメント例を読ませます。例は書き方の参考にし、規則と違う古いコメントまで正しい決まりにしないでください。

規則がない場合は、例えば `docs/development/comment-rules.md` に、チームで決めた対象・言語・必須項目・確認方法を保存できます。既に `CONTRIBUTING.md` などに規則があるなら、その場所を使います。詳しい規則を複数のファイルへコピーしないでください。

`AGENTS.md` などAIが読む入口には、例えば次の参照を置きます。

```text
コードを追加・変更するときは docs/development/comment-rules.md を読む。
使う人に必要な説明と、実装を直す人に必要な理由を分け、
変更したコードと既存コメントの一致を点検する。
```

依頼には「この関数を呼び出す開発者向け」「この処理を後で直す開発者向け」のように、コメントの読者も指定してください。規則に形式、必須箇所、使用言語が定められていれば、それを先に守らせます。

このリポジトリでは[Issue #51](https://github.com/tomiya7688/ai-context-reducer/issues/51)で、`tools/` の宣言直前に日本語の構造化コメントを置き、内部の説明は通常の日本語コメントにする方針を定めています。この方針を別のプロジェクトやすべての言語へ一律に当てはめません。対象プロジェクトの正式な規則と、その時点で使える検査を確認してください。

### 2. コメントの場所ごとに、書く情報を決める

| 説明する場所 | 読む人が知りたいこと | 書く内容の例 |
| --- | --- | --- |
| 関数や型の宣言 | 何を任せられ、どんな条件で使えるか | 入力の意味・単位、返す値、状態を変えるか、失敗時の動作 |
| 処理の途中 | なぜその順番や値を使うか、何を変えると壊れるか | 互換性の制約、順番を守る理由、常に成立させる条件 |
| 詳しい設計の説明がある箇所 | どの判断がここへ関係するか | 必要な理由を一文で書き、詳しい説明の節へ参照を置く |

コメントを読むたびに別の文書を開かなくても必要な意味が分かるよう、重要な条件はコメントにも短く残します。長い設計経緯は説明文書へ置きます。

以下は架空のPythonプロジェクトの例です。このリポジトリの形式規則を示すものではありません。説明する動作は、対象のコードと仕様で確認できたものとします。

関数を使う人向けの説明なら、次の違いがあります。

```python
# 修正前: 名前の言い換えだけ
def read_timeout(settings):
    """待ち時間を取得する。"""
    ...
```

```python
# 修正後: 呼び出す人に必要な約束を示す
def read_timeout(settings):
    """設定から待ち時間を秒単位で返す。未指定なら30秒、0以下ならValueError。"""
    ...
```

ここで分かるのは単位、未指定時の値、0以下の扱いです。`...` は省略した実装を表します。名前や引数一覧を繰り返すだけでは、これらは分かりません。

内部コメントでは、例えば設計文書に「旧版では省略時に30秒待つため、互換性を保つ」と記録されている場合、その理由を反映します。

```python
# 修正前: 次の行を言い換えただけ
# 設定から待ち時間を取得する。
timeout = settings.get("timeout_seconds", 30)
```

```python
# 修正後: 値を変える前に知っておくべき理由
# 旧版の設定でも動作を変えないよう、省略時は従来の30秒を保つ。
timeout = settings.get("timeout_seconds", 30)
```

コードに30とあるだけでは、互換性のために選んだとは分かりません。理由の記録がなければ、AIに過去の判断を想像させず、[仕様や実装を決めた理由をAIに渡す](仕様や実装を決めた理由をAIに渡す.md)のように根拠を確認してから渡してください。分かる動作だけを書き、理由が不明なら作業報告へ残します。

### 3. 追加・更新・削除を判断させる

| 状態 | AIにさせること |
| --- | --- |
| 必須箇所にコメントがない | 規則の必須項目を、その宣言固有の意味で記入する。空のひな型は残さない |
| 重要な単位・制約・理由がコードだけでは分からない | 根拠を確認して短く追加する |
| 動作や条件が変わり、説明が古い | 正しい仕様と実装を確認して、今回の変更と一緒に更新する |
| 処理をそのまま言い換えた説明がある | 必須か確認し、必須なら具体化する。不要で削除可能なら削る |
| コメントとコードが食い違う、理由の根拠が見つからない | 正しい動作や理由を確認する。判断できなければ、その不明点を報告する |

宣言ごとに説明を求めるプロジェクトでは、「自明だから不要」と判断して消させないでください。例えば責務、主な処理、引数、戻り値が必須なら、それぞれに今回の宣言が何を担当し、何を受け取り、何を返すかを書かせます。「処理を行う」のような共通の埋め草で項目数だけ満たしても役に立ちません。

### 4. 作業前の指示と、変更後の点検をまとめて渡す

次のパスは、自分のプロジェクトにあるファイルへ置き換えてください。

```text
src/settings/reader.py の変更箇所のコメントを点検・修正してください。
まず適用される指示書と docs/development/comment-rules.md を読み、
必須箇所・項目・言語・形式を確認してください。近くの例は参考にし、古い例を規則にしないでください。
宣言の説明はこの関数を使う開発者向け、内部の説明は後で実装を直す開発者向けです。
変更した処理、使う側、関係する仕様とテストを確認してください。
今回の作業はコメントの修正に限り、実装は変更しないでください。

各コメントで「読む人がコードだけでは分からない何を知れるか」を確かめてください。
必須の説明は削除せず、役割・入力・結果などを具体的に書いてください。
理由や保証は根拠のあるものだけを書き、不明なら報告してください。
コメントと実装が食い違い、どちらが正しいか判断できなければ、その箇所の修正は進めず質問してください。
規則が競合し、明示された優先順位でも解決できなければ、該当箇所を示して質問してください。

変更後は差分を規則と照らし、必須項目、内容の有用さ、実装との一致を点検してください。
既存のコメント検査があれば、対象と実行方法を確認して実行してください。
追加・更新・削除した場所、読者が知れることと根拠、検査結果、未確認箇所を短く報告してください。
未実行や検査対象外を成功と報告しないでください。
```

ファイルを読めないチャットには、規則、対象のコードと使う側、必要な仕様、変更差分を添付するか貼り付けます。パスだけでは内容は渡りません。AIが検査を実行できなければ、あなたが結果を渡すか、未実行と報告させます。

例えば次のように点検結果を受け取れます。これは報告の例で、実行した検査結果ではありません。

```text
reader.py / read_timeout の説明を更新:
  呼び出す人が単位、未指定時の値、0以下の扱いを知れる。
  根拠: 関数本体、呼び出し元、設定仕様と対応テスト。
既定値の内部コメントを更新:
  30秒を維持する理由を短く記載。根拠: 設計文書の互換性の節。
形式検査: 既存のコメント検査を実行して成功。対象は必須項目の存在と記法。
未確認: 内容が初めて読む開発者に十分伝わるかは、読者による確認が必要。
実装の差分: なし。
```

一般的な規則の保存や変更後の点検は[AIにコードの決まりを読ませ、変更後に確かめさせる](AIにコードの決まりを読ませ、変更後に確かめさせる.md)でも説明しています。同じ規則本文をコメント用の手順へコピーする必要はありません。

## 完成したか確かめる

AIに必須項目の有無だけでなく、本文と根拠の対応も確認させます。あなたも重要な約束や理由を元の資料と照らしてください。

- **形式:** 対象宣言、必須項目、使用言語、記法が規則どおりか。自動検査があれば、その検査範囲で確かめる。
- **内容:** その宣言固有の役割、使う条件、理由を知れるか。空欄や同じ埋め草がないか。
- **一致:** 入力・戻り値・エラー・変更する状態が実装と合うか。仕様と実装の不一致をコメントの書き換えで隠していないか。
- **根拠:** 設計上の理由や「必ず成功する」などの保証を推測していないか。
- **範囲:** 不要なコメントを大量に増やしていないか。今回の依頼にない実装変更が混ざっていないか。

形式検査の成功だけでは、有用さや事実の正しさまで判定できません。コメント数や文字数が増えたことを成果にせず、読む人が使い方や変更時の注意を判断できるかで確認してください。

## コンテキスト使用量が減る理由と限界

規則と読者を先に渡し、変更箇所のコメントを点検させると、形式や不足した説明を人が何度も指摘する会話を減らせます。短いコメントに重要な条件があれば、使い方を知るためだけに関数全体や過去の議論を毎回読む必要も減ります。

コメントを追加すれば、その分の入力も増えます。長い設計経緯や自明な説明を各宣言へ繰り返すと逆効果です。必要な約束と理由を短く残し、詳しい経緯は一か所へ置いてください。実装を確認すべき作業ではコメントだけで済ませず、元コードやテストを読みます。このリポジトリでは削減量を実測していません。

## 補助ツール

- **既存のコメント検査:** コメントの存在や必須項目、記法を調べます。規則で求められる形式の確認に使えますが、説明の有用さは別に点検します。
- **エディターの関数説明表示:** 宣言に付いた説明を表示します。使う側が必要な情報へ進めるかの確認に使えます。表示される形式は言語やエディターによって違います。
- **Gitの差分表示:** コメントと実装の変更を並べて確認できます。説明の更新漏れや、コメント修正に実装変更が混ざっていないか探せます。

## この手法について

宣言の近くに使い方や条件を記して、利用する人へ見せる説明を**ドキュメントコメント**と呼びます。Pythonで関数などの先頭へ置く説明用文字列は**docstring**と呼ばれます。

[Goのコメントガイド](https://go.dev/doc/comment)は、使う側に必要な動作や結果を宣言の説明へ、内部の詳細を処理内のコメントへ分けています。[PythonのPEP 257](https://peps.python.org/pep-0257/)は、動作、引数、戻り値、副作用、例外、利用条件などの説明を扱います。[GoogleのC++ガイド](https://google.github.io/styleguide/cppguide.html#Comments)は、自明なコードの言い換えを避け、分かりにくい処理の意図を説明する考え方を示しています。副作用とは、戻り値以外にファイルや状態などを変えることです。

これらは言語や組織ごとの指針です。例えばGoとPythonでは説明文の書き出しも異なるため、記法や必須箇所を一律に移植せず、対象プロジェクトの規則を優先してください。
