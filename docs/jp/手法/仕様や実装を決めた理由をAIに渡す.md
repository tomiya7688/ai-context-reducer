# 仕様や実装を決めた理由をAIに渡す

「設定は端末に保存する」とだけ伝えると、AIは別の保存方法へ変えてよいか判断できません。「通信できないときも使え、アカウントを作らず設定を保つために端末へ保存すると決めた」と伝えると、今回も守る必要がある条件を確認させられます。

コードから分かる現在の動作と、過去にその動作を選んだ理由は別です。理由は決定したときの記録へ残し、作業依頼では今回関係する記録だけをAIに読ませてください。

## 使う場面を決める

- **保存方法や外部との受け渡しを変える**：オフライン利用、既存データとの互換性など、現在の選択を支える理由を読ませます。
- **既存の実装を別の方法へ置き換える**：起動時に一度だけ読み込む理由など、処理のタイミングや構成を選んだ事情を確認させます。
- **同じ判断を何度も調べ直している**：過去の会話や履歴を毎回渡す代わりに、決定と理由の記録へ案内します。

理由が今の変更に影響しない誤字修正などでは、設計の記録を全部読ませる必要はありません。今回変える動作や守る条件に関係する決定を一つ選ぶところから始めてください。

## 1. 目的・仕様・理由・根拠を分けて記録する

次は架空の設定機能の例です。自分のプロジェクトでは、実際の決定と確認できる資料へ置き換えます。

| 記録すること | 例 |
|---|---|
| 目的 | 次回起動時も、利用者が選んだ言語を使えるようにする |
| 決めた仕様・実装 | 選んだ言語を端末の設定ファイルへ保存し、起動時に読み込む |
| 守る条件 | 通信できなくても使える。アカウント作成を求めない |
| 決めた理由 | サーバーへ保存する案では通信やアカウントに依存するため、端末への保存を選んだ |
| 根拠の場所 | オフライン利用の要求がある仕様書の節と、その案を採用したIssueの決定箇所 |
| 状態・確認日 | 確定 / [決定を確認した日] |
| 影響や制限 | 別の端末へ設定を自動で引き継ぐ機能は含まない |

同じ機能でも、保存場所を選ぶ理由と、読み込むタイミングを選ぶ理由は分けます。たとえば「画面を作る前に表示言語を決める必要があるため、起動時に読み込む」は実装のタイミングを選んだ理由です。その理由を確認した記録も一緒に残してください。

決めた内容と理由、前提、状態を記録する考え方は、[TyreeとAkermanの論文](https://personal.utdallas.edu/~chung/SA/zz-Impreso-architecture_decisions-tyree-05.pdf)でも扱われています。本書の項目は、今回の作業へ渡しやすいよう簡略化したものです。[1]

保存形式がソースに書かれていても、それだけで「オフライン利用のために選んだ」という過去の理由は確定できません。AIに理由の案を整理させる場合も、決定した人の確認や当時の記録で裏付けが取れない説明は「未確認」として残します。

## 2. 繰り返し使う理由と今回だけの理由の置き場所を決める

| 内容 | 置く場所 | AIへの渡し方 |
|---|---|---|
| 長く有効な仕様・実装の理由 | 既存の設計文書の該当節。独立した判断なら `docs/decisions/settings-storage.md` など | 今回関係するファイルと見出しを依頼に指定する |
| プロジェクト情報から理由へ進む入口 | [プロジェクト情報のひな型](../../../templates/PROJECT_CONTEXT.md)をコピーした `PROJECT_CONTEXT.md` | 参照先と読む条件だけを書き、理由の全文を複製しない |
| 今回だけの判断や、今回使う決定への案内 | [作業メモのひな型](../../../templates/CONTEXT_PACK.md)をコピーした `CONTEXT_PACK.md`、または今回の依頼文 | 短い理由、状態、根拠の場所を渡す |

設計文書に理由がすでにあるなら、その箇所を使います。別の決定文書を増やす必要はありません。複数の文書へ同じ理由をコピーすると、更新時に食い違いが起きます。作業メモで決めたことが今後も有効になった場合は、利用者が内容を確認して設計文書へ移し、メモにはその参照先を残してください。

新しく記録を作る場合は、次を `docs/decisions/settings-storage.md` などへ保存できます。項目名やファイル名は例です。

```text
# 言語設定の保存方法
状態：[確定 / 提案 / 未確認 / 現在も使えるか要確認]
確認日：[日付]
決定を確認した記録・人：[Issueの該当箇所など]

目的：
決めた仕様・実装：
守る条件：
決めた理由：
理由の根拠：[資料のパスと見出し、決定の記録]
影響・制限：
この決定を見直す条件：
```

## 3. 今回関係する理由を読むようAIへ指定する

文書を置くだけでは、AIがその内容を読んだことにはなりません。ファイルを読めるAIにはパスと見出しを指定します。ファイルを読めないチャットでは、該当する節を添付または貼り付けてください。過去の会話や変更履歴の全文ではなく、決定・理由・状態と必要な根拠の箇所を渡します。

```text
今回の目的：設定画面で選んだ言語を保存し、次回起動時に復元する。
読む資料：docs/decisions/settings-storage.md「言語設定の保存方法」
今回使う決定：通信やアカウントに依存しない端末への保存。

指定した資料で、決めた仕様・理由・状態・根拠を確認してから変更してください。
現在の動作は関連するコードとテストで確認してください。
理由が見つからない場合は、コードから過去の意図を推測せず質問してください。
資料が提案・未確認の状態なら、決定済みの条件として扱わないでください。
理由の前提が現在の仕様と矛盾する場合は、その箇所と必要な確認を報告し、
その判断に依存する変更を進める前に確認してください。
完了時は、使った決定の参照先、守った条件、実行した確認と未確認事項を短く返してください。
```

繰り返し使う場合は、利用中のAIが読む指示書へ「設定の保存方法を変更するときは `docs/decisions/settings-storage.md` の該当節を読む」と書きます。`AGENTS.md` に対応したAIなら、その作業場所に適用されるファイルへ書けます。自動で読まない環境では、毎回の依頼で参照先を指定してください。

## 4. 理由の状態と、現在も当てはまるかを確認させる

- **確定**：決定の記録や確認した人が分かる理由です。今回も前提が当てはまるか、AIに現在の仕様と照らさせます。
- **提案**：これから採用するかを判断する案です。採用済みの条件としてAIに実装させません。
- **未確認**：理由を裏付ける記録がない説明です。AIに事実として補わせず、利用者への質問にします。
- **古い可能性がある**：以前は確定していても、利用環境や要求が変わった状態です。「当時は確定、現在の適用は要確認」と日付を残します。

理由が分からないときは、何を決めるためにその理由が必要かもAIに返させてください。今回に影響しない理由まで探し続ける必要はありません。既存の決定を変える場合は、変更後の理由・根拠・状態を利用者が確認し、古い決定から新しい記録を辿れるようにします。

## なぜ会話で読む量を減らせるのか

関係する決定の場所と理由を先に渡すと、AIに過去の会話や変更履歴を広く読ませて、設計意図を推測させる作業を減らせます。理由の詳細を一か所に置けば、同じ説明をプロジェクト情報と作業メモで読み比べる必要も減ります。

記録の作成と更新には手間がかかります。短い変更に無関係な決定を大量に渡すと、読む量は増えます。同じ判断の調べ直しや理由についての聞き返しが減ったかを確認し、AIへ渡して処理させた情報量を測っていない場合は、削減量を断定しないでください。

## 補助ツール

- [context-pack-builder](https://github.com/tomiya7688/ai-context-reducer/blob/main/tools/common/medium/context-pack-builder/README.md) — 作業の目的・条件やGitの状態をまとめた作業メモを生成します。依頼へ渡すメモの土台を作るときに使えます。過去に決めた理由を自動で確定する道具ではないため、理由と根拠の参照先は確認して補います。

## この手法について

選んだ設計とその理由、前提、状態を明示的に記録する考え方は、TyreeとAkermanの論文で **architecture decisions（設計上の決定）** として紹介されています。[1] 本書では、その記録へAIを案内する利用手順を加えています。論文は、この依頼例やAIとの会話で渡す情報量の削減を検証したものではありません。
