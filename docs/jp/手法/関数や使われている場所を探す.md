# 関数や使われている場所を探す

大きなプログラムから変更する処理を探すときは、関数（名前を付けて呼び出せる処理）や型（データの種類）の定義場所、それらを使う場所を検索できる一覧を使えます。AIに一覧で候補を絞らせ、その場所のコードとテストから調べさせると、無関係なファイルを先に読む量を抑えられます。

一覧は読む場所を見つけるための案内です。現在のコードと一致するかを確かめてから、変更方法や必要な確認を判断させてください。

## 例：設定ファイルがないときの動作を変える

架空の設定アプリで、設定ファイルがない場合に初期設定を使うよう変更するとします。以下のファイル名と関数名は説明用です。

```text
設定を読み込む関数: load_settings
定義があるファイル: src/settings.py
利用する場所の候補: app.py
関連テストの候補: tests/test_settings.py
```

まずAIに `src/settings.py` の定義、`app.py` の利用箇所、`tests/test_settings.py` の期待結果を確かめさせます。設定画面や関係のないライブラリは、必要な関係が見つかった時点で追加します。

たとえば一覧が `app.py` を示していても、現在のコードでは `src/startup.py` に利用箇所が移っているかもしれません。表示された行番号や関数名だけで変更先を決めず、次の手順で照合します。

## いつ使うか

大きなファイルから同じ関数を何度も探す場合や、変更のたびに呼出し元・依存先・テストを探し直す場合に役立ちます。変更先と確認方法がすでに分かる小さな作業なら、普通の検索で十分です。

すでに使っている開発環境が定義や利用箇所を検索できるなら、その結果を使えます。一覧を作り直す手間が調査の短縮を上回る場合は、新しく導入しません。

## 一覧に載る情報と限界

一覧には、たとえば次の情報が載ります。何が得られるかは、利用する解析方法によって異なります。

- ファイル、型、関数などの名前と定義場所
- 関数が呼び出す先、またはその関数を呼び出す場所
- 別のファイルを読み込む関係
- 関連テストを探す手掛かり

一覧には、古い場所が残ったり、処理のつながりが抜けたりすることがあります。設定に書かれた名前で関数を選ぶ仕組みや、実行時に作られるコードなどは、解析だけでは関係を拾えない場合もあります。**一覧に出ないことは、関係がないという証拠にはなりません。**

## 一覧と現在のコードを照合する

利用者は、AIに次の順で確認させてください。自分で調べる場合も同じ順を使えます。

1. **定義を開く。** 一覧のパスから実際の関数や型を開き、今ある名前と処理を確認させます。行がずれていたら現在の定義を検索させます。同名の関数が複数あれば、ファイルと所属する型、入力や戻り値を比べ、対象を特定させます。
2. **利用箇所を開く。** 実際にどの定義を読み込み、何を渡し、戻り値やエラーをどう扱うかを確認させます。一覧にある名前が同じでも、別の関数を使っていないか確かめさせます。
3. **関連テストを開く。** 何を入力し、どの結果を正しいと判定しているか確認させます。対象の動作を扱っているかを読み、ファイル名が似ているだけで関連テストと決めないようにします。
4. **不足する関係を加える。** 呼出し先、共通処理、設定、別の利用箇所が見つかったら、その定義と関連テストを調査先へ加えさせます。一覧にない関係はパスと根拠を残させ、更新できる一覧なら生成元の情報や現在のコードから作り直させます。

上の設定アプリなら、次の内容を照らし合わせます。

| 開く場所 | 確かめること | 別の関係が見つかった場合 |
| --- | --- | --- |
| `src/settings.py` | ファイルがない場合に例外を返すのか、初期設定を返すのか | 読込みを別の関数へ任せているなら、その定義も読む |
| `app.py` | 対象の `load_settings` を使っているか。例外や初期設定をどう扱うか | 利用箇所が移っていれば移動先を読む。別の利用側も影響するなら加える |
| `tests/test_settings.py` | ファイルがある場合・ない場合の入力と期待結果 | 必要な条件を扱うテストがなければ、確認不足として報告する |

テストを読むことで分かるのは、書かれている期待結果です。現在成功しているかは、実行結果がある場合にだけ分かります。定義や利用箇所を特定できない場合も未確認として残し、一覧だけから原因・影響範囲・安全性を断定させないでください。

調査先を広げる基準は、変更する動作が別の処理へ委ねられている、別の利用側の期待が変わる、必要な条件を確かめるテストが見つからない、といった具体的な不足です。無関係なファイルを追加して埋め合わせるのではなく、その不足に答える場所を探させます。

## AIへ渡す場所と依頼例

一度だけなら、一覧の関係する部分と変更の目的を依頼へ添付し、上の照合手順を伝えます。ファイルを開けるAIなら、一覧の保存先とコードの場所を指定できます。開けないチャットなら、候補のコードやテストも必要な範囲を添付・貼り付けます。パスだけでは内容は渡りません。

繰り返し使うなら、索引の保存先と更新方法を既存の開発案内へ書きます。新しく案内を置く場合は、たとえば `docs/コードの探し方.md` にまとめ、利用中のAIが読む指示から「定義や利用箇所を探すときに参照する」と案内します。`AGENTS.md` などの自動読込みの有無は、使う環境で確認してください。

```text
設定ファイルがない場合に初期設定を使う変更を考えています。
添付した一覧から load_settings の定義、利用箇所、関連テストの候補を探してください。
実際の定義と利用箇所を開き、入力・戻り値・エラーの扱いを確かめてください。
関連テストも開き、対象の条件と期待結果を確認してください。

一覧にない呼出し先や利用側が見つかったら、そのコードと関連テストを調査先へ加えてください。
古いパスや欠けた関係、特定できない箇所は根拠付きで報告してください。
まず変更候補と必要な確認を示し、一覧だけで原因や影響範囲を決めないでください。
読んだ場所、実行した確認と結果、未確認事項を分けて報告してください。
```

## なぜ読む量が減るのか

一覧から候補へ進めば、AIに全ファイルを開かせて定義やつながりを推測させる調査を減らせます。候補をコードとテストで照合することで、古い案内や別の同名関数に基づく修正、その後の調べ直しを避けやすくなります。

一覧の作成・更新と照合にも手間がかかります。必要なコードやテストまで省かず、関係が分かった場所だけ追加で読ませてください。一覧が短いだけでは使用量の削減を証明できないため、読込み記録や、計測できる場合は入力使用量で比較します。

## 補助ツール

- [source-structure-index](../../../tools/common/large/source-structure-index/README.md)：既存の解析結果をまとめ、名前や変更ファイルから定義・参照・依存関係の候補を返します。必要な周辺情報だけを取り出すために使えます。得られる関係は元の解析結果に依存するため、呼出し元などが常にすべて分かるわけではありません。
- [Tree-sitter](https://github.com/tree-sitter/tree-sitter)：コードの構文（文法上の構造）を調べます。定義などを探す材料に使えます。
- [SCIP](https://github.com/scip-code/scip)：定義や参照の索引を共有するための形式とツールです。既存の解析結果を利用する際に使えます。

## この手法について

コードの定義場所や参照関係を検索できる形にまとめ、必要な元コードへ案内する一覧を、コード構造の索引（Source Structure Index、symbol index）と呼びます。
