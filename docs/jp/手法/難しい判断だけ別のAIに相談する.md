# 難しい判断だけ別のAIに相談する

設定の変更やテストの実行は順調でも、「保存方法を作り直すべきか」「二度失敗した修正方法を続けてよいか」といった判断では、間違った方針を選ぶと作業全体をやり直すことがあります。かといって、最初から最後まで最も高価なモデルで作業する必要があるとは限りません。

この手法では、**通常の調査と実装を担当するAIが、重要で判断の難しい場面だけ別のAIへ相談します**。助言するAIは、前提・別案・見落とし・判断が変わる条件を調べ、担当AIへ指摘を返します。担当AIは助言をそのまま正解とせず、原典と検査結果を確かめてから続行します。[1][2]

相談を受けるAIを、ここでは**助言担当AI**と呼びます。相談を決めるのは、あなたがあらかじめ指定した条件や、作業中の担当AIが観測した行き詰まりです。複数モデルを使える環境なら高性能なモデルへ相談できますが、**別モデルであるだけで独立性や正確さが保証されるわけではありません**。あなたは最終的に、必要な承認、変更差分、テスト結果を確認してください。

この手法は、考える量を作業に合わせる[AIに無駄な推論と再試行をさせない](AIに無駄な推論と再試行をさせない.md)方法と関連します。既に決まっている複数案を同じ根拠で比べる場合は、[提示された設計案をプロジェクトの根拠で比較する](提示された設計案をプロジェクトの根拠で比較する.md)も参照してください。

## 1. まず何を分担するのか

| 担当 | 役割 | やってはいけないこと |
| --- | --- | --- |
| **あなた** | 目的、必須条件、許可する操作、相談を使う場面、完了条件を決める | 「助言があった」をテストや承認の代わりにする |
| **作業担当AI** | 原典を調べ、コードを変更し、検証し、必要なときだけ相談する | 根拠なしに助言へ従う、相談だけで成功と宣言する |
| **助言担当AI** | 選びかけた方針を検査し、反例・別案・不足する根拠・次の確認を指摘する | 実際には読めないファイルや実行していないテストを「確認済み」とする |
| **元の資料と検査** | 現在の仕様・コード・テスト・実行結果で主張を確かめる | AIの意見だけで置き換える |

担当AIと助言AIの話し合いは、ソフトウェアの変更を自動的に安全にする仕組みではありません。例えば、公開APIや保存形式を変更する場合は、実際の利用側や移行手順も確認する必要があります。

## 2. 相談するかどうかの判断手順

難しそうに見えるだけで毎回相談すると、相談相手も同じ資料を読み、費用と時間が増えます。次の順で判断できます。

```text
今回必要な仕様・コード・テストの根拠があるか
  ├─ ない → まず該当する原典を調べる（相談だけで穴を埋めない）
  └─ ある
       ↓
いつもの方法で安全に判断・実行できるか
  ├─ できる → 作業担当AIが進め、必要なテストをする
  └─ できない／影響が大きい
       ↓
重要な設計分岐・矛盾・再試行の行き詰まり・完了判断に
別の見方が必要か
  ├─ 必要 → 助言担当AIへ、判断の論点と根拠を渡して相談
  └─ 不要 → 不明点を人へ確認するか、必要な実測を先に行う
       ↓
助言の主張を元の資料・テストで検査する
       ↓
必要な承認を得て続行する／止まる
```

**相談が役立ち得る場面**は、互いに矛盾する仕様、複数箇所へ波及する設計の選択、新しい原因が見つからない繰返しの失敗、変更完了前の重大な見落とし確認などです。**相談しなくてよい場面**は、対象と変更方法が明らかな短い修正、検査結果で次の操作が既に決まっている仕事、別のAIに渡す根拠がまだない場合です。[1]

失敗が繰り返されるときも、**同じ入力で何も変えずに同じコマンドを実行しただけなら、まずその反復を止めてください**。新しい仮説や判断の分岐があり、別の視点で評価する価値があるときに相談します。相談のために必要な情報がまだ足りなければ、先にその情報を取得します。

## 3. 例：設定の保存方法を変更するか

架空のアプリで、保存した設定が再起動後に消える問題を直します。あなたは、**オフラインで動くこと、既存データを失わないこと、関連テストに通ること**を必須条件にします。

- **調査：** 作業担当AIが保存処理、起動時の読込み処理、設定形式、テストを探します。以前のコードの版も確認します。
- **分岐：** 現在のJSON保存を修正する案と、データベースへ移す案が候補になりました。作業担当AIは「今回の不具合を直すために本当に移行が必要か」を決めかねています。
- **相談：** 助言担当AIへ、必須条件、現行コードと該当テストの場所、双方の案、確かめたい論点を渡します。「必須条件を満たせない案、見落とした移行リスク、結論を変える追加情報」を指摘してもらいます。
- **確かめる：** 助言が「現在の保存先と読込み先を先に照合するべき」と示したなら、作業担当AIが実際のファイルとテストで確かめます。助言AIの文章自体は実行結果ではありません。
- **実行と完了：** 必要な修正・テスト・差分確認を行い、変更の大きさに応じてあなたが判断します。重要な未解決条件があれば、成功扱いにせず報告します。

この例は**手順の説明用**であり、Advisorの導入によってどれだけ費用や不具合が減ったかを測ったものではありません。候補案が既にある場合の比較方法は、前述の[設計案の比較](提示された設計案をプロジェクトの根拠で比較する.md)に従ってください。

## 4. 助言担当へ何を渡すか

相談の内容は、**「もっとよく考えて」ではなく、どの判断を、何に照らして検査するか**まで指定します。

| 渡す内容 | 例 |
| --- | --- |
| 現在決めたいこと | JSON修正かデータベース移行か |
| 必須条件・禁止事項 | オフライン動作、既存データ保持、勝手な依存追加なし |
| 確認した根拠 | 現在の仕様の節、実装のパスと版、失敗したテストの名前と結果 |
| 自分が考えた方針と理由 | JSON継続なら移行不要。ただし同時書込みへの影響は未確認 |
| 依頼する反証 | どの条件で方針が破綻するか。見落とした依存・異なる仮説は何か |
| 相談後に行う検査 | 保存・再起動・読込みテスト、旧設定との互換性確認 |

このように必要な根拠を選んで渡すことは、**助言相手を別のAIや独立した作業へ委ねる場合**に使えます。ただし、**Claude Code標準のAdvisor Toolは、この小さな情報だけを渡す方式ではありません**。Advisorを呼ぶと、Claude Codeはそれまでの会話とツールの呼出し・結果を含む履歴全体を、助言モデルへ渡します。[1][3] この違いを混同しないでください。

### AIへの依頼文（あなたがAIに送る文章）

```text
今回の仕事は[対象の作業]です。
普段の調査・修正・テストは、作業担当AIで進めてください。

重要な設計の分岐、相反する根拠、または新しい進展のない失敗で
判断が難しいときは、許可された助言担当AIへ相談してください。
その前に、何を決めるのか、守る条件、確認した原典の場所と版、
候補案、自分の案の弱点、未確認の事項を整理してください。

助言には、反例・失敗条件・追加で確認すべき事実を求めてください。
助言に従う前に、現在の仕様・コード・関連テストで裏付けてください。
安全上の承認と必須テストは省略しないでください。

簡単な修正や、必要な資料がまだない段階で、相談を繰り返さないでください。
助言の利用回数、追加の確認、実施した検証、未確認事項を報告してください。
```

**この依頼文だけでは、あなたが使うAIに別モデルの相談機能が自動追加されるわけではありません。** 使える機能と接続権限がなければ、AIに根拠と疑問を整理させ、あなたが別チャットで検討したり、人が判断したりする形でも実践できます。

## 5. Advisor Toolと、似た方法はどう違うか

Claude Codeが公開した **Advisor Tool** は、作業担当のモデルが必要と判断した時点で、通常より高い能力の助言モデルへ相談する機能です。提供元による説明では、Claude Codeの `/advisor`、設定の `advisorModel`、起動時の `--advisor` で有効化でき、`/advisor off` で無効にできます。**実験的な機能で、対応モデルや利用環境に制限があります。** 具体的な設定・互換性は[Claude Codeの公式説明][claude-code-advisor]で確認してください。[1]

| 方法 | 高い能力のモデルが働く場面 | 情報の渡し方・注意点 |
| --- | --- | --- |
| **Advisor Tool（Claude Code）** | 作業中の重要な判断点。呼ぶタイミングはモデルが選ぶ | **会話とツール結果の履歴全体**を助言モデルが読む。強制的な最大呼出し回数の設定はClaude Codeにはない |
| **別のAIへの根拠を絞ったレビュー** | あなたが指定した判断点 | 事前に必要な根拠だけを選んで渡せる。抜けた情報があると助言の品質は落ちる |
| **計画段階だけ高能力モデル（`opusplan`）** | 計画を立てる段階 | 計画が終わると通常のモデルへ切り替える。作業途中の相談とは異なる |
| **別担当のAI（subagent）** | 独立して任せた調査・レビュー全体 | 独立した仕事を実行し、結果を返す。担当範囲と渡す情報を明示する |
| **主モデルを切り替える** | 切替後の作業全体 | 複数の判断を連続して高能力モデルへ任せる場合に向くが、その間の出力もそのモデル側の負担になる |

この表はClaude Codeの実装例と、製品非依存の使い方を比較したものです。Claude APIへ直接Advisorを組み込む場合、`max_uses` などの設定を使える構成もありますが、**その設定がClaude Codeの `/advisor` にも存在するとは限りません**。[3]

「思考の木（Tree of Thoughts）」は、候補の考え方を枝分かれさせ、途中の案を評価しながら探索・後戻りする研究上の方法です。**Advisorの「別のモデルに相談する」動作は、それだけで思考の木を探索したことにはなりません。** 異なる目的と計算の増え方を持つ手法なので、同じものとして紹介しません。[4]

## 6. コンテキスト・料金・品質への影響

**助言モデルの追加は、必ずしもコンテキスト削減になりません。** Claude CodeのAdvisorは会話の全文を読むため、長い履歴ほど相談一回の入力も大きくなり得ます。Claude Codeの公式説明では、作業担当モデルのキャッシュはAdvisorの有効・無効を切り替えても維持されますが、**Advisor自身は相談のたびに会話を改めて処理し、Advisor側のキャッシュ再利用は行いません**。[1]

一方、Claude APIのAdvisor Toolには、対応する環境で独自のキャッシュ設定があり、Claude Codeの利用画面とは機能が異なります。片方の仕様をもう片方へ当てはめないでください。[3]

**作業全体の費用**は、少なくとも実行担当モデルの入出力、助言担当モデルの入出力、キャッシュの料金区分、ツール・検索、失敗による再試行を合わせて比べます。助言モデルが増えるほどその呼出しの料金は加わりますが、方針を早く正せた場合は、後から何度も調査・修正・再検証する量が減る可能性があります。

Anthropicは2026年4月の発表で、**Sonnet 4.6単独と、Sonnet 4.6にOpus 4.6を助言させた方式**をSWE-bench Multilingualで比べ、同社の実験条件では正答率が2.7ポイント上がり、作業一件あたりの費用が11.9％下がったと報告しています。単独のSonnet側は適応的推論、助言あり側は推論を無効にした設定を使うなど、比較条件には差があります。**一般の仕事にその差をそのまま当てはめたり、Advisorだけが効果の原因だと断定したりはできません。**[2]

### 効果の比較方法

あなたは、同じ課題と完了条件で、少なくとも「普段のモデルだけ」「必要時に相談」「高能力モデルだけ」の三方式を比べます。課題の版、モデルの版、推論設定、ツール、権限、試行順を記録し、可能なら同じ課題で複数回試します。

| 記録すること | なぜ必要か |
| --- | --- |
| 作業の完了率、必須テスト、残る不具合 | 安いだけで誤った変更になっていないか判断する |
| モデル別の累積入力・出力とキャッシュ内訳 | 助言分を含め、全体でどのくらい処理したか確かめる |
| モデル別の実際の料金、または単価を明記した推定 | 安価なモデルへの切替だけで節約できたと決めつけない |
| 相談回数と、相談した時点の履歴の長さ | 必要以上の相談や、長い履歴の再読がないか確認する |
| ツール実行回数、再試行、経過時間 | 助言によって手戻りが減ったか、逆に作業が遅くなったか確認する |
| 根拠の欠落、助言と原典の食い違い | 助言そのものが判断を誤らせた事例も残す |

キャッシュの読出しや内部の推論に使ったトークンが**入出力の内訳**として報告された場合は、合計へ重ねて足しません。使用量が見えなければ「未計測」とし、短い最終回答から内部の負担を推測しません。計測方法は[作業ごとのコンテキスト使用量の目安を作る](../AI利用/作業ごとのコンテキスト使用量の目安を作る.md)も参照してください。

## 7. 相談を増やしすぎないために

相談に向かない仕事まで別モデルへ渡すと、費用と遅延が増えます。助言が不明確なら何度も同じ質問を投げるのではなく、**判断を変える根拠が不足しているのか、今回の作業自体を人が決めるべきなのか**を確認します。

重大な権限変更、個人情報を含む資料、外部サービスの操作は、相談AIへ渡す範囲と承認を確認してください。公式のAdvisorは会話全体を参照するため、**助言相手へ渡したくない情報を会話へ入れない設計**も必要です。助言が反例を挙げても、最終的な実装と必須検証を省いてよいわけではありません。

簡単な修正なら、適切な原典を読んで検証し、そこで終える方が効率的です。複数のAIを使うこと自体を目的にせず、**正しく終えるまでの負担が本当に減ったか**で判断してください。
