# 機能ごとのコードの分け方から読む場所を決める

プロジェクト内で、画面やデータ保存などの機能ごとにコードの場所が分かれているなら、その分け方を使ってAIに最初に読む場所を伝えます。利用者が新しい設計を考えたり、コードの役割を推測したりする必要はありません。

## 使う例

設定画面の文字だけを変更するなら、まず設定画面のコードと、その画面のテストを読みます。画面と保存処理のコードが分かれているなら、設定の保存方法まで変えるときにだけ保存側も加えます。

一方、画面から保存処理へ渡すデータの形を変える場合は、渡す側・受け取る側・データの決まりを確認します。コードの分かれ目をまたぐ変更では、その両側が影響を受けるためです。

## AIへの指示例

```text
まず既存の設計説明や、機能ごとにファイルの担当を示した一覧から、変更したコードがどの機能のものか確認してください。
その機能のコードと関連テストから読み始めてください。
別の機能とのデータの受け渡し方や形式を変更した場合は、渡す側・受け取る側・その決まりも確認してください。
機能ごとのコードの分け方が資料に書かれていない、または説明が古い場合は、推測で範囲を狭めず、通常の検索で関連箇所を探してください。
```

## 使う条件と広げ方

次のような場合に役立ちます。

- 複数の機能があり、どこから読めばよいか迷う。
- 機能ごとのコードの分け方やデータの受け渡し方が文書に書かれている。
- その説明を使えば、関係のない機能を最初に調べる対象から外せる。

機能ごとのコードの分け方が曖昧、説明が古い、または変更が複数の機能にまたがる場合は、関係する範囲を検索して広げます。小さなプロジェクトでコードの場所がすぐ分かる場合は、専用の一覧を作りません。

## どこに保存し、AIにどう読ませるか

何度も参照する機能の担当表は、たとえば `docs/機能の担当表.md` に置き、リポジトリ直下の `AGENTS.md` からリンクします。依頼では、変更した機能の行から調べ、別機能へ渡すデータを変えた場合だけ両側も確認するようAIに伝えます。既存の担当表があれば、新しい表は作らずそれを使います。

## なぜ読む量が減るのか

既存の機能ごとの分け方を使ってAIに読む場所を指示すれば、プロジェクト全体を読ませてコードの役割を推測させずに済みます。複数の機能にまたがる変更や、説明だけで判断できない場合は、AIに読む範囲を広げさせるため、必要なつながりまで省きません。

## 補助ツール

- 必要なら、[関数やファイルのつながりを一覧にする補助ツール](../../../tools/common/large/source-structure-index/README.md)で関係するコードを探せます。表示内容が古い場合もあるため、一覧だけで決めず、コードとテストも確認してください。
- 必要なら、[`architecture-boundary-router`](../../../tools/common/medium/architecture-boundary-router/README.md)が既存の機能分担やデータの流れから、変更に関係する境界と読み始めるファイルの候補を示します。どこから調べるか迷ったときに使えます。候補だけで範囲を決めず、AIに設計資料・コード・テストを確認させてください。

すでに使っている検索手段でも同じ場所を探せるなら、それを使えます。
