# 複数のAIに担当と編集範囲を分けて頼む

複数のAIに同時に作業を頼む前に、誰が何を担当し、どのファイルを変更してよいかを決めます。各AIには担当分の資料と完了条件を渡し、まとめ役が変更を集めて全体を確認します。人数を増やすことより、同じ場所を別々に直したり、相手の変更を知らずに作業したりする状態を避けることが目的です。

## 例：二つの説明ページを別々に直す

CSV取込と画像出力の説明に、それぞれ操作例を追加するとします。共通の用語と各機能の仕様は既に決まっており、片方の修正結果を待たずに書ける例です。次のパスや担当名は架空のものです。

| 担当 | 作業と完了条件 | 編集してよいファイル | 作業場所・開始条件 |
| --- | --- | --- | --- |
| AI-A | CSV取込の操作例を書く。仕様と実際の操作に合うか確認する | `docs/csv.md` | A専用の作業フォルダー。共通条件を確認したら開始 |
| AI-B | 画像出力の操作例を書く。仕様と実際の操作に合うか確認する | `docs/image-export.md` | B専用の作業フォルダー。共通条件を確認したら開始 |
| まとめ役 | 担当表を管理し、二つの変更を取り込み、目次と全体を確認する | `docs/tasks/parallel.md`、`docs/README.md` | 統合用の作業フォルダー。目次更新は両方の結果を確認してから |

例えば、あなたがまとめ役になり、別々のチャットへAとBの依頼を送れます。ファイルを編集できないチャットには変更案と根拠だけを返させ、あなたが一件ずつ反映します。複数エージェントを起動する専用機能は必須ではありません。

AとBには、共通の目的、守る用語、参照する版、相手の担当範囲を知らせます。ただし、相手の会話全文や無関係な資料まで渡す必要はありません。目次の修正が必要だと気付いたら、各AIは目次を編集せず、まとめ役へ追加すべきリンクを報告します。

## 1. 同時に進められる作業か確かめる

まとめ役は、各作業が必要とする入力と、返す結果を書き出します。「相手の完成物がまだなくても、決まった仕様だけで作業し、単独で確認できるか」を判断します。OpenAIの案内も、独立した調査などを分担し、短い作業や前の結果が必要な段階は一つのエージェントで進める方針を示しています。[1]

| 作業の組合せ | 分け方 |
| --- | --- |
| 別々の文書を調べ、根拠付きの指摘を返す | 同じ基準で調査を分担できる。共有文書への書込みはまとめ役に寄せる |
| 関係のない二つの機能のファイルを直す | 共通の設定や生成物まで変更対象が重ならず、それぞれ確認できるなら同時に進める |
| 実装を変え、その差分をレビューする | レビューは確認対象の版が用意されてから始める。レビュー担当は修正せず指摘を返す |
| 共通APIの仕様を決め、そのAPIを使う処理を書く | 仕様の決定を先に行う。仕様が未確定のまま別々に推測させない |
| 数行の修正や、同じ関数を何度も相談して直す | 一つの担当にまとめる方が受渡しを増やさずに済む |

別ファイルだから独立しているとは限りません。同じ設定形式、共通関数、テスト用データを使う変更では、入出力の決まりまで確認します。依存する作業は、前の結果が確認済みで、後の担当が使う版へ取り込まれてから開始します。日本語本文の確定後に英訳する作業なども、この順序が必要です。

## 2. 一つの編集対象に一つの担当を決める

担当表は既存のIssueや作業メモに置けます。表を管理する人またはAIを一つ決め、作業ID、目的、対象、完了条件、前提となる作業、作業場所、状態を記録します。各担当は自分の結果を返し、まとめ役が表を更新します。

編集対象には、本文やコードだけでなく、テスト、目次、翻訳対応表、依存パッケージの記録、生成ファイル、結果を書き出す場所も含めます。「担当フォルダーなら何でも変更してよい」とせず、今回必要な範囲を決めてください。読む場所と編集する場所は別です。判断に必要な共通仕様は読んでよくても、変更は担当へ戻します。

例えばAとBがどちらも `docs/README.md` を書き換えると、同じ作業フォルダーでは相手の追加を消すおそれがあります。別の作業フォルダーでも、取り込む際に変更が重なったり、見出しや順番の方針が食い違ったりします。単に別ブランチへ分けて終わりにはしません。

この場合は、目次をまとめ役だけが編集するか、Aの変更を確認した版をBへ渡して順番に直します。同じファイルの別の行でも、全文整形や見出し変更で重なるため、本書では同時編集を避ける進め方にします。

範囲を広げる必要が出たら、その変更を止めて理由と対象をまとめ役へ返します。担当を移すときは、前の担当が編集を停止し、残った差分を保存したことを確認してから、担当表と次の依頼を更新します。返答がないことを、停止した証拠にはしません。

## 3. 作業するファイルと共有状態を分ける

Gitを使う場合は、共通の開始時点をコミット番号で記録します。コミットは変更をひとまとまりで保存した記録で、その番号は版の識別に使えます。各担当には、その版から分けたブランチと、実際にファイルを編集する別の作業フォルダーを用意します。

ブランチ名を二つ作っても、一つの作業フォルダーを共有して切り替えながら編集するのでは分離できません。Gitのworktreeは、一つのリポジトリに複数の作業フォルダーを作り、それぞれで別のブランチを扱う機能です。[5] 環境に作業領域を分ける機能があればそれを使い、各AIが実際に使っているフォルダーとブランチを開始時に確認します。

Gitを使わない場合も、同じ版の資料を担当別のフォルダーへ分け、開始版と変更案を区別して保存できます。チャットだけの場合は、確認対象の添付資料を固定し、返答先を分けます。チャットを分けるだけでは、編集先のファイルまで別になるとは限りません。

作業フォルダーの分離は、あらゆる操作を隔離するものではありません。Gitのworktreeには共通の設定などもあります。[5] テスト用データベース、出力先、共有設定、外部サービスへの書込みも、別の場所を割り当てるか順番に実行します。分離できない対象は、担当を一つに寄せます。

「ここ以外を変更しない」という依頼文だけでは、権限を技術的に制限できません。読取り専用や許可範囲の設定があれば併用してください。担当を増やしたことを、公開、削除、環境設定の変更などへの追加許可とは扱いません。

## 4. 各担当へ目的・対象・返す結果を渡す

次はAへ渡す依頼のひな型です。角括弧は実際の値へ置き換えます。確認コマンドを推測させず、既存の手順と期待する結果を指定してください。

```text
あなたは作業A「CSV取込の操作例追加」の担当です。
共通の目的・用語・仕様は [作業メモの場所] にあります。
開始版は [コミット番号、または添付資料の版] です。
作業場所は [A専用フォルダー]、ブランチは [Aのブランチ] です。
編集できるのは docs/csv.md だけです。目次と共通設定は変更しません。
AI-Bは docs/image-export.md、まとめ役は目次と担当表を担当します。

最初に作業場所・版・編集対象を確認してください。
仕様と操作手順を読み、入力例・操作・期待結果を本文へ追加してください。
[既存の確認手順と期待結果] に沿って確認してください。
他のファイルの変更や未確定の仕様判断が必要なら、該当作業を止め、
必要な変更・根拠・判断が必要な点をまとめ役へ返してください。
相手のファイル、ブランチ、作業状態は変更しません。

最後に、開始版と成果の版、変更箇所、確認手順と結果、
根拠の場所、未確認・停止理由を返してください。
報告はこの会話へ返し、共有の担当表には直接追記しません。
まとめ役の依頼なしに別の作業を始めないでください。
```

ファイルを読めないAIには、作業メモと必要な本文を添付します。編集機能がなければ、編集の指示を「変更案を返す」に替えます。役割や引継ぎの詳しい書き方は[作業ごとにAIの役割とチャットを分ける](../AI利用/作業ごとにAIの役割とチャットを分ける.md)を参照してください。

各担当の報告には、例えば次を使います。空欄のひな型であり、確認済みの結果ではありません。

```markdown
- 作業ID・担当:
- 開始版・成果の版・作業場所:
- 変更したファイルと内容:
- 完了条件ごとの結果:
- 実行した確認: 対象の版、コマンドや操作、期待結果、実際の結果、ログの場所
- 未確認・未解決・停止理由:
- 共有ファイルへ必要な変更案:
- 状態: 作業中 / 個別確認済み・統合待ち / 確認待ち / 停止
```

## 5. まとめ役が一件ずつ取り込み、全体を確認する

各担当から成功の報告が届いても、全体の完成とは分けます。GitHubのFleet modeの資料にも、担当ごとの変更と確認結果を集め、親のエージェントが組み合わせた結果を確認する手順があります。[3]

1. **受け取る版を固定する。** 成果のコミット番号や保存した差分を記録し、担当がその成果を取り込み中に書き換えないようにします。報告と実際の変更ファイルを比べ、範囲外の変更や未確認を確かめます。
2. **順序を決めて取り込む。** 統合用の作業場所で、前提となる変更から一件ずつ取り込みます。上の独立したAとBなら、例えばA、Bの順を担当表へ記録します。共有目次は両方を取り込んだ後、まとめ役が更新します。
3. **重なりや前提の違いを解決する。** 同じ箇所の変更を機械的に片方で上書きしません。双方の差分と仕様を確認し、解決できなければ該当する統合を止めます。作業開始後に統合先が変わった場合も、新しい変更と両立するか確認します。
4. **組み合わせた版を確認する。** 文書なら見出し、用語、リンク、操作例の一致を確認します。コードなら関係するテストに加え、組み合わせた動作とプロジェクトで必須の確認を行います。修正が入ったら、その版で必要な確認をやり直します。
5. **状態を更新する。** 全体の完了条件、確認した版、実行結果、未確認を報告します。必須の確認が残れば「確認待ち」、仕様の判断待ちなら「停止」とし、個別の成功だけで完了にしません。

レビュー担当を分ける場合は、取り込み対象の固定した差分、仕様、確認結果を渡し、ファイルを編集させず指摘を返させます。修正は編集担当へ戻し、修正後の版を再確認します。実行する検査がファイルを書き換える場合は、検査用の別の場所で行います。

担当表には「作業中」「個別確認済み・統合待ち」「全体確認済み」などを区別して残します。失敗した確認を削ったり、他の担当の結果を無確認で置き換えたりしません。変更の提案を出すこと、取り込むこと、公開することも別の操作として、既存の権限と手順に従います。

## 何が減り、何が増えるか

担当を限定すると、各AIに別の作業の相談や資料を丸ごと渡さずに済みます。独立した調査を同時に進めれば待ち時間が短くなる場合もあります。一方、共通資料の重複読込み、担当分け、報告、統合、再確認にも入力と出力を使います。OpenAIも、複数エージェントでトークン使用量が増える可能性を挙げています。[2]

この方法が常に速い、安い、正確だとは限りません。小さな仕事や依存の強い仕事は順番に進めます。比較する場合は、一人分だけでなく、全担当とまとめ役の使用量、経過時間、手戻り、残った不具合を同じ完了条件で記録してください。[作業ごとの使用量の記録方法](../AI利用/作業ごとのコンテキスト使用量の目安を作る.md)を使えます。

順番に一件ずつ進めたい場合は[課題一覧から一件ずつAIに進めさせる](課題一覧から一件ずつAIに進めさせる.md)を使います。本書は、同時に進める場合の編集担当と統合を扱います。

## 補助機能と既存資料

このように複数のAIへ分担し、結果をまとめる構成を、複数エージェントによる協調と呼びます。各作業を配り、進行と統合を管理する役を、製品の資料ではオーケストレーターなどと呼ぶことがあります。名前を指定するだけで担当表や確認手順が決まるわけではありません。

OpenAIのMulti-agentとGitHub CopilotのFleet modeには、別のエージェントへ作業を配る仕組みがあります。[1][3] 作業場所を分ける例として、GitHub Copilot appには新しい作業ツリーやクラウドの実行環境を選ぶ機能があります。[4] 利用中の環境で、実際の作業場所、権限、停止方法を確認して使います。これらの導入は、手動で担当を分けるための条件ではありません。

以下は2026年10月17日に確認した公式資料です。本書の担当表と依頼例は、それらを参考にした運用例であり、製品が必ず同じ動作をするという保証や、この手順の効果を測定した結果ではありません。

1. OpenAI. [Multi-agent](https://developers.openai.com/api/docs/guides/agents-api/multi-agent) — 独立した作業の分担と、短い作業・依存する段階の扱い。
2. OpenAI. [API deployment checklist](https://developers.openai.com/api/docs/guides/deployment-checklist#use-multi-agent-for-parallel-work) — 共有する変更対象を避ける判断と、使用量・品質・時間の確認。
3. GitHub. [Fleet mode](https://docs.github.com/en/copilot/how-tos/copilot-sdk/features/fleet-mode) — 担当の割当て、依存関係、報告、組み合わせた結果の確認。
4. GitHub. [Working with agent sessions in the GitHub Copilot app](https://docs.github.com/en/copilot/how-tos/github-copilot-app/agent-sessions) — 作業ツリーや実行環境の選択。
5. Git. [git-worktree](https://git-scm.com/docs/git-worktree) — 複数の作業フォルダーと、共通設定など分離されない部分。
