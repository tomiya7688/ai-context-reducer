# 設計と完了条件を先に決める

作業を依頼する人が、AIに実装を頼む前に「何を変えるか」「どこは変えないか」「何を確認できたら完成か」を短く決めます。その内容をAIへの依頼文やIssueに書いて渡せば、AIは過去の会話や広い範囲のコードから設計意図を推測せずに作業を始められます。

## 例：CSV出力の日付形式を変える

CSVに出す日付の形式を変更する場合、依頼する人が実装前に次のように決めます。「出力形式だけを変え、読込形式と公開コマンドは変えない」「日付の出力処理を変更し、そのテストで新旧形式の例を確認する」。必要なら、その形式を読む既存プログラムへの影響も確認します。

この条件を受け取ったAIは、日付の出力処理と対応するテストから読み始められます。画面や読込処理、過去の議論を広く調べ、変更範囲や完了条件を推測する必要はありません。実装中に記録と矛盾する事実が分かったら、AIはそこで作業を止め、依頼者に確認します。

## AIに渡す

決めた内容は、AIが作業を受け取る場所に書きます。チャットで依頼するなら同じ依頼文に含めます。Issueや作業メモに書いたなら、AIにそのIssueやファイルを確認するよう伝えます。別の場所に置いただけでは、AIが読んだことになりません。

たとえば、依頼文に次を添えます。

```text
変更方針:
- 変える: CSV出力の日付を YYYY/MM/DD から YYYY-MM-DD にする
- 変えない: CSVの読み込み形式と公開コマンド
- 完了条件: 出力が新形式になり、読み込みと公開コマンドの動作は従来どおり
- 確認: 日付出力のテストで新形式を確認する
この条件を確認してから実装してください。実装と矛盾する場合は、変更を続ける前に質問してください。
```

依頼者が最初から文章を用意する必要はありません。AIに依頼内容からこのメモの案を作らせ、依頼者が内容を確認して合意してから実装に進ませても構いません。

## 何を記録するか

作業に関係する判断だけを残します。

- **目的**: 誰のどんな問題を解決するか
- **設計方針と変更範囲**: どの処理を変え、どこは変えないか
- **守る条件**: コマンドの使い方、出力形式、保存場所、既存利用との互換性など
- **完了条件**: 利用者から見て何ができれば完成か
- **確認方法**: 自動テストで確認する条件と、人が確認する必要がある点

既存の決まりや、一見不要に見える安全策を維持する必要があれば、その理由と参照先も記録します。小さな修正では、Issueや依頼文に目的と確認方法だけを書けば十分です。すべての項目を長い設計書にする必要はありません。

## 自動確認と人の確認を分ける

同じ入出力や配布ファイルの確認を繰り返しているなら、機械で確実に判定できる条件を自動テストにできます。たとえば「展開した配布物に必要なファイルがあり、指定したコマンドが動く」は自動確認に向いています。自動化すれば、依頼者や実装者が毎回手順を探し直す量を減らせます。

使いやすさや設計の妥当性など、機械だけでは意味を判断できないものは、人が確認する条件として残します。確認を増やすこと自体を目的にせず、繰り返し作業を減らす効果や利用者を守る契約が明確なものだけを自動化します。

## 検証方法の選択との違い

[変更内容に応じて検証を選ぶ](変更内容に応じて検証を選ぶ.md)では、変更後にどの検査を実行するかを決めます。この方法ではその前に、実装の目的、守る条件、変更範囲、完成の判定方法を決めます。決めた条件のうち、自動化できるものを後の検証で確認します。

## 使うとよい場合

担当が替わる作業、利用者向けの仕様や互換性を変える作業、変更範囲や完成条件が曖昧になりやすい作業に向いています。目的と変更箇所が明白な一行修正なら、独立した設計メモを作らず、Issueに目的とテストだけ記録すれば足ります。

特別なツールは必要ありません。依頼文に直接書くか、Issueや短い作業メモに書いて、その場所をAIに伝えれば使えます。

## AIへの依頼例

> 次の目的・変更範囲・守る条件・完了条件を実装前に読み、条件ごとに必要なコードと確認方法を示してください。不明点や条件の矛盾があれば、実装を始める前に指摘してください。完了時は条件ごとに確認結果を報告してください。

## 補助ツール・用語

専用ツールは不要です。依頼文、Issue、または[作業用メモ](作業用メモ.md)に記録できます。作業開始前に目的と受け入れ条件をそろえる方法は **Acceptance Criteria / design-first** と呼ばれます。
