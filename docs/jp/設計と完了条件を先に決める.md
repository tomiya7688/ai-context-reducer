# 設計と完了条件を先に決める

実装に入る前に、何を変えるか、どこまで変えるか、何をもって完成とするかを短く記録します。後から作業を引き継ぐ人が、過去の会話や広い範囲のコードを読み直して設計意図を推測せずに済みます。

## 例：CSV出力の日付形式を変える

CSVに出す日付の形式を変更する場合、実装前に「出力形式だけを変え、読込形式と公開コマンドは変えない」「変更対象は日付の出力処理とそのテスト」「新旧形式の例で期待結果を確認する」と決めます。必要なら、その形式が既存の利用者に与える影響も確認事項に含めます。

実装者はこの記録から、日付の出力処理と対応するテストを読み始められます。画面や読込処理、過去の議論を広く調べて、変更範囲や完了条件を推測する必要はありません。実装中に記録と矛盾する事実が分かったら、記録を更新してから続けます。

## 何を記録するか

作業に関係する判断だけを残します。

- **目的**: 誰のどんな問題を解決するか
- **設計方針と変更範囲**: どの処理を変え、どこは変えないか
- **守る条件**: コマンドの使い方、出力形式、保存場所、既存利用との互換性など
- **完了条件**: 利用者から見て何ができれば完成か
- **確認方法**: 自動テストで確認する条件と、人が確認する必要がある点

既存の決まりや、一見不要に見える安全策を維持する必要があれば、その理由と参照先も記録します。小さな修正では、Issueやpull requestに目的と確認方法だけを書けば十分です。すべての項目を長い設計書にする必要はありません。

## 自動確認と人の確認を分ける

同じ入出力や配布ファイルの確認を繰り返しているなら、機械で確実に判定できる条件を自動テストにできます。たとえば「展開した配布物に必要なファイルがあり、指定したコマンドが動く」は自動確認に向いています。自動化すれば、実装者が毎回手順を探し直す量を減らせます。

使いやすさや設計の妥当性など、機械だけでは意味を判断できないものは、人が確認する条件として残します。確認を増やすこと自体を目的にせず、繰り返し作業を減らす効果や利用者を守る契約が明確なものだけを自動化します。

## 検証方法の選択との違い

[変更内容に応じて検証を選ぶ](変更内容に応じて検証を選ぶ.md)では、変更後にどの検査を実行するかを決めます。この方法ではその前に、実装の目的、守る条件、変更範囲、完成の判定方法を決めます。決めた条件のうち、自動化できるものを後の検証で確認します。

## 使うとよい場合

担当が替わる作業、利用者向けの仕様や互換性を変える作業、変更範囲や完成条件が曖昧になりやすい作業に向いています。目的と変更箇所が明白な一行修正なら、独立した設計メモを作らず、Issueに目的とテストだけ記録すれば足ります。

この方法に特別なツールは必要ありません。Issue、pull request、短い作業メモなど、次の実装者が確認できる場所に記録します。
