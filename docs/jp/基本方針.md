# 基本方針

このリポジトリは、ソフトウェア開発をAIに頼むとき、作業に必要な情報を選んで渡す方法をまとめています。コードや資料が増えるほど、依頼のたびに全部を読み直すより、変更に関係する場所を見つけてから調べる方が効率的です。

目指すのは、読む量を減らすことだけではありません。必要な情報に早くたどり着き、元の資料で確かめながら正しく作業できる状態です。

## 例: 入力欄の動作を直す

画面の入力欄で、空の値を送信できてしまう問題を直すとします。関係するのは、入力値を受け取る処理、画面の表示、送信後の処理、そしてその動作を確かめるテストです。プロジェクトにある別画面や無関係な機能まで読む必要はありません。

作業では、まず依頼内容と完了条件を確認します。次に、ファイル一覧や検索結果を使って候補を絞り、関係する実装とテストを読みます。変更した後は、入力欄の動作に合った確認を行い、確認できなかった範囲があればそのまま伝えます。

```text
依頼と完了条件を確認
  -> 関係する実装とテストを見つける
  -> 元のコードを読んで変更する
  -> 変更に合った方法で確認する
  -> 未確認の範囲を報告する
```

候補一覧や短い説明は、読む場所を探すための手掛かりです。コードの意味や変更の安全性を判断するときは、一覧だけで済ませず元のコードやテストを読みます。

## 作業に必要な情報を分けて残す

どの作業でも変わらない決まり、プロジェクトの構成、今回の依頼と完了条件は、それぞれ分けて書きます。毎回同じ説明を依頼文へコピーすると、古い説明が残ったり、長い文章から必要な条件を見つけ直したりすることになります。

詳しい仕様は、それを管理する文書や実装に置き、概要文へ何度も書き写しません。短い一覧や要約から元の説明へ戻れるようにしておきます。

## 確認方法は変更に合わせる

変更後の確認方法は、何を変えたかで選びます。計算処理なら関連するテストを実行し、画面を変えたなら画面の動作を確認します。配布物を変えた場合は、作成した配布物そのものを確認します。

確認範囲が限定されている場合は、その範囲を明らかにします。実行した検査が対象を調べていない場合や、走査できなかった場所がある場合に、「問題なし」とは報告しません。

## 必要な仕組みだけを加える

小さなプロジェクトなら、短い作業手順と検索だけで十分な場合があります。ファイルが増え、同じ探し方や確認を何度も行うようになったら、一覧や自動化を追加します。導入や維持に必要な手間が、繰り返し減らせる手間より大きい仕組みは増やしません。

複数人や複数のAIが同じ場所を更新する場合は、自分の作業中に他の変更が入っていないかも確認します。競合を避けるだけでなく、最新の変更を見落とさないためです。

具体的な手法と使いどころは[手法一覧](手法一覧.md)、導入順の目安は[導入優先度](導入優先度.md)で説明しています。

## 補助ツール・用語

まず既存の検索とプロジェクト案内で試し、繰り返す作業が残る場合だけ[手法と補助ツールの対応表](手法と補助ツールの対応表.md)から選びます。必要情報を選んでAIへ渡す考え方は **Context Engineering**、参照先を選ぶ流れは **Context Routing** と呼ばれることがあります。
