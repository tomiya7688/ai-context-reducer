# 導入優先度

この文書は、プロジェクトにどの手法を取り入れるか決めるための案内です。手法を全部入れることが目的ではありません。作業のたびに同じ資料を探す、関係のない範囲まで読む、必要な確認方法が分からない、といった繰り返しの困りごとがある場合に、その原因を減らす方法を選びます。

## 例: 小さな変更のたびに大きな仕組みを足さない

小さなゲームで、音量設定の処理とテストの場所がすぐ分かるとします。この場合は、最初に見るファイルと実行するテストを短い案内に書けば十分です。関数を一覧にする仕組みや、変更からテストを自動選択する仕組みまで作ると、その仕組みの整備と更新に手間がかかります。

一方、複数のアプリを含む大きなプロジェクトで、設定変更のたびに関係する画面・読み込み処理・テストを探し直しているなら、作業別の案内表や変更内容ごとの案内表が役立ちます。手法は、実際に繰り返している調査を短くできる場合に追加します。

## 選び方

### 1. 繰り返している手間を一つ挙げる

「AIの読む量を減らす」だけでは、どの仕組みが必要か決まりません。直近の作業を見て、たとえば次のように具体化します。

- 変更のたびに、最初に見るファイルを探し直している
- 大きなソースのどこが関係するか分からず、全体を読んでいる
- 小さな変更でも、毎回すべてのテストを調べている
- 既に答えが分かっているのに、「念のため」の検索が続く
- 同じ説明が複数の文書にあり、どれが正しいか読み比べている

一度しか起きていない問題や、対象箇所が最初から明らかな作業には、専用の仕組みを作らなくて構いません。

### 2. まず入口を短く整える

多くのプロジェクトでは、最初に読む小さな案内を整えるだけで十分です。案内には、次の情報を置きます。

- 作業対象へ進むための入口
- 正式な説明や仕様が置かれている場所
- 変更時に必要な確認方法
- まだ確認していない範囲の伝え方

既に `AGENTS.md` などの案内があれば、それを直します。同じ役割の文書を増やす必要はありません。繰り返す作業手順は、利用中のAIがSkillsに対応している場合だけSkillへ分け、毎回読む案内に詰め込みません。詳しいルールや仕様は複製せず、原文書へのリンクを置きます。[基本方針](基本方針.md)と[コンテキスト削減の基本](コンテキスト削減の基本.md)に、入口や資料の絞り方の考え方があります。

### 3. 困りごとに合う手法を一つ選ぶ

| 繰り返している困りごと | 最初に検討する手法 | 効果が出る理由 |
|---|---|---|
| 作業ごとに見る場所が違い、毎回探している | [作業別の案内表](作業別の案内表.md) | 作業の種類から、最初に確認する説明・コード・テストへ進める |
| 変更した箇所から関連範囲を探している | [変更内容ごとの案内表](変更内容から確認先を選ぶ.md) | 変更の種類に対応する確認先を再利用できる |
| 大きなファイルを最初から読んでいる | [読む候補の優先度](変更に必要なファイルから読む.md)、[コード構造の索引](コード構造の索引.md) | 関連するファイルや関数を先に絞り、全文を読む回数を減らせる |
| 確認済みの内容を何度も調べている | [探索を止める条件](調査を止める条件を決める.md)、[確認する根拠の量](必要な確認を先に決める.md) | 何が分かれば判断できるかを先に決められる |
| 変更のたびにテストを一から探している | [変更内容に応じた検証](変更に合わせて確認方法を選ぶ.md)、[変更に関係するテスト](変更の影響から検証範囲を選ぶ.md) | 変更と関係する確認方法やテスト候補から始められる |
| 同じ規則や説明を何度も読んでいる | [場所ごとの指示](場所ごとに作業ルールを分ける.md)、[規則の確認先](今回の変更に関係する規則を確認する.md)、[文書の重複管理](文書の同じ説明を一か所にまとめる.md) | 作業場所や確認内容に必要な説明だけを参照できる |

手法の概要と選び方は[手法一覧](手法一覧.md)を参照してください。すべてを一度に導入せず、まず最も頻繁な困りごとに対応するものだけを試します。

### 4. 使い続ける価値があるか確かめる

導入後、実際の作業で次を確認します。

- 案内から変更対象へ迷わず進めるか
- 関係のないファイルや説明を読む回数が減ったか
- 必要なテストや確認を省いていないか
- 案内や索引の更新に、削減できた手間以上の時間がかかっていないか

効果がなければ、仕組みを簡単にするか削除します。案内が古い場合は調査範囲を広げ、共通部分や公開仕様の変更では必要な確認を追加します。読む量を減らす場合も、変更の正しさを確かめます。

## プロジェクトの特徴ごとの目安

規模はファイル数だけで決めません。作業対象に迷わずたどり着けるか、同じ調査が繰り返されているかで判断します。

- **小規模:** 対象コードとテストが明らかなら、短い入口と必要なテストだけで十分です。専用の索引や自動判定を作る前に、手で案内先を示せないか確認します。
- **複数の機能や資料がある:** 作業内容によって見る場所が変わるなら、作業別または変更別の案内表を検討します。現在の機能・制約が説明だけでは分からなくなったときは、短い現状メモを加えます。
- **大規模なコードや長いテスト:** 大きなファイルの関連箇所を繰り返し探すなら、コード構造の索引を検討します。テスト全体の実行が高価で、変更とテストの対応が分かる場合に限り、影響範囲から候補を絞ります。共通処理や公開仕様を変えた場合に広い確認へ戻る手段は残します。
- **複数人・複数AIが同じリポジトリを更新する:** 作業を始める前に、前回からの変更を確認する手順と、作業中の目的・変更範囲を共有する短い記録を検討します。
- **画面操作や生成物を含む:** 実行結果を画面で見る必要がある場合や、配布物がソースと異なる場合は、その作業に必要な実行・配布物の確認を加えます。全プロジェクト向けの追加手順にはしません。

## 判断の基準

手法を追加するのは、繰り返し減らせる調査の手間が、導入と維持にかかる手間を上回る場合です。正確さと必要な検証を保ったまま、実際に読む量や探す時間が減ったかで判断してください。

### 基準の例

たとえば、同じ種類の作業で毎回12分かけて対象を探し、それが月に8回あるなら、検索に約96分使っています。入口の案内を作るのに30分、毎月の更新に10分かかり、導入後の検索が1回3分になったなら、月の作業は約34分となり、維持時間を差し引いても導入する価値があります。反対に、一度きりの作業で探すのが12分だけなら、30分かけて専用の索引を作る必要はありません。

この数字は計算方法を示す例で、共通の合格基準ではありません。直近の作業で実際に探し直した回数・時間と、仕組みを更新する負担を見積もって決めます。

## AIへの依頼例

> 直近の作業で繰り返した調査を一つ特定し、表からそれを減らす手法を一つだけ選んでください。利用者が作るもの、AIへの渡し方、減る作業、導入・更新の負担を並べ、既存の仕組みで足りる案を優先してください。
