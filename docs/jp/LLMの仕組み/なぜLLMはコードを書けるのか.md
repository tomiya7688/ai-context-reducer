# なぜLLMはコードを書けるのか

LLMは自然言語を扱うモデルなのに、なぜPythonやGoのコードまで生成できるのでしょうか。「大量のコードを暗記しているから」だけでは、この能力を十分に説明できません。

自己回帰型LLMにとって、自然言語もソースコードも最終的にはトークン列です。コードを含むデータで学習すると、モデルは次トークン予測に役立つコードの構造、自然言語との対応、典型的なAPI利用などをパラメータへ反映できます。

## ソースコードもトークン列になる

たとえば次のPythonコードも、モデルへ入る前にトークナイザーで分割されます。

```python
def add(a, b):
    return a + b
```

モデルは「これはPythonだから別の種類のニューラルネットワークへ切り替える」という動作を必ず行うわけではありません。同じTransformerが、入力トークン列と学習済みパラメータを使って続きを予測します。

コードには、自然言語とは違う強い規則があります。括弧、インデント、型、識別子、関数呼び出し、APIの引数などには繰り返し現れる構造があります。次トークン予測を改善するには、モデルがこれらの関係を利用する必要があります。

## コメントや文書が自然言語とコードを結び付ける

ソフトウェアの周辺には、コードだけでなく次の情報があります。

- READMEやAPI文書
- 関数・型の名前
- docstringやコメント
- Issueや変更説明
- エラーメッセージ
- テスト名と期待結果

このようなデータでは、自然言語による目的とコードが同じ文脈へ現れます。モデルは次トークン予測の学習を通じて、「この説明の後にはどのようなコードが続くか」「この関数名の周囲ではどのAPIが使われるか」といった統計的な対応を利用できるようになります。

## コード補完と仕様からの生成は同じ原理でつながる

コード補完では、既存コードの続きを条件として次のトークンを生成します。

```text
既存コード
  ↓
続きのコードを予測
```

仕様からコードを書く場合も、基本原理は同じです。

```text
自然言語の仕様
+ 既存コード
+ 型やAPI
+ 必要なら例やテスト
  ↓
条件に合うコードの続きを予測
```

入力の種類は増えますが、モデルが行う生成処理は「現在のコンテキストから次トークンを予測する」という同じ枠組みにあります。

## コードで追加学習すると能力を強められる

コードを多く含むデータで事前学習・追加学習したモデルは、一般の言語モデルよりコード生成へ適応できます。

Codexの研究では、GPT系モデルを公開GitHubコードで微調整し、docstringからPython関数を生成するHumanEvalで機能的正しさを評価しました。研究結果は、自然言語の説明から実行可能なコードを生成できる場合がある一方、長い処理列や変数への操作の対応などに失敗することも示しています。

この結果は「コード生成は単なる文字列コピー」とも、「コードを生成できれば正しさも理解している」とも言えないことを示します。

## 既存プロジェクトのコードを渡す意味

学習済みモデルがGoやPythonの一般的な書き方を知っていても、あなたのプロジェクト固有の情報までは現在のパラメータに正確に入っているとは限りません。

たとえば、実際の修正には次の情報が必要になります。

- 現在の関数名と型
- プロジェクト固有のAPI
- 変更してよい責務の範囲
- コーディング規則
- 期待動作を示すテスト
- 実際に出たエラー
- 最近変更された仕様

これらを現在のコンテキストへ渡すと、モデルは一般的なコードパターンだけでなく、そのプロジェクトの条件を使って生成できます。

このリポジトリで「関係するコードとテストを先に見つける」ことを重視するのは、このためです。

## コードを書けることと、コードが正しいことは別

LLMが生成するのは、学習済みパターンと現在のコンテキストに対してもっともらしいコードです。生成したコードを実行した結果を、素のLLMが生成前から自動で観測しているわけではありません。

次のような失敗は起こり得ます。

- 存在しないAPIを呼ぶ
- 型や戻り値を取り違える
- 例外条件を見落とす
- 古いライブラリ仕様を使う
- テストにない境界条件を壊す
- プロジェクト固有の決まりを見落とす

コード実行、コンパイラ、型検査、テスト、リンターなどのツールを使えば、生成した候補を外部の事実で確認できます。LLMがツール結果を再びコンテキストへ受け取れば、エラーを条件として次の修正案を生成できます。

```text
コードを生成
  ↓
コンパイル・テスト・実行
  ↓
結果をコンテキストへ戻す
  ↓
結果に基づいて修正
```

このループでは、LLMと実行環境が別の役割を担当しています。

## コンテキスト削減との関係

コード生成で重要なのは「リポジトリを全部渡すこと」ではなく、「今回の変更を判断・検証するために必要な情報を渡すこと」です。

変更対象の実装、関連型、仕様、テスト、エラーを先に特定できれば、無関係な機能を大量に読ませずに、プロジェクト固有の条件をモデルへ与えられます。作業中に別の依存関係が見つかったら、その時点で範囲を広げます。

これは単なるトークン節約ではなく、LLMがコード生成へ使う条件を作業に合わせるための設計です。
