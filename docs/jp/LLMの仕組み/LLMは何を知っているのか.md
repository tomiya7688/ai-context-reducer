# LLMは何を知っているのか

LLMが歴史上の出来事やAPIの使い方を答えると、「モデルの中に知識が保存されている」と表現したくなります。しかし、その「知っている」をデータベースの保存と同じ意味で扱うと、LLMの失敗を説明しにくくなります。

LLMのパラメータには、学習データから得た統計的な構造が分散して反映されます。モデルは、そのパラメータと現在のコンテキストを使って次トークンを生成します。

## パラメータは文書検索用の表ではない

データベースでは、レコードを特定するキーと保存した値を対応付け、必要なレコードを明示的に検索できます。

LLMのパラメータは、そのような「質問 → 保存済みの回答」の一覧ではありません。学習では、非常に多くの例に対する予測誤差を小さくするよう、多数の数値を一緒に更新します。

その結果、特定の事実、文法、文体、コードパターンなどに関係する情報は、多数のパラメータや内部表現へ分散して反映されます。

## だからといって、学習データを逐語的に覚えないわけではない

「パラメータはデータベースではない」ことと、「学習例を一切暗記しない」ことは別です。

GPT-2を対象にした研究では、適切な入力を使って学習データ中の文章を逐語的に抽出できる例が報告されています。つまり、大規模言語モデルは一般化したパターンだけを保持するとは限らず、一部の訓練例を記憶する場合があります。

したがって、「LLMは全部を暗記している」と「LLMは何も暗記していない」のどちらも単純化しすぎです。

## 「答えられる」と「出典を持っている」は別

モデルが「東京は日本の首都です」と正しく生成できても、その出力に対応する一つの学習文書をモデルが内部から特定して提示しているわけではありません。

学習済みパラメータから出した回答には、通常、出典のレコードIDが付いていません。モデル自身が「このURLのこの文から答えた」と保証できる構造ではありません。

出典が必要な作業では、検索やRAGで原典を取得し、その文書を現在のコンテキストへ入れて回答と照合できるようにする必要があります。

## 知識を引き出せるかは入力にも依存する

同じモデルでも、質問の形式、前後の文脈、使用言語などによって答えられる内容が変わることがあります。

これは、モデルの出力がパラメータだけで決まるのではなく、現在の入力との組み合わせで決まるからです。パラメータ中にある関連情報を、どの入力でも必ず同じように取り出せるとは限りません。

この性質を考えると、「モデルが知っているか」を一回の質問だけで完全に判定することも難しくなります。

## 学習済み知識と現在のコンテキストを分ける

ソフトウェア開発では、この区別が特に重要です。

モデルは、一般的なGoの構文やよく使われるHTTP APIのパターンを学習済みかもしれません。しかし、あなたのリポジトリで昨日変更された関数、非公開の仕様、現在失敗しているテスト結果を学習済みだと期待することはできません。

```text
学習済みパラメータ
  一般的な言語・コード・世界のパターン

現在のコンテキスト
  今回の仕様・コード・テスト・エラー

外部ツール
  最新情報・実行結果・検索した原典
```

三つを分けると、何をモデルへ追加で渡すべきか判断しやすくなります。

## 「知っている」を実用上どう扱うか

このリポジトリでは、LLMが何かを哲学的な意味で理解しているかを決めません。作業では、次のように実用上の能力として扱う方が安全です。

- 一般知識として答えられても、重要な事実は必要に応じて原典で確認する。
- プロジェクト固有の情報は、学習済みだと期待せず現在の原典を渡す。
- 最新情報は、モデルの学習時点を推測して済ませず外部情報で確認する。
- 出力に自信があるように見えても、正しさの証拠とは扱わない。

## コンテキスト削減との関係

「モデルがたぶん知っているから何も渡さない」とすると、プロジェクト固有の条件を失います。反対に、「何も知らないから全部渡す」とすると、今回使わない大量の情報までコンテキストへ入ります。

必要なのは、その作業で**学習済みの一般能力へ任せられる部分**と、**現在の原典を渡して確認すべき部分**を分けることです。

コード修正なら、言語文法の教科書を毎回すべて渡す必要はありません。一方で、変更対象の実装、関連仕様、テストは現在の事実として確認します。
