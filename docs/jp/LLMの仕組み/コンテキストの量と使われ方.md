# コンテキストの量と使われ方

LLMのコンテキストウィンドウが大きくなると、「プロジェクト全体を入れてしまえば、情報を選ぶ必要はない」と考えたくなります。しかし、入力できる量と、その情報を作業で有効に使えることは別です。

この文書は、LLMの仕組みと、このリポジトリで扱うコンテキスト削減の手法をつなぐ位置にあります。

## 情報が足りなければ、モデルは推測する

コード修正で変更対象の実装を渡さなければ、モデルは一般的な実装パターンから不足を補おうとします。プロジェクト固有の型、規則、既存テストを知らなければ、もっともらしくても実際には合わない変更を作る可能性があります。

したがって、コンテキスト削減は「とにかく削る」作業ではありません。必要な根拠を残すことが先です。

## 情報を増やせば単調に良くなるわけでもない

コンテキストウィンドウへ情報を追加すると、その情報はモデルが処理する入力の一部になります。しかし、長い入力中のすべての情報を同じ品質で利用できる保証はありません。

*Lost in the Middle* の実験では、長い入力の中で関連情報を置く位置によって性能が変わりました。この結果は特定のモデル・課題で得られたものであり、「長いほど必ず悪い」という一般則ではありません。

重要なのは、**入れられることと、使えることを分ける**ことです。

## 無関係な情報は「無料の保険」ではない

無関係なファイル、重複した説明、全件ログを追加しても、今回の判断に新しい根拠が増えないなら、その入力は作業の保険にはなりません。

さらに、古い仕様と新しい仕様を区別せずに並べると、モデルへ矛盾した条件を与えることになります。大量の候補コードをそのまま渡すと、どの実装が変更対象かを再びモデルに探索させることになります。

そのため、まず検索・索引・変更差分などで候補を絞り、必要な原典を読む流れが有効です。

## ただし、長い原典を理由なく要約しない

情報量を減らすとき、原典を何でも短い要約へ置き換えると、条件や例外を落とす危険があります。

たとえば、セキュリティ要件を「認証を確認する」と一文に縮めても、どの操作でどの権限が必要かは分かりません。実装判断に必要な条件が原文へ書かれているなら、その箇所を直接読む方が安全です。

このリポジトリでは、索引や要約を**読む場所を探すための手掛かり**として使い、判断時には必要な原典へ戻ります。

## 作業中にコンテキストは変化する

最初から必要範囲を完全に当てる必要はありません。

```text
依頼
  ↓
候補を絞る
  ↓
関係する原典を読む
  ↓
新しい依存先を発見
  ↓
その依存先だけ追加で読む
```

たとえば設定保存の修正を始め、実装を読むと共通のシリアライザーが関係すると分かった場合、その時点でシリアライザーと関連テストへ範囲を広げます。

最初からリポジトリ全体を渡すのではなく、**根拠に従って必要範囲を拡張する**のがポイントです。

## 情報の種類ごとに役割を分ける

コンテキストへ入る情報には役割があります。

| 情報 | 作業での役割 |
| --- | --- |
| 依頼・完了条件 | 何を変え、どこまで確認するかを決める |
| 実装 | 現在の動作と変更場所を確認する |
| 仕様・規則 | 変更後に守る条件を確認する |
| テスト | 期待動作と回帰確認の手掛かりにする |
| エラー・ログ | 実際に起きた失敗を確認する |
| 検索結果・索引 | 原典へ進む候補を絞る |
| 要約 | 状態を短く受け渡すが、必要な判断では原典へ戻る |

この役割を混同すると、検索結果だけを実装の証拠にしたり、古い要約を最新仕様として使ったりする問題が起きます。

## 「最小コンテキスト」ではなく「必要十分なコンテキスト」

このリポジトリが目指すのは、文字数やトークン数が最小の入力ではありません。

良い状態は、次の条件を満たすコンテキストです。

- 今回の判断に必要な原典がある。
- 変更後の確認に必要なテストや条件がある。
- 今回使わない大量の情報を先に混ぜない。
- 不足が判明したら、理由を持って範囲を広げられる。
- 要約・索引から原典へ戻れる。
- 何を確認していないか分かる。

## LLMの仕組みから見ると何が起きているか

LLMは現在のコンテキストをトークン列として受け取り、Transformerで各位置の表現を更新し、次トークンを生成します。

つまり、コンテキスト設計はモデルの外側にある単なる整理術ではありません。**どの事実・コード・指示を次トークン予測の条件として与えるかを決める操作**です。

この理解があると、「長いプロンプトは悪い」「短いプロンプトは良い」という単純なルールから離れられます。必要な長いコードは読むべきですし、不要な短いメモは外すべきです。
