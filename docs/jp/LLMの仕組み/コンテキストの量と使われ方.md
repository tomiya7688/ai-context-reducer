# コンテキストの量と使われ方

「コンテキストを減らすのは、料金を節約するためだけでしょうか。大きなウィンドウへ全部入れれば、AIは必要な情報を選んで使ってくれるのではないでしょうか。」

**必要な根拠を残して不要な情報を減らすことには、回答や作業の品質を保ちやすくする意味もあります。** 長い入力の中で根拠を使い損ねたり、答えに不要な情報に判断を引っ張られたりする現象が、研究で観測されています。[1][2] 一方、判断に必要な情報を削れば、短い入力でも正しく作業できません。

この文書は、LLMの仕組みと情報を選ぶ手法をつなぎます。コンテキストという情報の意味は[コンテキストとは何か](コンテキストとは何か.md)、計算や課金の内訳は[コンテキストの量と計算量と料金の関係](コンテキストの量と計算量と料金の関係.md)で説明します。

## 「性能が落ちる」は何が悪くなることか

性能には、速さやメモリ使用量だけでなく、**質問に正しく答えること、必要な根拠を使うこと、指定された条件を守ること**も含まれます。以下では主に、この後者を「品質」と呼びます。研究で正答率を測ったことを、そのまま実際のコード修正の成功率へ読み替えないようにします。

コンテキストウィンドウは、入力と生成に使う容量の上限です。容量内であっても、情報をどの程度正しく使えるかは別問題です。長い入力の一か所を見つける試験に成功しても、複数の情報を結び付ける作業まで同じ品質でこなせるとは限りません。[3]

したがって、「上限を超えていないから問題ない」ではなく、「今回必要な情報を実際に使い、完了条件を満たしたか」で判断します。

## 長い入力ではどんな誤りが観測されているか

次の資料は、異なる問題を調べています。研究の名前だけを並べず、何を変えて何を観測したかを分けて読みます。

| 資料と対象 | 比較した条件 | 観測したこと | そこから言えないこと |
| --- | --- | --- | --- |
| **Lost in the Middle**（2023年に公開、2024年にTACLへ掲載された論文）[1]。当時のモデルによる複数文書の質問応答と、キーに対応する値の検索 | 長い入力の中で、必要な情報の位置を変更 | 先頭・末尾より中央で成績が下がる傾向 | 現在のすべてのモデルが、中央の情報を必ず見落とすわけではない |
| **GSM-IC**（ICML 2023）[2]。算数の文章題 | 元の解答に不要な情報を追加 | 対象モデル・評価方法で正答率が低下 | 算数の低下幅を、そのままコード修正へ適用できない |
| **RULER**（COLM 2024）[3]。17の長文対応モデル、13課題 | 入力長や課題を変え、検索だけでなく複数段の追跡・集約も検査 | 単純な検索に強くても、長さを増やした評価では多くのモデルで成績が低下 | 公称容量の大きさだけで、すべての作業の能力を決められない |
| **Context Rot**（Chroma、2025年7月14日の技術報告）[4]。研究全体で18モデル | 検索、会話履歴、反復などの実験で、入力長や紛らわしい情報を変更 | 長い入力での性能低下や、情報の内容による違いを報告 | 全実験に18モデルすべてが参加したわけではなく、普遍的な劣化開始トークン数も示していない |

論文と企業の技術報告は、発表形式も実験条件も異なります。ここでは特定のモデルの優劣ではなく、**情報が入っていても正しく使えるとは限らない**という性質の根拠として参照しています。

「無関係な情報」と「紛らわしい情報」も同じではありません。前者は問題に関係しない内容、後者は同じ話題や似た形を持ちながら今回の答えにはならない内容です。コードでいえば、無関係な画面の処理と、名前は似ているが旧版でしか使わない保存処理では、選び分ける難しさが違います。このコード例は本書の説明であり、上の研究で測定した結果ではありません。

## なぜ情報を選ぶことが品質につながるのか

LLMは、入力された各トークンの表現を計算し、Attentionなどを通して他の位置の情報を組み合わせ、次の出力を生成します。余分な資料も、入力に含めればこの計算の条件に入ります。[5]

ただし、Attentionは「今回の正しい根拠だけを必ず選ぶ装置」ではありません。古い仕様と新しい仕様を区別せずに渡せば、モデルには両方を見分ける仕事も発生します。関係する場所を先に選び、版や用途を明示すれば、その追加の選別を減らせます。

ここから本書が提案するのは、**回答の根拠を失わずに、候補の取り違えや余分な探索の要因を減らす**ことです。改善の程度は実際の作業で確認します。

「大量に読むと集中力が切れる」「Attentionが薄まる」といった比喩だけで、性能低下の原因を説明し切ったことにはしません。上の研究が示す観測結果と、個々の失敗を生む内部の仕組みの特定は別です。入力の配置、内容、課題、モデルの学習や構造などを切り分けず、一つの原因へ決めつけないでください。

## 同じ修正を「全部」「必要な根拠」「削りすぎ」で比べる

架空のアプリで、保存した設定が再起動後に消える不具合を直すとします。完了条件は、指定した保存先を使い、設定を保存して再起動した後も値が保たれ、関連する既存テストにも通ることです。

この例では、現在の仕様、保存処理、起動時の読込み処理、保存先を決める設定、関連テストが判断に必要だとします。以下は入力の作り方を比べるための仮例で、AIを動かして成功率を測った結果ではありません。

| 渡し方 | モデルへ渡す情報 | 何を余分に判断するか、何が不足するか |
| --- | --- | --- |
| **全部渡す** | 必要な根拠に加え、別画面のコード、古い保存方式の案、過去の全ログ | 現在使う仕様と実装を、大量の候補から選び直す必要がある |
| **必要な根拠を選ぶ** | 現行仕様と対象の保存・読込み処理、保存先の設定、関連テスト。版と場所も付ける | 今回の処理をたどり、同じ保存先を使うか確認する作業へ進める |
| **削りすぎる** | 保存する関数だけ | 起動時の読込み先と守る仕様がなく、保存関数だけでは正しい修正を決められない |

二番目が狙うのは、モデルに読ませる文字数の最小化ではありません。**今回の条件を確認するために必要な資料を、一緒に使える状態にすること**です。

三番目では、短い入力からもっともらしい変更を生成できても、再起動後の動作は確かめられません。モデルには、足りない読込み処理や仕様を取得させるか、不足を報告させます。推測で埋めた変更を完了とは扱いません。

なお、「古い資料だから常に不要」とも限りません。旧形式の互換性や移行が完了条件に含まれるなら、その旧仕様は必要な根拠になります。関連性は資料の長さや新しさだけでなく、今回の作業から決めます。

## 削減のメリットは料金以外にもある

**根拠を使い損ねる要因を減らせる可能性があります。** 必要な情報が保たれているなら、無関係・紛らわしい情報の除去を品質改善の候補にできます。[1][2][4] ただし、検索で必要な根拠を選べたかと、モデルがそれを使えたかの両方を確認します。

**入力処理と一時メモリの負担を抑えられます。** 全履歴を参照する基本的な構成では、短い入力にすることで計算する位置と参照相手、保持するKVキャッシュを減らせます。応答時間が同じ比率で短くなるという意味ではありません。詳しい仕組みは[計算量と料金の説明](コンテキストの量と計算量と料金の関係.md)にあります。

**次の作業に必要な情報を追加する余地を残せます。** 不要な履歴で容量を埋めなければ、新たに分かった依存先、失敗したテスト結果、出力や推論用の領域を確保しやすくなります。容量に余地を残すことと、モデルの品質を保証することは別です。

**従量課金の入力費用を抑えられます。** ただし、出力、キャッシュ、検索、要約などの費用も含めて比較します。定額の月額料金が自動的に下がるという話ではありません。数値の見方は[計算量と料金の説明](コンテキストの量と計算量と料金の関係.md)を参照してください。

**誤読が減れば、手戻りも減らせます。** 仕様の取り違えを防げたなら、追加説明、再修正、再検証を減らせます。これは間接的な利点なので、入力が短くなった事実だけでは効果を証明できません。正しい完了までのやり直しを測ります。

## 削減側にも失敗と追加の負担がある

検索結果に必要なファイルが出ないことがあります。ファイル名に「設定」がない共通処理などは、最初の検索だけでは候補から漏れ得ます。検索結果だけで対象を確定せず、実装の呼出し先やテストをたどって不足を確かめます。

また、長い原典を何でも短い要約へ置き換えると、条件や例外を落とします。例えば「認証を確認する」だけでは、どの操作にどの権限が必要か分かりません。Anthropicの実務解説も、過度な会話圧縮で後から重要になる情報を失う危険と、短さだけでなく十分な情報を保つ必要性を挙げています。[6]

索引や要約は**読む場所を探す手掛かり**として使い、細部を判断するときは原典へ戻ります。原典のパスや版を残しても、本文を読み直すまでは本文を確認したことにはなりません。

さらに、要約や再取得が増えれば、その時間と使用量が削減分を上回る場合もあります。少ない資料で完結する作業を、削減のためだけに何段階も分割する必要はありません。

## 情報の役割を分け、根拠に従って範囲を広げる

| 情報 | 作業での役割 |
| --- | --- |
| 依頼・完了条件 | 何を変え、どこまで確認するかを決める |
| 実装 | 現在の動作と変更場所を確認する |
| 仕様・規則 | 変更後に守る条件を確認する |
| テスト | 期待動作と回帰確認の手掛かりにする |
| エラー・ログ | 実際に起きた失敗を確認する |
| 検索結果・索引 | 原典へ進む候補を絞る |
| 要約 | 状態を短く受け渡すが、必要な判断では原典へ戻る |

役割を混同すると、検索結果だけを実装の証拠にしたり、古い要約を最新仕様として使ったりします。情報を減らす前に、判断と確認に必要な役割が欠けていないかを確かめます。

最初から必要範囲を完全に当てる必要はありません。

```text
依頼と完了条件を確認する
  → 候補を絞って原典を読む
  → 判断や検証に足りない情報を確かめる
  → 新しい依存先が分かったら、その原典と関連テストを読む
```

設定保存の実装を読んで、共通のシリアライザーが関係すると分かったなら、その処理と関連テストへ範囲を広げます。シリアライザーは、設定の値を保存用の形式へ変換する処理です。必要なコードが長いことを理由に省略しません。

## 減らして良くなったかをどう確かめるか

同じ種類の作業、同じ開始版、同じモデル・設定、同じ完了条件で比較します。選別方式を変えるとき、必要な根拠まで変わっていないかを先に確認します。以下は評価の計画であり、本書で実測済みの結果ではありません。

| 確認すること | 記録する例 |
| --- | --- |
| 必要な根拠が残ったか | 現行仕様、保存・読込み処理、関連テストの有無と版 |
| 品質を保てたか | 要求した動作、既存テスト、差分の確認、残った不具合 |
| 入力を減らせたか | 一回の入力と、作業全体の累積入力を別々に記録 |
| 全体の負担はどう変わったか | 出力・推論用・キャッシュの内訳、検索や要約を含む料金と経過時間 |
| 手戻りはどう変わったか | 追加説明、修正、再取得、再検証の回数と理由 |

成功した回だけを集めず、不足で停止した回や失敗も残します。可能なら同条件で複数回試し、結果の幅も確認します。使用量が取得できなければ、文字数の減少をトークンや料金の実績へ置き換えません。

記録の詳細は[作業ごとのコンテキスト使用量の目安を作る](../AI利用/作業ごとのコンテキスト使用量の目安を作る.md)にあります。このリポジトリの[実測ベンチマーク](../コンテキスト削減の実測ベンチマーク.md)も、実際のLLMの修正品質を測ったものか、渡す資料の量を測ったものかを区別して読んでください。

## 「最小」ではなく、正しい完了に必要な情報を選ぶ

コンテキスト削減の目的は、少ない情報でAIに無理をさせることではありません。**必要な根拠を正しく使えるように情報を選び、正しい結果を得るまでの費用・時間・手戻りを減らすことです。**

必要な長い原典は読み、不要な短いメモは外します。不足が分かれば追加し、未確認の範囲は報告します。実際に情報を選ぶ方法は[コンテキスト削減の基本](../コンテキスト削減の基本.md)と[手法一覧](../手法一覧.md)、初めてのコード変更では[変更に必要なファイルから読む](../変更に必要なファイルから読む.md)へ進んでください。
