# 今回の変更に関係するものから読む

調査する候補が多いときは、ファイルの大きさや変更頻度ではなく、今回の依頼にどれだけ関係するかで読む順を決めます。依頼に直接関係する実装、テスト、仕様から始めれば、無関係な大きなファイルや過去の履歴を開かずに済み、必要な情報へ早くたどり着けます。

## 例：CSVの日付形式を変更する

CSV出力の日付を `2026/10/05` 形式から `2026-10-05` 形式へ変えるとします。まず日付を出力する処理と、その形式を確認するテストを読みます。日付形式の取り決めがあれば、それも確認します。アプリで最も大きい画面ファイルや、過去に何度も変更された画面があっても、CSV出力に関係しないなら読む対象には加えません。

日付を出力する処理が大きなファイルに含まれていても、最初に全体を読む必要はありません。日付を扱う関数と、その呼び出し元・関連テストを探し、判断に必要な周辺だけを読みます。必要な情報が足りないと分かったときにだけ、範囲を広げます。

## 読む順を決める

依頼から変更の目的と完了条件を確認し、直接関係する実装とテストを特定します。外部との形式や呼び出し方を変える場合は、その取り決めと利用側も候補に加えます。候補の大きさや過去の変更回数は、読む必要性を決める根拠にはなりません。

大きさは「読むかどうか」ではなく「どの範囲を読むか」を考えるときに使えます。関連する大きなファイルなら、見出し、関数名、検索語で必要な部分を探します。小さくても今回の仕様を決めるファイルや、直接のテストなら優先して確認します。

## 範囲を広げるとき

実装を追って別の機能への影響が分かった、仕様とコードが食い違った、テストで予想外の失敗が出た場合は、原因を判断するのに必要なファイルを追加します。変更頻度が高い、サイズが大きいという理由だけで履歴や広い資料へ進む必要はありません。

変更箇所と確認方法が最初から明らかな小さな作業なら、特別な順位付けや分析は不要です。読む順を工夫するのは、候補が多く、どれが今回の判断に関係するか迷うときです。
