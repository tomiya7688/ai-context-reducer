# 参照先の目録（Context Manifest）

参照先の目録は、作業でよく調べる説明書・コード・テストの**場所と役割だけを並べた一覧**です。ファイルの中身をコピーして要約集を作るのではなく、「何がどこにあるか」を先に見つけやすくします。

たとえば CSV の日付変換に関する修正を頼まれたとき、リポジトリ全体から毎回 `csv` や `date` を検索して候補を読み比べる代わりに、目録から形式の説明、読み込み処理、関連テストの場所を確認できます。候補の所在が分かったら、今回の作業に関係する原典だけを開きます。そのため、関係のない機能や古い資料を先に読む量が減ります。

## 例：CSV の日付変換を調べる

目録には、たとえば次のように記録します。

| 場所 | 役割 | 何を確認するときに使うか |
| --- | --- | --- |
| `docs/csv-format.md` | CSV形式の説明 | 日付列の書式や互換性を確認する |
| `src/csv/importer.py` | 読み込み処理 | 文字列を日付へ変換する箇所を調べる |
| `tests/csv/test_importer.py` | 読み込みテスト | 既存の入力例と期待結果を確認する |

「CSV の日付がずれる」という作業なら、まずこの3か所が候補だと分かります。目録だけで原因を決めるのではなく、説明で対応形式を確認し、コードで変換方法を調べ、テストで現状と期待値を確かめます。関係しない画面や他形式の資料を端から開く必要はありません。

## 目録に書く内容

場所と、そこに何があるかが分かれば使えます。作業ごとの詳しい条件やファイル本文は入れません。

```text
場所                     役割              用途
docs/csv-format.md       形式の説明        列の書式と互換性
src/csv/importer.py      読み込み処理      文字列から値への変換
tests/csv/               関連テスト        入力例と期待結果
```

目録は手で短く作っても、既存のディレクトリ構成や検索用ツールから作っても構いません。すべてのファイルを網羅することより、繰り返し探す場所へ迷わずたどり着けることを優先します。候補が多くて一覧が読みにくくなったら、機能ごとに分けるか、今回の作業に関係するものだけ表示します。

## 使うときの手順

1. 作業の目的を確認します。
2. 目録から関係しそうな説明・コード・テストの場所を選びます。
3. 選んだ原典を開き、今回の作業に必要な範囲を確認します。
4. 関係がなかった候補は読まず、目録に不足があれば次回の探索で更新します。

目録に載っているからといって、毎回すべて読む必要はありません。たとえば形式変更がない不具合修正なら、形式説明は確認済みの内容だけで足りる場合があります。反対に、目録に必要な資料がなければ通常の検索を行い、新しい参照先を追加します。

## 他の文書との違い

| 文書 | 役割 |
| --- | --- |
| README / AI向け案内 | プロジェクトの入口と、最初に読む場所を示す |
| 現在の状態 | いま使える機能や既知の制約を伝える |
| 参照先の目録 | 繰り返し使う説明・コード・テストの場所を示す |
| [作業用メモ](作業用メモ.md) | 今回の作業で実際に確認する対象と完了条件を記す |
| 原典 | 仕様、実装、テストなどの判断根拠を保持する |

目録は「調べる候補の場所」を示し、作業用メモはその中から「今回使うもの」を選びます。仕様や実際の動作を確かめるときは、目録の説明ではなくリンク先の原典を確認してください。目録と原典の記述が食い違った場合も、原典を優先します。

## 作るとよい場合・不要な場合

同じ機能について何度も調査する、担当者が変わるたびに入口を探し直す、コード・仕様・テストの場所が離れている、といった場合は目録が役立ちます。候補を探す時間を初回にまとめて減らせます。

対象ファイルが依頼に明記されている小さな修正や、候補が数個しかない一度きりの作業では、目録を作る手間の方が大きくなります。その場合は依頼に直接参照先を書けば十分です。目録を作るのは、繰り返し探す手間が作成・更新の手間を上回るときです。

## 更新と注意点

ファイルの移動や役割の変更に気付いたら、該当する場所と説明を更新します。古い場所しか指していないと、読む人は存在しないファイルを探してしまいます。更新できる人や仕組みがない目録を巨大化させず、維持できる範囲に絞ります。

このリポジトリには目録づくりを補助するツールもありますが、利用は必須ではありません。ツールが出す一覧や順位は候補を探す手掛かりであり、どの資料が今回必要かは作業内容を見て決めます。

## AIに使わせる依頼例

単発の作業では、依頼文に本書を添付するかパスを書きます。繰り返し使う場合は、利用中のAIが実際に読むプロジェクト指示へ本書へのリンクを置き、自動で読み込まれる設定か確認します。

> 今回の変更に関係する仕様・コード・テストだけを目録から選び、パスと選んだ理由を先に示してください。選んだ原典を開いて確認し、参照したファイルと実行したテストを最後に報告してください。

## 補助ツール・用語

必要なら[context-manifest](../../tools/common/large/context-manifest/README.md)で目録を作れます。手作業でも実践できます。この方法は **Context Manifest（参照先の目録）** と呼ばれます。
