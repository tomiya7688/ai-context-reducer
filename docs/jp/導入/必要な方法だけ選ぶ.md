# 必要な方法だけ選ぶ

AIに渡す指示書や補助ツールは、最初から全部そろえる必要はありません。まず基本の進め方を決め、同じことで何度も困ったときに、その問題を減らす方法を一つ加えます。

プロジェクトの大きさではなく、実際に起きている困りごとから選んでください。

## まず整える基本

- AIに最初に読ませる短い指示書を置き、詳しい資料の場所を示す。
- ファイルを開く前に、名前や内容を検索する。
- 作業の目的と、何を確認したら終わりかを決める。
- 仕様を決めた資料を示し、実際の動きはコードやテストで確かめる。
- 関係のない修正を混ぜない。
- 関係するテストを行い、確認できなかったことも伝える。
- ログや自動生成ファイルは、必要なときだけ調べる。

小さなプロジェクトなら、これだけで十分な場合があります。

| ファイル名だけでは担当が分からない | [ファイルやフォルダーの担当を探す](../手法/ファイルやフォルダーの担当を探す.md) |

## 特定のプロジェクトで役立つ方法

| プロジェクトの特徴 | 役立つ方法 |
| --- | --- |
| 大きなコードや長いファイルがある | [関数や使われている場所を探す](../手法/関数や使われている場所を探す.md)、[今回読むファイルを選ぶ](../手法/今回読むファイルを選ぶ.md) |
| 画面やゲームなど、実際に動かして確認する必要がある | まず画面を出さずにできる確認を行い、必要な画面だけ目で確かめる |
| 保存・変換・配布の途中で別のファイルが作られる | 一時フォルダーで試し、最後に配布・保存されるファイルも確認する |
| 時刻、乱数、通信などで結果が変わる | 時刻や入力を固定し、同じ条件で確認できるようにする |

## なぜ繰り返しの困りごとから選ぶのか

目的に合う指示書だけを用意してAIに渡せば、毎回読む規則や一覧を増やさずに済みます。たとえばテストが数秒で終わる小さなプロジェクトなら、実行するテストの表を保つより、毎回すべて実行する方が簡単です。テストが多くAIに毎回長いログを渡しているなら、変更と関係するテストを選ぶ表が役立ちます。

## 効果が分かるまで加えないもの

- 更新や手入れが重い、大規模なコード一覧
- 何段階も処理する複雑な要約の仕組み
- AI向けの指示書を大量に作ること
- 小さなプロジェクトに大きな一覧や自動化を持ち込むこと

準備や手入れの手間が、繰り返し作業を減らす効果より大きいなら追加しません。

## AIに導入を手伝わせるとき

1. READMEと既存のAI向け指示書を確認し、プロジェクトの全ファイルを最初から読ませない。
2. 実際に繰り返し起きている困りごとを一つ挙げる。
3. その困りごとを減らす、最小の方法を選ぶ。
4. 新しい文書を増やす前に、既存の指示書へ短く追記できないか考える。
5. AIに関係するコードや確認方法を伝え、必要な場所にたどり着けるか確かめる。
6. 追加した方法と、追加しなかった方法・理由を短く報告する。

「将来便利そう」という理由だけで追加せず、実際に困っていることを解決するものだけを選びます。

## 判断のしかた

説明の聞き返しが繰り返される場合は、[修正前後で残る質問を比べる手順](../手法/読者が理解できる説明に直す.md#修正前後で聞き返しが減ったか確かめる)を使い、追加質問と実際の再説明を分けて記録してください。質問が減っても、操作や条件が誤っていれば改善とはしません。

困りごとが実際に何回起きたか、調査や確認にどれくらい時間がかかったかを記録します。方法を追加する前後で、探す時間、AIへ渡す不要な資料やログ、必要な確認の抜けを比べます。効果が分からない大きな仕組みは保留し、短い指示書を一つ足すところから始めます。

AIに選定を手伝わせるときは、次のように頼めます。

```text
このプロジェクトで実際に繰り返している困りごとを、既存の指示書と作業記録から確認してください。
困りごとを減らすための最小の変更を一つ提案し、準備や更新にかかる手間と、減らせる探す時間・読む量を比べてください。
効果が見込めない方法は追加せず、選んだ理由と見送った理由を短く報告してください。
```
