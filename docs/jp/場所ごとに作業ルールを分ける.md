# 場所ごとに作業ルールを分ける

大きなリポジトリでは、全体に共通するルールと、特定のアプリだけに必要な手順を別の場所に置きます。作業対象のファイルが決まったら、リポジトリ共通の案内と、そのファイルを含むフォルダーに適用される案内だけを確認します。

## 例：Desktopアプリの設定を直す

Desktopアプリの設定画面を変更するとします。プロジェクトにはDesktopとWebの両方があり、ビルド方法やテスト方法も異なります。

```text
repo/
  AGENTS.md                     # 全体で守るルールと案内先
  apps/
    desktop/
      AGENTS.md                 # Desktopだけのビルド・テスト手順
      src/settings/              # 今回変更するファイル
    web/
      AGENTS.md                 # Webだけのビルド・テスト手順
      src/
```

`apps/desktop/src/settings/`を変更するときは、全体に適用される`AGENTS.md`と、Desktop向けの`apps/desktop/AGENTS.md`を読みます。Webの手順は今回のファイルには適用されないため、読む必要がありません。

たとえば全体の案内には「保存形式との互換性を保つ」と書き、Desktopの案内には「Desktopの起動確認にはこのコマンドを使う」「設定画面のテストはこの場所にある」と書きます。Webだけで使うビルド手順を全体の案内から外すことで、Desktopの作業者は関係のない手順を読まずに済みます。

## ルールを置く場所

全体の案内には、どの部分を変更するときも守る条件と、各部分の案内の探し方を置きます。特定のアプリのビルド方法やローカル設計上の制約は、そのアプリのフォルダーに置きます。すべてのフォルダーに専用の案内を作る必要はありません。繰り返し必要な固有ルールがある場所だけに追加します。

上の例なら、Desktopの案内に全体ルールを丸ごとコピーせず、Desktopで追加して守る条件だけを書きます。親の案内が変わったとき、同じ文章を何か所も直す手間を減らせます。

## まずは短いAGENTS.mdから始める

利用中のAIが`AGENTS.md`を指示ファイルとして読むなら、ルートに一つ置き、全作業に共通する決まりと案内先だけを書きます。`AGENTS.md`はどのAIでも自動で読まれる共通規格ではありません。ツールが認識するファイル名と、下位フォルダーのファイルも読むかを設定や説明で確認してください。既に`CLAUDE.md`など認識されている案内がある場合は、同じ役割のファイルを重ねず、それを更新します。

ルートに置く内容は、たとえば次の程度です。

```markdown
# AGENTS.md
- 変更する動作、仕様、対応テストを確認してから編集する。
- `apps/desktop/`を変更するときは、そのフォルダーのAGENTS.mdも読む。
- 仕様やコマンドの詳細は、案内した原文書を参照する。
```

コマンド一覧、設計説明、全機能の注意書きをルートへ詰め込まず、該当するときだけ読む資料へリンクします。指示を短く保ちつつ、次に何を開くかを具体的に示せます。

## 繰り返す作業にはSkillsを使う

利用中のAIがSkillsに対応しているなら、API変更やリリース準備のように、決まった手順を繰り返す作業をSkillに分けられます。ルートの`AGENTS.md`には全作業に必要なルールを置き、Skillには「どんな依頼で使うか」「確認する順」「実行する検査」「完了時に報告すること」を書きます。Skillの形式、保存場所、呼び出し方はAIツールごとに異なるため、そのツールの仕組みに合わせます。

Skillには、使う条件と実行手順を書きます。登録形式はAIツールの説明に合わせます。

```markdown
# api-change-review
使う場面: APIの入力・出力や互換性を変更するとき
1. endpointと、そのAPIを使う側を探す。
2. 契約テストを確認し、変更に合うテストを実行する。
3. 調べたパス、結果、未確認の利用側を報告する。
```

自動選択されない場合は、依頼に「api-change-review Skillを使ってください」と書きます。Skills機能がない場合も、同じ手順を短いMarkdownに置き、作業依頼からそのパスを伝えれば実践できます。

## 肥大化させず、実際に使える状態を保つ

- まず一つの繰り返し作業だけを対象にする。案内があるだけで作業が変わらないものは追加しない。
- 各ルールを「使う条件 → 開く場所や行うこと → 確認方法」で書く。「品質に注意」のように次の行動が決まらない文は、具体化するか削る。
- 共通ルールはルート、フォルダー固有の手順は下位の案内、作業別の一連の手順はSkillへ置く。同じ説明を複数にコピーせず、詳細へのリンクを使う。
- 実際の作業を一つ依頼し、AIが適切な案内やSkillを選び、必要なコード・テストへ進むか確かめる。読み込まれたファイルを表示できるツールならその記録を確認し、表示できない場合は、報告されたパス・変更差分・検査結果が案内どおりか照合する。自己申告だけで自動読込を確認済みとはしない。
- ファイル移動やテスト変更に合わせてリンクとコマンドを更新する。使われない指示や重複した決まりは定期的に削る。

## 対象ファイルに適用される案内を読む

作業では、対象ファイルまでのフォルダーをたどり、その途中にある案内を確認します。

```text
repo/AGENTS.md
  └─ apps/desktop/AGENTS.md
       └─ apps/desktop/src/settings/config.py
```

`apps/desktop/src/settings/config.py`なら、ルートと`apps/desktop/`の案内が対象です。隣の`apps/web/`にある案内は対象外です。さらに`apps/desktop/src/settings/`にも案内がある場合、そのフォルダー内だけに適用される追加条件として確認します。

エージェントがフォルダーごとの案内を自動で読み込む機能を持たない場合は、ルートの案内に「対象ファイルまでのフォルダーにある案内を確認する」と書き、担当者がたどります。ファイル名や自動読み込みの範囲は使うツールによって違うため、既定だと思い込まず、プロジェクトの設定を確認します。

## 内容が食い違ったとき

ルートの案内はリポジトリ全体の条件、下位フォルダーの案内はその場所に追加される条件を説明します。たとえば、ルートが「保存形式を変えない」と定めているなら、Desktop向けの案内だけでその条件を無断で取り消してはいけません。作業依頼は今回の目的や完了条件を示しますが、長く有効なルールを黙って無効にするものではありません。

ただし、指示の優先順位は利用するエージェントやリポジトリの規則によって異なります。矛盾を見つけたら独自の順序で片方を選ばず、該当する仕様や原典を確認します。それでも決められない場合は、実装前に矛盾点を明らかにします。

## 使うと効果がある場合

アプリごとにビルドやテストが異なる、同じルールを毎回読み直している、ルートの案内が長くなっている、といった場合に役立ちます。対象のフォルダーから必要な案内だけを追加で読めるため、無関係なアプリの手順を作業ごとに読み込まずに済みます。

小さなリポジトリで、短い全体案内からコードとテストへ迷わず進めるなら、場所ごとの案内は不要です。ルールがほとんどないフォルダーに空の案内を作ったり、同じルールを複製したりせず、繰り返し必要になる場所から始めます。

## 導入するときの確認

1. どのルールがリポジトリ全体で共通かを決め、ルートの案内へ置きます。
2. 特定のアプリだけに必要な手順や条件を、そのアプリのフォルダーへ置きます。
3. 対象ファイルから、どの案内が適用されるか分かるようにします。
4. 1つの作業例を使い、関係する案内だけで必要な条件と確認方法が分かるか確かめます。

適用する案内を探す作業は、ファイルの場所を見ながら手でたどっても実践できます。

## AIへの依頼例

> 対象ファイルまでの親フォルダーにある案内を確認し、適用したファイルのパスを示してください。隣のアプリの案内は混ぜず、全体の規則と対象アプリ固有の手順を分けて説明してください。

## 補助ツール・用語

必要なら[scoped-guides](../../tools/common/small/scoped-guides/README.md)が、対象ファイルの親フォルダーにある適用候補の案内を探し、パスと理由だけを一覧にします。フォルダーに応じて案内を重ねる方法は **Hierarchical Context / scoped instructions** と呼ばれます。
