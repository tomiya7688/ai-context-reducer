# 現在の状態を短くまとめる

プロジェクトで今できること、分かっている制約、まだできないことを、短い文書にまとめておきます。作業のたびにREADMEや過去のIssueを読み直さなくても、現時点の前提をつかめるようにするためです。詳しい仕様や今回の作業内容を、この要約に書き写すものではありません。

## 例：CSV読込機能の現状

たとえば、次のような要約を置きます。

> CSV読込はUTF-8に対応。日付はタイムゾーンを扱わない。Excel形式の読込は未対応。詳しい日付形式は `docs/csv-format.md` を参照。

「Excel形式にも対応したい」という依頼を受けたAIは、この要約から現在の対応範囲を知り、CSV形式や日付の過去の議論を最初から読み直さずに、該当機能と今回の要件を確認できます。要約は調査の入口なので、具体的な実装や細かな日付仕様を変更するときは、リンク先の説明、コード、テストを確認します。

## 何を書くか

繰り返し作業で前提になる事実に絞ります。

- 現在利用できる主な機能
- 現在の制約
- 既知の未対応事項
- 詳細を確認するための参照先

すべての機能や未完了Issueを並べる必要はありません。作業の判断に使わない情報を増やすと、要約自体が毎回読む負担になります。

## 更新するときの注意

実装やテストと食い違う記述は、現在の事実として扱わず確認します。機能を変更したら、今回の変更に関係する要約の記述と参照先を更新します。未確認の内容は、確定した事実のように書かず、未確認だと分かる形にします。

この要約は、詳細仕様、変更履歴、優先順位、作業ごとの完了条件の代わりにはなりません。それらが必要な作業では、それぞれの原文書やIssueを確認します。

## 作るとよい場合・不要な場合

複数の依頼で「今どこまで対応しているか」「既知の制約は何か」を毎回調べ直しているなら、短い状態メモが役立ちます。たとえば「CSV読込はUTF-8に対応、日付はタイムゾーン非対応、Excelは未対応」と入口に置けば、AIは詳細な過去のIssueをすべて読み直さず、今回の依頼に関係する機能と仕様へ進めます。

一度きりの作業で、最新のREADMEに機能と制約が明記されているなら、別の要約は不要です。機能が頻繁に変わり更新を保てない場合も、要約を増やさず、現在の仕様書やテストへ直接案内してください。

## AIに使わせる依頼例

要約を依頼に添付するか、作業対象のプロジェクトでAIが実際に読む案内からリンクします。自動で読まれるかは利用するAIの設定で確かめます。

> まず現在の状態メモを読み、この依頼に関係する記述だけ使ってください。詳しい仕様や動作を判断するときはリンク先の原典を確認し、要約と原典が違えば違いを報告してください。

## 補助ツール・用語

専用ツールは不要です。READMEや短い手動メモで始められます。現状の機能と制約を短く残す方法は **Context State（project snapshot）** と呼ばれることがあります。
