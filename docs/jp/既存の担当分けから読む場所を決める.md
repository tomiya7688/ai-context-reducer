# 既存の担当分けから読む場所を決める

大きなソフトウェアでは、画面、データの取込、保存など、部分ごとに担当が分かれていることがあります。すでにある担当分けを調査の案内に使えば、変更に関係する部分から読み始められます。プロジェクト全体の構造を毎回読み直さずに済むため、必要な情報へ早くたどり着けます。

## 例：CSV取込の日付を直す

CSVを読み込むと日付がずれる問題を直すとします。プロジェクトの案内に「CSVの読込と変換は取込機能が担当する」と書かれていれば、まずその機能と対応するテストを確認します。画面の表示や、読み込んだ後の保存処理は、取込機能とのつながりが変更に影響すると分かった場合に調べます。

この順序なら、最初から画面・保存・帳票など全機能の説明を読む必要がありません。取込機能の案内は読む入口を決める目印です。実際の動作やテストが案内と異なる場合は、案内をうのみにせず、実装とテストを確認します。

## 担当分けを読む案内に使う

変更したい内容に対応する担当部分を既存の設計書や開発案内で探し、その部分の実装と確認方法から読みます。変更がその部分の中で完結するなら、関係の薄い部分まで読む必要はありません。

一方、画面と取込機能の間の約束や、保存形式など、担当部分どうしの取り決めを変える場合は、片側だけでは判断できません。取り決めの内容と両側の実装・テストを確認します。

## 案内がない、または合わないとき

プロジェクトに担当分けの説明がない場合は、新しい構造を推測して作る必要はありません。通常の検索や既存のコード索引から対象を探します。案内が古い、変更内容をどの担当にも当てはめられない、案内に従っても対象を絞れない場合も同じです。

読む範囲を狭くするために、関係があるかもしれない部分を無理に外してはいけません。新しい依存や影響が見つかったら、そのつながりを確認するのに必要な範囲を追加で読みます。小さなプロジェクトで変更箇所とテストが初めから分かるなら、担当分けを別の案内表にまとめる必要はありません。

## AIへの依頼例

> 既存の担当範囲から、今回の変更を所有する部分と直接関係するテストを選んでください。境界をまたぐ場合は両側の契約と実装を示し、根拠のない新しい担当分けを作らないでください。

## 補助ツール・用語

必要なら[architecture-boundary-router](../../tools/common/medium/architecture-boundary-router/README.md)が、既存の構成情報から作業対象の境界や先に読むファイルの候補を示します。適合判定や責任の確定はしないため、原典の案内とコードで確認してください。この方法は **Architecture Boundary Routing** と呼ばれます。
