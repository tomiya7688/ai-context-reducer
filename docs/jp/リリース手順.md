# Releasing v1.x

v1.0.0は最初のユーザー配布版です。v1.0.xのパッチ版は、公開CLI / JSON contract / bundle contentsを維持した保守変更として同じcompletion gateで検証します。

## Release gate

Releaseの現在のgateは `.github/workflows/release.yml` です。文書上の説明ではなく、このworkflowと `release/scripts/acceptance.sh` が実際に行う検証を基準にします。

### Source validation

Ubuntu runner上で、repository整合性とacceptance scriptの構文、全Python toolのcompileとtest、全Go moduleの `go vet` / `go test` / `go test -race` を確認します。

### 通常版の配布検証

Windows x64 / arm64、Linux x64 / arm64、macOS x64 / arm64の各runnerで、通常版に含めるbinaryをbuildし、fixtureを使った `release/scripts/acceptance.sh` を実行します。acceptanceでは主要commandの出力、policy違反・template drift・Large実行の確認要求などのstatus / exit code、生成物を確認します。

### Archive validation and re-extracted E2E

各platformでarchiveを作成した後、再展開して内容を確認し、**同じfull acceptance scriptを再展開後のarchiveに対してもう一度実行**します。最後に6archiveの揃いと `SHA256SUMS` を確認します。いずれかの必須jobが失敗すればRelease jobへ進みません。

### Full Bundle smokeとv1.1.0で残るgate

各platformのE2Eでは、通常版coreへGUI Hub binaryを加えたsmoke用Full Bundleも組み立て、loopback URLでの起動とhealth API応答を確認します。このsmokeは起動境界のみを対象とし、Full Bundle manifestに基づくarchive全体やGUIの全actionを検証するものではありません。

現行workflowでは、Python tool entrypoint・wrapperを含む全user-facing scriptの入出力・副作用のE2Eと、clean environmentで追加runtimeが不要なことの検証は保証していません。v1.1.0では、これらを #32 のcompletion gateへ組み込む前提です。#33でsource/script・build binary・再展開archive間の入出力・exit code・生成物の期待値を確認し、#34で追加環境構築が不要なこととoptional dependency不在時の挙動を確認します。検証が実装され、CIでgreenになるまでは完了済みとして扱いません。

## User distribution

`release/RELEASE_MANIFEST.json` を現在のv1.0.x配布内容のSource of Truthとします。

必須内容:

- `acr-toolbox`
- `go-symbols`
- `go-import-map`
- `go-package-graph`
- `affected-tests`
- `README.md`
- `TOOLS_README.md`
- `LICENSE`
- `RELEASE_MANIFEST.json`

Windows executableには `.exe` suffixを付けます。

## Platforms

```text
ai-context-reducer-v<version>-windows-x64.zip
ai-context-reducer-v<version>-windows-arm64.zip
ai-context-reducer-v<version>-linux-x64.tar.gz
ai-context-reducer-v<version>-linux-arm64.tar.gz
ai-context-reducer-v<version>-macos-x64.tar.gz
ai-context-reducer-v<version>-macos-arm64.tar.gz
SHA256SUMS
```

現在のcandidate versionは `release/RELEASE_MANIFEST.json` の `release_version` と一致させます。

## Bundle variants

v1.1.0以降は、軽量な通常版とGUI Hub付きFull Bundleを別artifactとして扱います。

- 通常版: release/RELEASE_MANIFEST.json
- Full Bundle: release/FULL_BUNDLE_MANIFEST.json
- Full Bundle layout / compatibility: docs/jp/Full Bundleの配布構成.md

Full Bundleは通常版root contentsをそのまま含む上位集合とし、Go sourceやGo toolchainを利用者へ要求しません。

## Candidate validation

mainへのpushでworkflowのpath filterに一致した場合は同じcompletion gateを実行し、`v1-release-candidate` artifactを生成します。Release関連の文書だけを変更したpushなど、filterに一致しない変更ではこのworkflowは起動しません。candidate CIはReleaseを公開しません。

main上のcandidate CIがgreenでも、tagやGitHub Releaseを自動作成しません。

## Publishing

公開は必ず明示操作を起点にします。

```text
main candidate CI green
  -> 配布内容とbug checkを最終確認
  -> 人がrelease tagを作成してpush
  -> tag commit上でcompletion workflowを再実行
  -> 全job success
  -> GitHub Releaseを作成
```

`v1.0.0` 以降、main pushやREADY markerからtag/Releaseを自動promotionする経路は持ちません。

workflow_dispatchからpublishする場合も、matching tagがrepositoryに存在することを必須とします。

## Post-release

v1.0.0後の新言語対応、外部backend追加、heuristic改善は新しいIssueとして管理します。patch releaseの完了条件へ新機能を後付けしません。
