# 今回の変更に関係する規則を確認する

開発規則が長いときは、作業を始める前に今回の変更に適用される決まりを探します。関係する節と、既に自動で確認できる項目だけを先に押さえれば、無関係な設計規則や説明を毎回読み直さずに済みます。

## 例：新しいAPIを追加する

新しいAPIを追加する作業で、規則集に「APIは認証を必須とする。ただし公開APIは例外として明記する」「エラー応答に秘密情報を含めない」と書かれているとします。まずAPIに関係する二つの決まりと、その確認方法を読みます。画面の色や文書の書式など、今回のAPIに適用されない規則は、必要が生じるまで読まずに済みます。

認証の有無を検査する仕組みが既にあれば、その結果を確認します。自動検査で扱えないエラー内容は、実装とテストを見て確かめます。検査が成功しても、検査対象外の規則まで守られたとは限りません。

## 確認する規則の選び方

変更する場所と内容を手掛かりに、適用される必須規則を探します。規則が当てはまるか判断できない場合は、関連する説明や原文書を開きます。推奨事項や参考情報は、今回の判断に影響するときに確認すれば足ります。

作業中に別の機能へ影響することが分かった場合や、規則どうしの矛盾が見つかった場合は、必要な節を追加で確認します。規則の適用範囲が分からないまま、検索を減らすために読み飛ばしてはいけません。

## 自動検査について

機械で確実に判定できる規則は、既存の検査があれば利用します。検査結果は、何を確認したかに限って判断材料にします。検査に失敗した項目や、機械で判断できない規則は、該当箇所を人が確認します。

自動検査がない規則をすべて機械化する必要はありません。新しい検査を加えるのは、繰り返し確認する価値があり、誤判定せずに判定できる場合に限ります。

## AIへの依頼例

> 今回の変更に適用される必須規則を原典から特定し、関係する規則と根拠箇所だけ示してください。機械検査がある規則は検査範囲と結果を報告し、人の判断が要る規則は該当するコードやテストを確認してください。

## 補助ツール・用語

規則の候補探しは[policy-index](../../tools/common/medium/policy-index/README.md)、対応する機械検査は[policy-check](../../tools/common/medium/policy-check/README.md)で補助できます。この方法は **Policy Routing** と呼ばれます。
