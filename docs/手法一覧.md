# 手法一覧

AI Context Reducerで扱う手法の目次です。

個別の手法は別々の魔法のような技術ではありません。基本的には、[`コンテキスト削減の基本`](context-reduction-basics.md) にある次の3原則の組み合わせです。

1. 静的解析できるものは静的解析する
2. よく使う操作をまとめる
3. 一部だけ読ませる

全部を導入する必要はありません。対象projectで繰り返し発生している無駄に効くものだけ選びます。

## 一言で見る手法一覧

| 手法 | 一言でいうと | 主に減らすもの |
|---|---|---|
| Current State | 今できること・制約・未実装を短く固定する | 現状確認のためのREADMEや履歴の再読 |
| Context Pack | 今のtaskに必要なGoal・根拠・対象だけを小さくまとめる | task開始時の広い探索 |
| Task Routing | taskの種類から読むdocs / source / testsを決める | 関係ない領域の探索 |
| Exploration Control | 必要情報が揃ったら探索を止める | 念のための追加検索・再読 |
| Evidence Budget | Required evidenceの不足だけを追い、十分なら止める | 過剰な証拠集め |
| Change Routing Map | 変更内容から触るsource / tests / docsへ案内する | 変更箇所を探す反復作業 |
| Hierarchical Context | そのdirectoryに必要な指示だけ読ませる | 無関係なsubsystemルール |
| Validation Routing | 変更に必要な最小十分の検証だけ選ぶ | 毎回のfull test / full validation |
| Change / Test Impact Routing | 変更箇所から影響するtestを絞る | 不要なtest実行とtest探索 |
| Responsibility Map | file / moduleが何を担当するかを短く示す | 名前だけでは分からない責務探索 |
| Policy Routing | 規則を対象・強さ・判定方法で振り分ける | 長い規約の毎回再読 |
| Remote Delta First | remoteの差分だけ先に見て変化を把握する | repository全体の再確認 |
| Source Structure Index | symbol / dependencyを機械解析して必要部分だけ引く | 大規模sourceの全文読解 |
| Boilerplate Generation | 定型文や定型fileをtemplateから生成する | AIに同じ定型作業を繰り返させること |

## 詳細リンク

### 現在のtaskを小さくする

- [Current State](context-state.md) — 現在の能力・制約・未実装を短い状態情報として持つ。
- [Context Pack](context-pack.md) — task固有のGoal / Required / Acceptance / pointerをまとめる。
- [Task Routing](task-routing.md) — taskから必要な文書・source・testへ直接案内する。
- [Exploration Control](exploration-control.md) — 探索を続ける条件と止める条件を決める。
- [Evidence Budget](evidence-budget.md) — Required evidenceが足りているかだけを管理する。

### 変更対象を絞る

- [Change Routing Map](change-routing-map.md) — 変更カテゴリとsource / tests / docsを対応付ける。
- [Responsibility Map](responsibility-map.md) — file / moduleの責務から候補を絞る。
- [Hierarchical Context](hierarchical-context.md) — scope固有のAI向け指示だけを適用する。
- [Remote Delta First](remote-context.md) — concurrentな変更をcompact deltaから確認する。

### 構造を機械的に調べる

- [Source Structure Index](source-structure-index.md) — symbol / dependency / changed-symbol等をindex化し、必要部分だけ取得する。

### 検証を絞る

- [Validation Routing](validation-routing.md) — 変更内容に応じて必要な検証へroutingする。
- [Change / Test Impact Routing](change-impact-routing.md) — 変更から影響testを選び、必要時だけ広いtestへfallbackする。

### 規則・反復作業をAIの外へ出す

- [Policy Routing](policy-routing.md) — machine-checkableな規則とsemantic reviewを分離する。
- [Boilerplate Generation](boilerplate-generation.md) — license / NOTICE / header等の定型出力を再利用可能な生成処理へ移す。

## どれを選べばよいか

全部を読む必要はありません。

まず [`導入優先度`](adoption-priority.md) でprojectの特徴を確認し、必要な手法だけこのページから開きます。

```text
3原則を理解する
  -> projectの困りごとを見る
  -> 対応する手法を1つ選ぶ
  -> 必要ならtoolで反復部分を補助する
```

toolそのものの用途を知りたい場合は [`tools/README.md`](../tools/README.md) を参照してください。v1.1では、各toolの用途・入力・出力・対応手法をまとめた専用tool guideも用意します。
